argument-hint: <task-dir>（例: tasks/feature/task-260601153000-foo）

`$1` を対象に、以下の作業手順を実行する。各段階は対応するサブエージェントに
委譲し、状態は `$1/` 配下のファイル（`task.md` / `review.md` / `impl.md` / `eval.md`）で受け渡すこと。
サブエージェントは `meta.yaml` を触らない。`meta.yaml` の更新はこのオーケストレーターが
`tasks:set` / `tasks:close` 経由で行う（規約は `tasks/README.md`）。

各ステップの完了時は、サブエージェントの\*\*最終メッセージ（判定と特記事項の要点）を確認し、
かつ対応する状態ファイル（`review.md` / `impl.md` / `eval.md`）を必ず読んでから次へ進む。
サブエージェントは親の履歴を継承しないため、最終メッセージと状態ファイルが唯一の引き継ぎ手段になる。

> 補足: 下記の `tasks:set` / `tasks:index` / `tasks:reindex` / `tasks:close` / `tasks:metrics` /
> `eval:worktree` / `gate` はプロジェクトのスクリプトランナーで実行する
> （例: `npm run tasks:set ...` / `pnpm tasks:set ...` / `bun run tasks:set ...`）。
> 「3 点ゲート」= 静的解析・整形検証、型検査・ビルド、テスト。`npm run gate`（`scripts/gate/gate.mjs`）で
> 回し、ステップの実コマンドは `package.json` の `gateSteps` を正本とする。

## 1. レビュー段（3 段ゲート — /new-task 済みタスクのフルレビュー重複を避ける）

`$1/meta.yaml` の `review` / `reviewed_sha` を読み、次の順に分岐する。

### 1-a. 機械スキップ（エージェント起動なし）

`review=APPROVED` かつ `reviewed_sha` があり、
`git diff --name-only <reviewed_sha>..HEAD -- ':!<タスク格納ルート>'` が**空**なら、レビュー時点から
コードベースは進んでいない。レビュー段を**スキップ**して実装へ進む
（要約報告にスキップ根拠として `reviewed_sha` を記す）。

### 1-b. 鮮度チェック（task-freshness-checker・軽量）

`review=APPROVED` だが上記 diff が空でない、または `reviewed_sha` が無い場合は、
task-freshness-checker サブエージェントに `$1` と基準 SHA（`reviewed_sha`、無ければ
「基準 SHA なし」と明示）を渡し、**前提の鮮度のみ**確認させる。仕様の質は再評価させない。

- **FRESH** → 実装へ進む（申し送り〔行ずれ等〕があれば実装担当の指示に含める）
- **STALE** → 1-c の全体レビューに戻す（崩れた前提の列挙をレビュー担当の指示に添える）

### 1-c. フルレビュー（task-reviewer）

`review` が null / NEEDS_REVISION、または 1-b で STALE の場合のみ、task-reviewer
サブエージェントで `$1/task.md` をレビューさせ、結果を `$1/review.md` に出力させる。

- 判定が NEEDS_REVISION の場合: `tasks:set $1 review=NEEDS_REVISION` を実行し、
  指摘を要約してユーザーに提示して停止する。
- 判定が APPROVED の場合: `tasks:set $1 review=APPROVED reviewed_sha=$(git rev-parse HEAD)`
  を実行し、次へ進む。

## 2. 実装

task-implementer サブエージェントで、**実装段階専用の隔離作業ツリー上で**実装させる。
メインチェックアウトでは編集・コミットさせない（同一 clone で `/run-task` を並走させたとき、
メインの作業ツリー・HEAD を共有しないため安全になる。並列実行モデルは `tasks/README.md`
「ブランチライフサイクル」参照）。

- 実装ブランチ名は `package.json` の `taskBranchPrefix`（既定 `task/`、未設定時も `task/`）を読み
  `<prefix><task-id>`（既定 `task/<task-id>`）とする。
- **作業ツリーを構築する**: `npm run eval:worktree add <現在ブランチ HEAD SHA> --branch <prefix><task-id>`
  を実行する。指定ブランチが未存在なら現在 HEAD を基点に新規作成、既存（再実装ループ）なら
  そのブランチをチェックアウトした作業ツリーを、依存ディレクトリのシンボリックリンク・Git 管理外の設定ファイルの
  コピー（`package.json` の `evalWorktree` 設定が正本。`.gate-cache` 既定含む）つきで構築し、作業ツリーの
  絶対パスを標準出力の最終行に出力する。この **作業ツリーの絶対パスを `<wt>` として実装担当に渡す**。
    - 実装段階はメインチェックアウトへ変更を残さないため、着手前のメイン側 `git status`
      による変更なし判定は行わない（従来の判定は並走時の検査と使用の時間差に対応できないため撤去）。
      隔離は「専用作業ツリーに新規ブランチを切る」ことで保証する。
- 呼び出しプロンプトに `$1/task.md` と `$1/review.md` のパス、および構築済み `<wt>` 絶対パスを
  明記すること（サブエージェントは親の履歴を継承しないため）。1-b の鮮度確認による申し送りが
  あればそれも含める
- 実装者は **`<wt>` を作業ディレクトリとして**全ファイル操作・コミット・`npm run gate` を行う
  （Edit は `<wt>` 配下の絶対パス、git は `git -C <wt>`、gate は `<wt>` を cwd に実行）。状態ファイル
  （`task.md` / `review.md` / `impl.md`）は従来どおりメインチェックアウト側の `$1`（`<task-dir>`）を
  読み書きする（作業ツリーには置かない）
- 実装者は `<prefix><task-id>` ブランチ上で、区切りごとにコミットする
- 開発の赤→緑ループは**変更レイヤだけ**を高速に回させる（テストランナーのパス/フィルタ指定）。
  フルビルドや全テストを毎イテレーションで回さない
- 完了報告の前に 3 点ゲートを **`npm run gate`** で通させる（静的解析・整形検証、型検査・ビルド、
  テスト。`gate` は PASS 結果をコミット SHA 単位でキャッシュするため、後段の評価者が
  同一コミットを検証する際に再実行せず結果を利用できる。`.gate-cache` は作業ツリー間でシンボリックリンク共有
  される。仕組みは `scripts/gate/gate.mjs`）
- 実装者は作業ログ（判断・逸脱・詰まり）をメインチェックアウト側の `$1/impl.md` に追記する。
  `task.md` は触らせない
- 実装担当へ、タスク固有のツール群、作業ツリーの依存物、固定データ、ソケット、ブラウザー・FFmpeg などを
  実装開始時に読み取り専用で事前確認し、環境不備を実装上の不具合と混同しないよう指示する
- **実装作業ツリーはこの段では破棄しない**。再実装ループ（§4）で再利用し、最終確定（§5）の後に
  片付ける

## 3. 評価

impl-evaluator サブエージェントで実装を独立検証させ、結果を `$1/eval.md` に出力させる。

- 評価に渡す前に実装者の変更がすべてコミット済みか確認する（未コミット変更が残っていると
  「クリーンな状態」が崩れる）
- **評価は実装者 HEAD から作った隔離作業ツリーで行わせる**。構築・破棄は専用スクリプトに
  固定化済みで、手組みさせない:
    1. `npm run eval:worktree add <実装者 HEAD SHA>` — 作業ツリー 展開・依存ディレクトリの
       symlink・gitignore された設定ファイルのコピーまでを行い、作業ツリー パスを stdout 最終行に
       出力する（対象は `package.json` の `evalWorktree` 設定が正本。submodule を持つ
       プロジェクトは `scripts/eval/setupWorktree.mjs` に展開処理を足してカスタマイズする）
    2. 評価完了後は `npm run eval:worktree remove <パス>` で片付ける。dirty（未追跡・
       未コミット変更あり）な 作業ツリー は既定で削除を拒否し保全候補パスを表示する（安全網）。
       コピーバック漏れがあっても無言破棄しない。破棄してよいと確認できた場合のみ `--discard`
       を付ける

    ゲートのキャッシュは作業ツリー間で共有するため、同一コミットなら評価側でも即座に結果を利用できる

- **評価成果物の出力先**: `eval.md` は**常にメイン作業ツリー側の `$1`（`<task-dir>`）に書く**
  （作業ツリーはゲート実行・検証専用。`eval.md` をコピーバックする必要は無い）。検証テストを
  作業ツリー内で生成・実行した場合は、**`eval:worktree remove` の前に**作業ツリーの `acceptance/` を
  メイン作業ツリーの `$1/acceptance/` へコピーバックする（コピーバック後に削除する）
- 評価者はクリーンな状態で 3 点ゲートを **`npm run gate`** で独立実行する。実装者が
  同一コミットで既に通していれば**キャッシュヒットで即時**（独立性はコンテンツアドレス＝
  実ツリー SHA をキーに担保。実装者の自己申告ではない）。そのうえでカバレッジの十分性まで
  検証する
- 実装コードと実装者のテストは変更させない。検証テストの追加は
  `$1/acceptance/` 配下に限定させる

## 4. 再実装ループ

評価が FAIL の場合、`$1/eval.md` の残課題を task-implementer に渡して再実装させ、
再度 impl-evaluator で評価する。

- `eval.md` の不合格分類が `task_revision_required` または `stale_task` の場合は、
  再実装へ直行しない。実装ブランチ/作業ツリーを保持し、`tasks:set $1 review=NEEDS_REVISION`を実行して
  task-reviewer の全体レビューへ戻す。承認済みタスクの受け入れ条件を実装者や評価者が暗黙に拡張しない。
- 最大 2 回まで反復する
- PASS または上限到達で停止する
- **再実装は §2 で構築した同一の実装作業ツリー（`<wt>`）を再利用する**（実装ブランチ
  `<prefix><task-id>` がそこにチェックアウトされたまま追加コミットを載せる）。作業ツリーを破棄して
  しまった場合は `npm run eval:worktree add <最新 HEAD SHA> --branch <prefix><task-id>` で
  同一ブランチを別作業ツリーに再展開してよい（既存ブランチをチェックアウトする）
- 再実装時も実装者は `$1/impl.md` に `## attempt <n>` を追記する（過去ログは消さない）

## 5. 最終確定と完了処理

PASS した場合のみ最終確定する。実装ブランチ `<prefix><task-id>` は実装作業ツリー（`<wt>`）に
チェックアウトされたままなので、**同一ブランチを 2 箇所でチェックアウトできない Git の制約**を踏まえ、
**マージ → 完了処理 → index 再生成（reindex）→ 作業ツリー片付け**の順で確定する（順序を入れ替えない）:

1. **マージ（メインチェックアウトの基点ブランチ上）**: メインチェックアウトは基点ブランチを
   チェックアウトしたまま、`git merge <prefix><task-id>` で実装ブランチを取り込む（履歴整理 /
   本流への `--no-ff` マージは運用方針に従う）。Git は他作業ツリーがチェックアウト中のブランチでも、
   それを**自分がチェックアウトしない**マージは許可するため、実装作業ツリーを先に片付ける必要はない。
   最終確定は task-implementer に指示してよい（マージ自体は基点ブランチ＝メインチェックアウト側）。
2. **完了処理（基点ブランチ上）**: **`tasks:close $1 verdict=PASS attempts=<反復回数>`** で確定する
   （meta 更新〔closed_at 自動〕→ **自タスクディレクトリのみ**のコミットまでを 1 コマンドで行う）。
   **全体の index 再生成（カテゴリ `index.md`）は完了処理から分離した**ため、完了処理は `index.md` を
   一切 stage / コミット しない。フォーマッタが Markdown を対象とするプロジェクトでは、md 成果物
   （`review.md` / `impl.md` / `eval.md` 等）を整形してから完了処理する（非冪等な再整形による
   後追い差分を防ぐ）。
3. **index 再生成（基点ブランチ上・直列ステップ）**: **`tasks:reindex`** で全カテゴリ `index.md` を
   再生成し、変更があれば `chore(tasks): reindex` で 1 コミットする（変更が無ければ何もコミット
   しない）。マージは git により基点ブランチ上で直列化されるため、この reindex も同じ直列区間に
   入り、index は常にマージ後の全体像から一意に生成される（タスクごとの完了処理は互いに素なパスのみ
   を触り、並列・作業ツリーのマージで `index.md` が衝突しない）。
4. **作業ツリー片付け**: マージ・完了処理・reindex 完了後に **`eval:worktree remove <wt>`** で実装
   作業ツリーを破棄する（`git worktree remove` はブランチを消さないため、実装ブランチは残る）。変更が残っていれば
   なら拒否される（コミット漏れの安全網）。

- FAIL のまま上限到達した場合は状態を `open` のままにし、
  **`tasks:close $1 verdict=FAIL attempts=<反復回数>`** で記録・コミットしてから残課題を報告する。
  実装ブランチ・実装作業ツリーは破棄せず保持する（再開のため）。

## 6. 要約報告（書式固定）

最終報告は**必ず**次の見出し構成で行う（順序・見出し名を変えない。該当が無い節は「なし」と書く）:

```
### タスクで行なったこと
（受け入れ条件と対応づけた変更概要・実装コミット範囲・最終状態・合否）

### 各エージェントからの報告事項
- レビュー担当: 判定と申し送りの要点。1-a でスキップした場合は「スキップ（reviewed_sha=<sha> から差分なし）」、
  1-b の場合は鮮度判定と申し送り
- 実装担当: 変更概要・`review.md` 申し送りへの対応・逸脱・詰まり
- 評価担当: 判定・網羅性・ドキュメント整合の所見

### 実績
- `tasks:metrics $1` を実行し、リードタイム（起票→完了処理）とサブエージェント実行の
  所要時間・トークン集計を転記する
- 試行回数

### 残課題

### その他特記事項

### 次のタスク提案
- `tasks:next` を実行し、READY 先頭の推奨タスクと `/run-task <dir>` への投入可否を提示する
```
