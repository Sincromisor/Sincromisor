# 実装判断と未実施事項

## 終了処理

確認した配布イメージの`timeout`はuutils 0.10.0であり、TERMを無視する人工journalctlとその子のsleepが、KILL段階を過ぎても生存するケースを再現した。Ubuntuに同梱済みのGNU版`gnutimeout`へ切り替え、追加の依存インストールは行っていない。TERMを受けた親シェルが前景処理を待つtrapも設け、強制終了まで監視対象を維持した。3回の実装試行（初回、TERM待機追加、GNU版への切替）で対象テストが通った。

`init: true`は終了済み孤児の回収を担う。生存中の子孫の停止はGNU timeoutのプロセス群へのシグナルで行い、両方をコンテナ内で確認した。Docker自身の12秒制限を変えず、10秒でTERM、1秒後にKILLとする。

## 所要時間と確認範囲

カーソル読取のhead・grepをシェル処理へ置き換え、外部プロセスとパイプを減らした。通常時の`--cursor -n 1`も従来から1件を読むため、`-n +1`への変更だけで通常時の全件走査を解消したとは扱わない。初回の確認位置は末尾から先頭1件へ変えた。実journalの確認には専用コンテナ内のjournaldと人工2件を使い、ホストの原本は読んでいない。

報告対象のコンテナは接続先に存在せず、実環境への反映と既存ゾンビ解消、6.7〜10.3秒という報告値との性能比較、長時間の再発監視は未実施である。配置先で変更を取り込んだ後、[ログ設計の反映手順](../../../documents/design/infrastructure/logging.md#ホストのjournal)に従ってVectorだけを再作成する必要がある。journalへのI/O自体が遅い場合でも、時間制限と回収が働く構成とした。
