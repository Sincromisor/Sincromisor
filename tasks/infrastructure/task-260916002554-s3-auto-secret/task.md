# S3秘密鍵の自動生成と変更手順を整える

## 背景と目的

管理者トークンとS3キーを後から変更できるかという質問に答え、
S3キーも空欄なら自動生成・保存して利用できるようにする。
`docker compose down` → `up` を前提に、キーと利用サービスの設定、および保存領域を整合させる。

## 完了条件

- [x] 管理者トークンの変更条件、TextProcessorへの反映、空欄へ戻した場合の挙動を説明する。
- [x] S3キーを専用ボリュームへ自動生成し、再起動時に再利用する。
- [x] 明示値を優先し、変更時はS3側と音声認識・音声合成に同じキーを使う。
- [x] キー変更後に旧キーを拒否し、保存済みオブジェクトは読み出せる。
- [x] S3のMaster・Filerも名前付きボリュームへ保存し、再作成後に同じ保存先を使う。
- [x] 認証設定のJSONをログへ出さず、初期化失敗や無認証状態を正常終了にしない。

## 実装と設計判断

`initialize.sh` の乱数生成を共有し、`s3-credential-initializer` が `s3-auth` の `/auth/secret` を準備する。
AgentServer用の `service-auth` は音声認識・音声合成へ渡さない。
`with-s3-secret.sh` が既存の環境変数へ認証情報を注入する。

S3の起動設定を正とし、従来の秘密キー不一致を拒否する処理を、同じアクセスキーの更新へ変更する。
`weed shell` の設定出力を抑制し、署名付きS3要求の成功と不正キー403を正常終了の条件にする。
手動値に空白・改行などコマンドの解釈を変える文字を許可しない。

採用イメージのSeaweedFS 4.46、コミット `d997fba15` の
[s3.configure実装](https://github.com/seaweedfs/seaweedfs/blob/d997fba15/weed/shell/command_s3_configure.go)
で、同じアクセスキーの更新が該当利用者の認証設定だけを変更することを確認した。
実行イメージの `/data` は匿名ボリュームとなるため、Master・Filerにも名前付きボリュームを設定した。

## 確認結果

- `node --test scripts/tests/s3-bootstrap.test.mjs`: 成功。検証専用の実SeaweedFSで、
  自動キー再利用、明示値への変更、旧キー403、空欄への復帰、再作成後の既存オブジェクト保持、
  不正な設定値の拒否を確認した。
- `node --test scripts/tests/{service-initializer,llama-compose,nemo-compose,consul-compose}.test.mjs`: 7件成功。
  秘密値の共有範囲、起動コマンド、保存領域、依存関係、運用プロファイルの維持を確認した。
- 変更シェルの `sh -n`、変更JavaScriptのBiome、変更MarkdownのPrettier、差分検査: 成功。
- 検証用コンテナ・ネットワーク・名前付きボリュームは終了後に削除した。

## 同期した文書

AgentServer設計にトークン変更、保存領域設計にS3キーの変更・自動生成・分散配置・旧保存領域の引継ぎを記載し、
Compose設計と `examples/compose.env` を同期する。
HTTP・WebSocket・DataChannelの通信形式は変更しない。

## 未実行の確認と移行事項

既存環境の `.env`、保存データ、匿名ボリュームは変更していない。
実音声の処理と全サービスの一括起動は今回の確認対象外とし、S3境界を実サービスで確認した。
旧構成で保存したS3データを引き継ぐ場合は、元のMaster・Filerボリュームの特定と引継ぎが必要である。
調査時点で元のコンテナは存在せず、匿名ボリュームとの対応を特定していないため、移行は未実施である。
`down -v` による保存領域削除はキー変更手順に含めない。
