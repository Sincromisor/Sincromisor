# 収集停止時のログ回収と欠落検知・復旧を整える

## 背景と目的

旧案は収集停止・短時間コンテナ・ローテーション・バッファ満杯・中央故障の欠落を限界として記録するだけだった。
[収集タスク](../task-260921212104-vector-host-collection/task.md)のVector → VictoriaLogsを維持し、原本が残っている範囲の回収と、回収不能な区間の検知・保存データの復旧を実装する。

## 変更範囲と方針

- Dockerログの原本、Vectorに取り込んだイベント、永続バッファ、中央が受理したイベントの境界を分け、どこまで保持・再送されるかを明記する。
- 通常の`docker compose up`で短時間コンテナが収集開始前に終了しても、残存ログを自動回収する。手動の起動順を前提にしない。
- Vector停止中に発生しDocker側に保持されたログ、ローテーション後も原本が残るログを再開時に回収する。再開位置を永続化し、コンテナ再作成によるID変更を扱う。
- Docker API入力がこの再開要件を満たせなければ、Vectorの既存の位置保存可能な入力と対応するDockerログドライバー等へ切り替える。採用方式、必要な権限、保持場所を収集・ホスト診断タスクと同期する。単なるbest effortの説明を完了条件の代わりにしない。
- 再送による重複を許容する範囲と識別方法を決める。永続化前の強制終了、原本削除、保持容量超過などの限界を区別し、厳密に一度だけの保存は約束しない。
- 送信失敗・破棄数・バッファ使用量・最終成功時刻・収集不在を既存のVector指標とConsul監視で観測する。中央停止中の診断はローカルに残し、中央復旧後に調査できるようにする。実測できない欠落件数を0とせず、不明な区間を示す。
- 中央の永続データを停止または製品の整合した方法でバックアップし、隔離した保存領域へ復元する最小手順を用意する。保存ボリュームの外にバックアップを置き、ホスト故障に備える場合は別ホスト保存を案内する。新たなバックアップ基盤や常時複製クラスタは追加しない。

## 完了条件

- [x] 連番付きの人工ログで、通常起動の短時間コンテナ、収集停止/再開、原本が残るローテーションの欠落がないことを照合する。再送重複も数える。
- [x] 中央停止中にバッファへ保持したログが復旧後に届き、Vectorの正常な再作成で未送信ログを失わない。強制終了ではディスク同期前の境界と原本から再回収できる範囲を区別する。
- [x] 検証用の小さな上限で容量超過と原本削除を再現し、破棄または回収不能区間を検知できる。本体がログ送信待ちで停止しない。
- [x] 中央コンテナ再作成とバックアップ復元後に人工ログを検索でき、消失し得るバックアップ後の区間を説明できる。
- [x] ブラウザー未送信・ホスト物理故障など他経路の限界を棚卸し表と照合し、各経路の回収/検知責任が明記されている。

## 確認方法と同期

隔離したComposeで連番の投入数と抽出数を機械的に突き合わせ、対象条件ごとの欠落・重複・診断を残す。
通常の回収可能条件で不足が残る場合は修正し、環境都合で確認できない条件は未実行として最終結合確認を完了させない。
`compose/`、Vector設定、ホスト側保存の前提、`examples/compose.env`、`documents/design/infrastructure/logging.md`と`storage.md`を同期する。
保持容量外・同時物理故障までの無欠落保証や、稼働データを破壊する障害試験は対象外とする。

## 実装と確認結果

2026-09-22、基点`2cb347d1`から実装。Vector 0.58.0、journalctl 259.5、VictoriaLogs 1.52.0の隔離Composeで人工データだけを使用した。実ホストのjournalは読取専用とし、回転・原本削除は`systemd-journal-remote`で作った専用journalだけに行った。

Docker API入力をnative journald入力へ変更し、Compose全サービスをjournald / non-blocking 4MiBへ揃えた。入力名・確定cursorと中央ACKを維持し、Vector自身も同じ原本から回収する。旧local原本の自動移行はしない保存方式の変更であり、再作成前の退避とホスト永続journalの前提を設計へ記載した。

小容量試験は本番の約256MiBディスク / blockをmemory / drop_newestへ置換して破棄経路を検証したもので、本番容量の性能測定ではない。本番の原本削除による回収不能は別試験で確認した。Dockerの原本前メモリ破棄には公開計測値がないため、件数不明を常時明示し、0件とは報告しない。

網羅性表のL05（短命・停止・世代）、L06（バッファ・ACK・強制停止・容量）、L07（中央復元）、L09（cursor・原本消失）に対応する。L08のブラウザー未送信は端末キューの責任、H02/H03のホスト物理故障は管理者の別ホスト保管の責任として、ログ設計の経路表へ記載した。保持外や物理故障を無欠落とは扱わない。

人工journalの初回fixtureは単調時刻を省略していたため、複数世代のcursor探索が不正になった。実形式と同様に単調時刻を付けた新fixtureで回転・消失を確認した。回収可能な原本の不足を許容して合格にはしていない。

文書と本番コメントは、原本・確定cursor・バッファ・観測状態の責務、秘密を含む原文を診断へ複製しない境界を点検した。バックアップ後の区間、重複、journal容量・レート制限、同一ホスト物理故障の残余リスクはログ設計と保存領域へ同期した。2ホスト間の最終結合確認は後続タスクであり、本タスクの単一ホスト人工試験で代用しない。

対象確認はVector nativeテスト16件、observerの`GO111MODULE=off go test -race .` / `go vet .`、`node --test scripts/tests/log-collector.test.mjs scripts/tests/log-lifecycle.test.mjs`の2件がPASS。通常起動の短時間ログと停止中原本の中央到達を既存回帰テストへ追加した。シェル構文、対象Biome/Prettier、`git diff --check`、`npm run tasks:check`も確認した。

同じnative入力でホストの固定probeを中央から抽出した。Vector自身の分類は対象サービス名ではなく収集元ラベルを使い、observerが記録するVectorのDocker診断を誤変換しないことをテストへ追加した。native Checkpointerと同じ先頭行を使い、短いcursorへの更新で残る旧末尾を消失と誤判定しない。

中央正常時のVector自己ログは12秒間で1117件から増えず、再帰増殖しない。中央停止中にローカルへ残ったcursor消失診断8行・破棄診断9行も中央復旧後に検索した。専用cursorへ旧末尾を付けた検査は成功し、消失markerは再読取後も残った。既存バックアップを指定した再実行は上書きせず失敗した。
