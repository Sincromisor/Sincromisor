# ブラウザーの障害ログを同一オリジン経由で集約する

## 背景と目的

現在の`sincromisor-frontend/src/shared/logging/appLogger.ts`はconsoleへ出すだけで、Caddyのアクセスログには端末・描画の失敗理由が含まれない。
[網羅性の棚卸し](../task-260921221013-logging-coverage-inventory/task.md)に基づき、利用者端末で発生した障害を中央で抽出できるようにする。

## 変更範囲と方針

- `appLogger.ts`と`features/media/`、`features/rtc/`、`character/`の関連する失敗経路を追う。既存のログ入口を利用し、別ロガーを機能ごとに作らない。
- マイク・カメラの取得拒否/取得失敗・トラック終了、RTC接続失敗/切断、モデル読込・描画初期化/WebGLコンテキスト喪失、未処理例外・Promise拒否を記録する。回復する処理では回復イベントも残す。
- 既存Caddy→Consul→RTCの経路を利用し、同一オリジンの診断受付APIをRTCのHTTPサーバーに追加する。ブラウザーからVectorやVictoriaLogsへ直接接続しない。
- 受信APIは検証したイベントを構造付き運用ログへ出し、Vectorで集約する。専用DBや別のログ受信サービスを増やさない。パス・JSON・応答・上限をフロント/RTC双方の契約へ記載する。
- 端末側の識別子と発生時刻、受信サーバーのhost/受信時刻、取得できる会話IDを区別する。サーバーは信頼した収集項目をブラウザーの申告で上書きさせず、受信ログは`source=browser`等で区別する。
- RTCセッション作成前の端末障害も受け付ける。既存構成の同一オリジン用途に限定し、入力の型・件数・サイズ・頻度を制限する。管理者トークンをブラウザーへ配布しない。
- 本文や資格情報を任意のcontextから無制限に転送せず、診断に必要な項目を選ぶ。サーバー側の内容ログ無効化を任意のクライアント値で迂回できないようにする。
- 転送は本体操作を待たせず、有限の待ち行列・再試行を使う。転送失敗を同じ転送処理へ再帰投入しない。オフライン・タブ終了で未送信になる条件を示し、可能な送信失敗/破棄数を観測する。

## 棚卸しで具体化したWorker診断

[網羅性表B04](../task-260921221013-logging-coverage-inventory/coverage.md)の`learnedVadWorkerClient.ts`と`sincroTrackerWorkerClient.ts`も対象にする。
Workerの起動・モデル取得・推論失敗は状態通知や代替処理へ流れ、windowの未処理例外だけでは拾えない。
既存の通知境界から失敗・代替処理・復旧を有限に記録し、人工的なWorker失敗で中央到達を確認する。音声・映像や毎フレームの推論結果を追加収集しない。

## 完了条件

- [x] マイク/カメラ、RTC、描画、未処理例外の人工的な障害を代表例で中央から抽出でき、発生端末と受信ホストを区別できる。
- [x] 会話IDのない起動前エラーと、会話開始後のエラーを受け付けて区別できる。
- [x] 不正・過大入力を拒否し、中央ログのホスト/サービスを偽装できない。ログ転送停止でも本体の操作が止まらず、再帰出力しない。
- [x] 既定の`docker compose up`で受付経路が起動し、追加の手動起動や公開ポートを必要としない。

## 確認方法と同期

受付APIの小さな境界テストと送信の停止・再開テストを行う。
画面確認は`playwright-cli`スキルを使い、実機を壊さず権限拒否・通信失敗・描画初期化失敗を再現する。ブラウザー組合せ試験は追加しない。
`configs/Caddyfile`、RTCの`internal/signaling/`、必要なフロント初期化を変更し、`documents/design/contracts/frontend-rtc.md`に追加APIを同期する。
`documents/design/frontend/app-shell.md`とログ設計にも利用範囲・保存しない情報・未送信の限界を記載する。
既存RTC APIの形式変更や画面の新設は対象外とする。

## 実装と確認結果

- 共通ロガーに本文・URL・stack・任意contextを含まない固定語彙の診断を追加した。メディア取得/終了、RTC/両DataChannel/受信トラック、描画/モデル/WebGL、未処理例外、VAD/追跡Workerの失敗・代替・回復を既存の通知境界から送る。
- 既存のCaddy→Consul→RTC経路にPOST診断APIを追加した。同一オリジン、16 KiB、8件、プロセス全体60要求/分、厳密なJSONと固定語彙を検証する。端末UUID・端末時刻・申告会話ULIDと、受信時刻・収集元host/service/containerを区別する。既存APIの形式変更はない。
- 端末は最大64件、1秒間隔、3秒タイムアウト、初回を含め3回で打切る。失敗/破棄数は次の成功バッチへ載せる。タブ終了や全要求失敗では未送信分とカウンターが中央へ残らない限界を設計へ明記した。
- Goの診断境界テストを含むsignalingのraceテストとvetが成功した。既存の実ICEテストが一度候補収集タイムアウトしたが再実行では成功した。フロント全体642件成功・2件skipの後、DataChannel等の追加変更に対するRTC/診断対象60件が成功し、型確認・ビルドも成功した。
- 専用Composeで実RTC、既存Caddy設定、Consul、Vector、VictoriaLogsを起動し、PlaywrightからViteを経由して実受付経路を確認した。実getUserMediaの機器不在、人工的NotAllowedError、人工的Worker通知/起動例外、描画初期化失敗、モデル失敗、WebGL喪失/復旧、実RTCセッション作成と人工的切断/復旧・DataChannel開閉・受信トラック終了を確認した。音声は人工的な無音、映像は空のcanvasだけを使用した。
- 中央から100件を抽出し、41件に実RTCの会話ULIDが付くこと、会話前の診断もあること、端末UUIDと受信host/service/containerが別項目であること、人工的な秘密文字列が一切含まれないことを確認した。Workerのfallback/ready/unavailable、WebGLのlost/restoredも到達した。
- Playwrightで診断POSTだけを遮断し、未送信1・失敗1のまま設定の「デバイス」タブを操作できた。遮断解除で未送信0・失敗1になり、中央にもclient_failures=1が届いた。有限再試行・満杯時の破棄・反復状態の抑止は単体テストでも確認した。
- 既定Composeの解決結果に既存RTC/Caddyとログ収集経路が含まれ、診断専用サービス・手動登録・公開ポートを本番構成へ追加していないことを確認した。全業務サービスを含む既定起動の実動作は分散ログ結合確認タスクで実施する。今回の実動作確認は上記の専用構成であり、全構成起動の証拠とは扱わない。
- 変更ファイルのBiome・Prettier・構造検査・diff検査は成功した。全体ゲートはlint段階で停止したため、別途checkを実行し、変更対象の整形を修正した。対象外のMarkdown整形不一致15件（documents/research/character_animation/answers/の2件、既存character-sincro-motionタスク12件、既存sincro-rtcタスク1件）は変更していない。
- 変更したシンボル・処理群と直接の理解範囲のコメント、およびRTC契約・共通枠組み・ログ設計を点検・同期した。コメント点検: PASS。
