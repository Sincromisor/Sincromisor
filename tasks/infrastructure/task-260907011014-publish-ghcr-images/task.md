# GHCRの月次公開と旧構成イメージの整理を定型化する

## 背景 / 目的

ユーザー要求に基づき、月1回程度の手動更新をスクリプト化し、旧構成を整理して現行イメージを実際に公開する。

## 完了条件

- [x] 現行Composeの自作9イメージをコミット済みソースからビルドできる。
- [x] 履歴タグと `latest` をGHCRへ送信し、ダイジェスト一致を確認する。
- [x] 現行対象を保護した上で旧 `minio` と `sincro-client` を削除し、現行名の更新前バージョンも新規公開成功後に整理して一覧で確認する。
- [x] 月次更新、認証、失敗時の再開手順を設計文書へ記録する。

## 設計判断と範囲

公開先は `ghcr.io/sincromisor`、構成はコミット済み `compose.yml` と `examples/compose.env` に固定する。
Gitのアーカイブを一時展開し、端末の `.env`、未追跡辞書、モデルキャッシュをビルドへ入れない。
対象環境は既存構成に合わせて `linux/amd64` とする。依存の更新自体はロックファイルの変更で別途行い、ビルドは `--pull` で基底イメージを確認する。
全ビルド後に履歴タグを全件送信し、その後 `latest` を順次更新する。複数パッケージの一括切替はできないため、途中失敗は同じタグで再送する。
削除は明示名、現行対象外、当リポジトリへの所属の3条件を必須とする。稼働中サービス、Dockerの既存データ、他リポジトリのパッケージは変更しない。
外部の公開・削除を伴うため、削除保護と公開順序を独立確認する。実行ソースはGitアーカイブで分離し、実装は現在の作業ツリーで行う。

## 確認

- CLIの模擬コマンドで現行対象削除の拒否、所属確認、全対象検証後の削除、送信前のビルド失敗停止を確認する。
- 実際の9イメージのビルド、送信、GHCRのダイジェスト・公開可視性、旧パッケージ削除を確認する。
- 文書整形とタスク整合性を確認する。アプリ実装を変更しないため、アプリ全体の検査は追加しない。
