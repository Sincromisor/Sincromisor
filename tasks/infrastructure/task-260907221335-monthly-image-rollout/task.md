# 月次イメージ更新に各ホストへの反映と起動確認を含める

## 背景 / 目的

ユーザーは手動のバージョン更新の煩雑さを避けるためlatestを使用している。
月次公開手順は既にあるが、各ホストへの取得・再作成は別作業である。
2026-09-07の実機調査ではPython4サービスの起動コマンドが `uv run` のみで、
現行Dockerfileの `--no-sync` が未反映だった。初回の保守作業でこの差を解消する。

## 完了条件

- [ ] 既存の月次公開手順に、各ホストのプロファイル確認・取得・再作成・確認・復旧の手順をつなぐ。
- [ ] 月1回および起動障害修正の公開時を実施契機として明記し、実施日・対象コミット・配布ダイジェスト・反映済みホストを記録する方法を定める。
- [ ] 初回の反映でPython4サービスの実コンテナの `Config.Cmd` に `--no-sync` が含まれ、各サービスが起動することを確認する。
- [ ] ホスト間で反映が途中の場合を記録し、全ホスト更新済みと誤報しない。

## 設計判断 / 変更範囲

latestを維持する。バージョン固定、定期自動配備、新たな更新基盤は導入しない。
既存 `scripts/publish-images.mjs` と `documents/design/infrastructure/image-publishing.md` を再利用する。
ロック更新・ビルド・公開・稼働反映を区別し、更新前のイメージIDまたは既存履歴タグを復旧用に記録する。
稼働ホストの接続情報は公開成果物へ保存せず、ホストの役割と成功・未実施の記録だけを残す。
未公開修正を含める必要がある場合は先にコミットし、既存公開手順を使う。
本タスクは初回の保守実施と手順の整備で完了し、以後の月次作業はその都度実施記録を残す。

## 確認方法 / 作業経路

手順整備は通常変更。実ホストへの配備は対象ホストと利用状況を確認し、停止影響に応じた経路で実行する。
公開処理を変更した場合は `node --test scripts/tests/publish-images.test.mjs` を実行する。
実コンテナの起動コマンド・イメージID・死活確認と、会話の主要経路を確認する。
VPSなど接続不能な対象は未実施として記録し、公開成功だけでタスク完了としない。
