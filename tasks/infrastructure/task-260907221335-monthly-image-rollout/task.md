# 月次イメージ更新に各ホストへの反映と起動確認を含める

## 背景 / 目的

ユーザーは手動のバージョン更新の煩雑さを避けるためlatestを使用している。
月次公開手順は既にあるが、各ホストへの取得・再作成は別作業である。
2026-09-07の実機調査ではPython4サービスの起動コマンドが `uv run` のみで、
現行Dockerfileの `--no-sync` が未反映だった。初回の保守作業でこの差を解消する。

## 完了条件

- [x] 既存の月次公開手順に、各ホストのプロファイル確認・取得・再作成・確認・復旧の手順をつなぐ。
- [x] 月1回および起動障害修正の公開時を実施契機として明記し、実施日・対象コミット・配布ダイジェスト・反映済みホストを記録する方法を定める。
- [x] 初回の反映でPython4サービスの実コンテナの `Config.Cmd` に `--no-sync` が含まれ、各サービスが起動することを確認する。
- [x] ホスト間で反映が途中の場合を記録し、全ホスト更新済みと誤報しない。

## 設計判断 / 変更範囲

latestを維持する。バージョン固定、定期自動配備、新たな更新基盤は導入しない。
既存 `scripts/publish-images.mjs` と `documents/design/infrastructure/image-publishing.md` を再利用する。
ロック更新・ビルド・公開・稼働反映を区別し、更新前のイメージIDまたは既存履歴タグを復旧用に記録する。
稼働ホストの接続情報は公開成果物へ保存せず、ホストの役割と成功・未実施の記録だけを残す。
未公開修正を含める必要がある場合は先にコミットし、既存公開手順を使う。
本タスクは初回の保守実施と手順の整備で完了し、以後の月次作業はその都度実施記録を残す。

## 確認方法 / 作業経路

手順整備は通常変更。実ホストへの配備は対象ホストと利用状況を確認し、停止影響に応じた経路で実行する。
公開処理を変更した場合は `node --test scripts/tests/publish-images.test.mjs` を実行する。
実コンテナの起動コマンド・イメージID・死活確認と、会話の主要経路を確認する。
VPSなど接続不能な対象は未実施として記録し、公開成功だけでタスク完了としない。

## 公開・反映結果（2026-09-10、承認受領後）

ユーザーの明示承認後、履歴タグ `20260910t131702-1f099415eef5` を既存 `push` 手順で公開した。
自作8イメージ全件で履歴タグと `latest` の配布ダイジェスト一致、匿名取得を確認した。
[配布ダイジェストと更新前後のイメージID](artifacts/release-candidate.md) を記録した。

ローカル8件とVPSのRTC1件について、取得したダイジェストを照合し、
セッション0で再作成した。全9コンテナの公開元ラベルとダイジェストが一致し、
全件healthy、Python4件の実 `Config.Cmd` に `--no-sync` がある。
S3の一回限りの準備処理は終了コード0。旧イメージと設定は復旧用に保持した。

会話確認の依存先である管理下DifyとOllamaが未起動だったため、
既存構成・既存イメージ・保存済みモデルで起動した。これらのイメージやモデルは更新していない。
Difyの起動時には親プロセスの `DEBUG` が既存設定を上書きしたため、
`env -u DEBUG docker compose up -d --no-build --pull never` で起動し直した。
API再作成後のプロキシの古い名前解決も設定再読み込みで解消した。
Difyは既存の認証設定でHTTP 200を返し、接続先LLMの初回読み込み後に実応答を完了した。

Chromiumの自動確認環境では更新前後とも `AudioWorklet.addModule` が完了しなかった。

RTC・Consul・音声区間抽出・NeMo認識・Dify・LLM・音声合成は実サービスを使用した。
接続先、認証値、発話内容、画面原本は公開成果物へ保存していない。

VPSのFirefox実画面では録音サンプルの自動入力から認識結果を得られなかった。

配備確認は実画面の接続とRTC契約入力の音声経路を組み合わせた。
これは実画面全体の自動会話試験が成功したという意味ではない。
UIの自動入力の制約を残し、VPSの媒体・認識・応答・合成の実サービス確認と区別する。
VPSの生ログ保存は自動承認レビューに拒否されたため、保存せず固定イベント名・理由コードの集計と
公開契約の固定ラベルのメトリクスだけを使って切り分けた。

両ホストの対象イメージ反映、起動、実コマンド、配布ダイジェスト、主要音声経路の確認を完了した。
Dify・LLMの起動前提を月次手順へ補足した。文書点検はPASS。本実施では本番コードを変更していない。
