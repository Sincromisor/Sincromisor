# フロントエンドとRTCの共通ビルドでキャッシュを再利用する

## 背景 / 目的

2026-10-18、HEAD `d9e4916b` を調査した。[frontend](../../../Docker/sincro-frontend/Dockerfile) と [RTC](../../../Docker/sincro-rtc/Dockerfile) は同じフロントをビルドするが、frontendの `npm ci` にだけ `chown -R` があり、その地点から命令が一致しない。
共通の依存導入と生成処理で、同じビルダーのキャッシュを再利用できるようにする。

## 完了条件

- [x] 同一入力・引数で両Dockerfileのフロントビルド部分が同じ処理となり、依存導入とフロントビルドのキャッシュを再利用できる。
- [x] 既存のUID、npmキャッシュの所有者、Node.jsとnpmの版、ビルド引数を維持する。
- [x] Caddy用とRTC同梱用に、従来と同じ公開ページ・素材を含む成果物を配置できる。

## 変更範囲・実装方針

上記2つのDockerfileの共通ビルド部分を揃える。`COPY --chown` とディレクトリ生成時の所有権で足りることを確認して重複処理を除く。
必要ならDockerfile構文指定も揃える。新しい共通配布イメージ、Bake設定、Composeのサービス間ビルド依存は導入しない。
Goビルド、Caddy・RTCの起動方式、配信先、依存版は変更しない。

## 確認方法

同一の入力・引数・ビルダーで一方のフロントビルド段階をビルドし、続いてもう一方の該当段階をビルドする。
後者で `npm ci` と `npm run build` がキャッシュを再利用し、生成物が一致することを確認する。比較のために `--no-cache` や全サービス再ビルドは使わない。
両最終段階のコピー元・配置先を確認し、今回の差分で必要になった場合だけ最終イメージまで検証する。

## 文書同期・実行上の制約

公開契約は変わらず、設計文書の変更は原則不要。確認結果を本タスクに記録する。
容量確認と作成物の扱いは [Docker Compose管理ルール](../../../documents/rules/docker-compose.md) に従う。起票時点で短縮時間は未測定。

## 実装・確認結果

フロントの不要な再帰chownを除き、構文指定と共通ビルド段階をRTCへ揃えた。COPY --chownとディレクトリ作成時の所有権、UID 1001、npmキャッシュのuid/gid、Node.js 26.11.1・npm 11.20.0、引数は維持した。

同じ入力・引数・defaultビルダーでフロント、RTCの順にビルドし、後者のnpm ciとnpm run buildがCACHEDになることを確認した。両成果物のファイル名と内容から計算したSHA-256は8278173c97b7f052b64b633f10d97482eb1536f2647a3fe4bf29646eee238115で一致した。共通段階の文字列一致とCaddyの/srv/sincromisor-frontend、RTCの/opt/sincromisor/frontendへのコピーを確認した。最終段階の動作変更がないため、最終イメージの再ビルドは行っていない。コメント点検: PASS。

接続先unix:///var/run/docker.sock、linux/amd64、--output type=cacheonlyで検証し、新規イメージタグ・ID・永続コンテナは作成していない。開始時のキャッシュ114.5GB、空き142GB。共有キャッシュは既存GCの下で通常ビルドに再利用する。

終了時のキャッシュは114.6GB（約0.1GB増加）、空き142GBである。
