# ログ発生箇所と診断の網羅性

## 目的と判定方法

2026-09-21のコード・Composeを静的に調べた、実装担当と最終結合確認のための台帳である。
現在、標準Composeに中央保存・収集・ブラウザー診断受付はない。以下は出力箇所の確認結果であり、中央到達の実機確認結果ではない。
全行の中央到達は**未確認**。担当は実装後、行IDごとに確認日、対象コミット、構成・ホスト、人工入力、検索条件、結果へのリンクを追記する。
表に並ぶサービスをまとめて確認した場合も、サービス・インスタンスごとの抽出結果を残す。

| 判定           | 意味                                                                               |
| -------------- | ---------------------------------------------------------------------------------- |
| 未出力         | 必要なイベントを出す処理がない                                                     |
| 出力済み未収集 | コードに出力経路があるが中央収集がない。実際の出力量・製品の既定出力は別途確認する |
| 診断不足       | 出力はあるが原因・段階・識別・完了区分が足りない                                   |
| 取得不能       | 原本消失・未送信・権限など具体的条件で取得できない。理由と影響区間を残す           |
| 未確認         | 実機・製品出力・配置条件の証拠がない                                               |
| 確認済み       | 必要なイベントを実際に中央から抽出した証拠がある場合だけ使用する                   |
| 要件上の非収集 | 下記の明示した情報だけを収集しない。障害経路全体を除外しない                       |

## Compose全サービスとの照合

[compose.yml](../../../compose.yml)の有効なincludeは12ファイル・30サービス。
[compose/](../../../compose/)の全16ファイルは重複を除き33サービスを定義する。
`distributed.yml`と`management.yml`は既存サービスの公開先を重ね、発生元を追加しない。
配布設定の`COMPOSE_PROFILES=full,chat`を標準とし、分散時はホストごとの選択プロファイルで照合する。
MediaMTXはコメントアウトされたinclude、MinIOはincludeされていない旧構成である。未選択と未収集は区別し、選択・配置される場合は確認必須とする。

経路Dはコンテナstdout/stderr → Docker原本 → 各ホストVector → 同居log-router → Consul DNSで発見したVictoriaLogsを表す。
現在あるのはDocker原本までの出力経路で、Vector以降は担当タスクの実装予定である。
外部製品はComposeのcommand・起動スクリプトから標準出力の収集対象を特定した。製品の具体的なログ内容は未確認であり、起動・正常要求・異常要求の実出力を確認する。

## プロセス内・ブラウザー・ホストの境界

ソースへの入口は[Pythonログ設定](../../../sincromisor-server/sincro-config/src/sincro_config/SincromisorLoggerConfig.py)、[RTC](../../../sincromisor-server/sincro-rtc/)、[AgentServer](../../../sincromisor-server/agent-server/src/mastra/)、[フロント](../../../sincromisor-frontend/src/)である。
Pythonの各`*Process.py`は共通設定を適用してUvicornとワーカーを起動する。モデル初期化、引数検証、uv起動など通常ロガーより前のstderrもDの対象にする。
