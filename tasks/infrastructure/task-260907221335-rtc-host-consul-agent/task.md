# VPS上のRTCを同一ホストのConsulエージェントへ接続する

## 背景 / 目的

ユーザーの実運用は複数ホストに跨り、RTCはグローバルIPv4を持つVPSにある。
サーバーへの直接登録はPion移行時の考慮漏れであり、ホスト側のConsulエージェントを経由する意図だった。
確認したHEADは `163b46f2927788de98da8d68af0853a561f091f1`。
起票時の `compose/sincro-rtc.yml` はConsulサーバーの正常性に依存し、`rtc` はサーバーとRTCの2サービスを選択する。

## 完了条件

- [x] RTCと同じホストのConsulエージェントをComposeで配置し、RTCの登録・探索・解除のHTTP接続先にする。
- [x] `rtc` 単独構成は新しいConsulサーバーを起動せず、既存の別ホストのサーバーへ参加する。full構成は既存のローカルサーバーを維持し、新エージェント経由で利用する。
- [x] エージェントの参加先・広告先・必要ポート、RTCの登録先・ブラウザ向けIPv4の違いを設定サンプルと設計文書に明記する。
- [x] 別ホストからのサービス探索とRTCへの到達、同一ホストのエージェントによる死活確認、終了時の登録解除を確認する。

## 設計判断 / 外部境界

既存のホストごとのConsul構成を維持し、中央への集約はしない。Go側のHTTP登録APIは再利用する。
RTCのHTTP接続先は `consul-agent-rtc:8500` に固定し、旧 `SINCRO_PION_CONSUL_HTTP_HOST/PORT` は廃止する。
参加先は既存 `SINCRO_CONSUL_SERVER_HOST` を起点とし、ホストを跨ぐゴシップの広告先は導入先の管理ネットワークで到達できる値を使う。
別ホストの利用者から到達不能なDocker内部IPをRTCのサービスアドレスとして広告しない。
ブラウザ向け `SINCRO_PION_PUBLIC_IPV4` は別の責務として維持する。
実VPSの管理アドレス・ネットワーク・配備方法は着手時に確認し、未確認値で稼働先を切り替えない。
公開ネットワークへのConsul管理API公開を解決手段にしない。

## 変更範囲

`compose/sincro-rtc.yml`、`compose/consul-server.yml`、必要なエージェント設定、`examples/compose.env`。
Goの設定・登録処理は `sincromisor-server/sincro-rtc/internal/config/` と実際のConsul利用箇所を確認する。
`documents/design/infrastructure/compose.md`、`consul.md`、`documents/migration/pion/rollout-and-operations.md`、READMEを同期する。
WebRTCの通信形式、他サービスのエージェント削除は対象外。

## 確認方法 / 作業経路

実ホスト間の通信と配備を伴う高リスク変更。起票時に独立レビューし、実装時も対応する経路を使う。
full/rtcのCompose構成検査、Goの変更範囲の確認に加え、別ホスト相当の分離ネットワークで登録・探索・死活確認を検証する。
実VPSへの反映は接続条件確認後に行い、実施できない検証は理由と残作業を記録する。

## 着手前に確定する事項

独立レビューではネットワーク設定が不足しているため `NEEDS_REVISION` となった。
VPSと既存Consul側で使う管理ネットワーク、エージェントの `-bind` と `-advertise`、
ホスト間のTCP/UDP 8301の到達経路・公開先・ファイアウォールを確認して仕様を確定する。
RTC向けHTTP 8500はホストの公開ネットワークへ公開しない。
ホストの実アドレスは公開タスクへ記録せず、設定キーと役割、確認結果を記録する。

完了時は別ホストからRTCを発見でき、エージェントの `/health/ready` 確認がpassingとなること、
SIGTERM後の登録解除、RTCから下流探索が成功することを観測する。
実VPSまたは必要な二ホスト検証が実施できなければ、記録だけで完了扱いにしない。

## 実装仕様の確定（2026-09-10）

非公開情報はタスク成果物へ転記せず、運用設定へだけ供給する。実機の接続確認は成功した。
以下は導入先の具体値によらない共通仕様である。

- Consulの全メンバーが相互通信できるよう、サーバーと既存エージェントに任意の `SINCRO_CONSUL_ADVERTISE_ADDR` を渡す。空の場合は従来の自動選択を使う。Dockerネットワークのホスト間ルーティングを必須にしない。
- 公開先は `SINCRO_CONSUL_PUBLISH_HOST` で管理する。サンプルはループバック、分散配置では導入先の管理アドレスを指定する。エージェントのHTTP 8500は公開しない。サーバーの既存公開ポートも同じ管理先へ限定する。
- サーバーのLANゴシップは8301を維持する。エージェントはRTC8311、フロント8312、音声区間抽出8313、音声認識8314、テキスト処理8315、音声合成8316、Redis8317、S3 8318を使い、TCP/UDPともコンテナとホストで同値にする。サーバーRPCのTCP 8300も管理経路で到達可能にする。
- 参加先には既存 `SINCRO_CONSUL_SERVER_HOST` の8301を再利用する。単一ホストではサーバーのDocker名、分散配置では到達可能な管理ホストを指定する。DNS用途の8600と参加先8301は同じサーバーを使う。
- RTCは同一Composeの `consul-agent-rtc` のHTTP 8500を登録・探索・解除に使用し、その正常性へ依存する。`rtc` プロファイルからサーバーを外し、`full` には維持する。
- 既存エージェントの削除・集約は行わない。広告先と待受ポートの追加は全メンバー間の到達性を成立させるために必要な範囲であり、通信契約やGoのAPIは変更しない。

高リスク経路で専用ワークツリーと独立レビュー・評価を使う。公開記録には設定キー、役割と結果だけを残す。

## 実施結果（2026-09-10）

実装コミット `0dad179e`、文書同期 `690e36fd` を `1f099415` へ統合した。
独立レビューはAPPROVED、独立実装評価は [PASS](eval.md) となった。
Compose回帰試験、全体ゲート、文書点検、構成コメント点検はPASS。

ローカルの全サービス構成とVPSのRTC構成に既存イメージで設定を反映した。
両ホストの設定とイメージ、Consulの保存状態を退避し、セッション0で再作成した。
全10メンバーが正常に参加し、各RTCは同居エージェントを利用する。
エージェントのHTTP 8500はホストへ公開されていない。
両RTCから下流4サービスのpassing登録を取得し、各接続先へのHTTP到達を確認した。
各RTCを順番にSIGTERM停止し、当該登録がエージェントとカタログから消え、
他方のRTC登録だけが残ることを確認した。再起動後は両RTCがreadyへ復帰した。

RedisとVOICEVOXには稼働先と異なる旧登録のcriticalが各1件残るが、
稼働先の登録は各1件passing、実コンテナもhealthyである。
イメージの月次公開・反映と会話確認は別の月次更新タスクで扱う。
公開成果物にはホストの役割と集計結果だけを記録した。
