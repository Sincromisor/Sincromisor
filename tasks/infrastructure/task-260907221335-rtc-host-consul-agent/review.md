# レビュー: task-260907221335-rtc-host-consul-agent

## 判定

APPROVED

## 理由・申し送り

- RTCをConsulサーバーへ直接登録している現行構成を、同一ホストのエージェント経由へ移す根拠がある。既存のGo登録・探索・解除APIを再利用し、Compose、設定例、運用文書を同期する範囲で実装できる。WebRTC通信契約とGo APIは変更しない。
- 同一データセンターのLANゴシップはサーバーとクライアントを含む全メンバー間のTCP/UDP到達を必要とする。全メンバーの広告先を管理経路へ揃え、サーバーは8301、各エージェントは固有のLANゴシップポートを使う仕様は、重複するDocker橋渡しネットワークをホスト間で経路化せずに要件を満たす最小単位である。HTTP 8500をホストへ公開しない境界と、サーバーRPC 8300を管理経路で到達可能にする条件も明確である。
- `SINCRO_CONSUL_SERVER_HOST`の再利用は妥当である。現行の参照先はエージェントの`-retry-join`と、full構成でサーバーへ問い合わせるDNS確認だけであり、どちらも同じConsulサーバーを指す。サーバーのLANゴシップポートを8301に固定するため、専用の参加先キーは必要ない。単一ホストではDocker名、分散配置では管理経路のホストを同じキーに設定し、両方を同時に必要とする構成を作らない。
- `rtc`ではサーバーを選択・依存対象から外し、RTCと新規エージェントだけを起動する。fullでは既存サーバーと全エージェントを維持する。RTCは同一ComposeネットワークのエージェントをHTTP接続先とし、`SINCRO_PION_SERVICE_BIND_HOST`とブラウザ向け`SINCRO_PION_PUBLIC_IPV4`の責務は分離されたままである。
- 完了には、二ホストで全メンバーの到達性、外部からのRTC登録・探索、同一ホストのエージェントによる`/health/ready`確認、SIGTERM後の登録解除、RTCから下流サービスの探索を観測する必要がある。実環境確認の失敗は記録だけで完了にしない。
