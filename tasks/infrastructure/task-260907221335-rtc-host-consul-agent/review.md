# レビュー: task-260907221335-rtc-host-consul-agent

## 判定

NEEDS_REVISION

## 理由・申し送り

- 背景と目的には、複数ホスト構成でRTCを同一ホストのConsulエージェントへ登録するというユーザー要求と、現在の`compose/sincro-rtc.yml`がサーバーへ直接接続する実装との差分という根拠がある。Goの登録・解除処理も既存のエージェントHTTP APIを使うため、RTCの通信契約を変更せずに進められる。
- 実装方針を一意に決めるネットワーク境界が不足している。Docker bridgeでエージェントを動かすなら、ホスト間のLAN gossip用にどのホスト側管理IPv4を`-advertise`するか、TCP/UDP 8301をどの方向に公開するか、`-bind`・ポート公開・ホストのファイアウォールをどう組み合わせるかを完了条件へ明記する必要がある。エージェントHTTP APIの8500はRTCコンテナだけに公開し、公開ネットワークへ出さないことも確認対象にする。現在の`-retry-join`と`-client=0.0.0.0`だけでは、別ホストのConsulメンバーがDocker内部IPv4へgossipするおそれがある。
- `full`はローカルの`sincro-consul-server`を起動する既存用途を維持し、`rtc`だけが外部サーバーへ参加することを明示する必要がある。現在は`rtc`プロファイルにもサーバーが含まれ、RTCもその正常性へ依存しているため、どのprofileからサーバー依存を外すかが変更前後で検証可能になっていない。
- 高リスク変更の完了には、選定済みの管理ネットワークアドレスを使った二ホスト検証を必須とする必要がある。実VPSへ反映できない場合に理由と残作業だけを記録して完了扱いにはできない。少なくとも、外部サーバー側から`RTCSignalingServer`を発見してagentが実行する`/health/ready`確認がpassingになること、SIGTERM後に外部サーバーから登録が消えること、RTCコンテナから下流サービスを解決できることを観測点として固定する。
- 変更範囲にあるGo設定・登録処理は既存の`internal/pipeline/discovery/registration.go`と`cmd/sincro-rtc/server.go`を確認してから、変更不要なら変更しない。変更する場合は登録アドレス、確認URL、解除順序を守る試験を同期する。ソースコードコメント品質は`documents/rules/source-comments.md`の直接適用である。

## 自律補完

- なし。gossipの広告・到達経路と、`full`におけるローカルConsulサーバーの責務は公開構成と実運用の選択を伴うため、自律補完できない。
