# 画面の初期読み込みを計測して遅延対象を確定する

## 背景 / 目的

優先度: 中。[画面と購読フックを軽量なアプリ参照窓口へ移行する](../task-261115055437-ui-controller-imports/task.md) の完了後、静的依存の整理済み状態で初期読み込みを確認する。現在は設定パネルの動的読み込みを待ってReactを配置し、診断表示も静的に参照する。モジュール数だけで速度改善を断定せず、遅延読み込みの採用範囲を決める。

## 調査範囲

- [共通起動](../../../sincromisor-frontend/src/app/shell/bootstrapSincroPageAppShell.tsx)、[共通画面](../../../sincromisor-frontend/src/app/shell/sincroPageAppShell.tsx)、[診断表示](../../../sincromisor-frontend/src/features/debug/react/debugConsole.tsx)、3つのVRMページの設定パネル入口を確認する。
- `/simple-vrm/` の開発時の初回表示、診断の初回表示、設定の初回表示を確認する。初期表示前のモジュール取得と画面表示までの所要時間を、キャッシュ条件を明記して採取する。本番ビルドでも対象コードの分割・先読みを確認する。
- 診断表示と常設設定について、それぞれ初回表示まで不要なコード、開始前から必要なDOM・購読・副作用、共通依存によって分割効果が失われる経路を特定する。診断内の `rtcAudio` と追跡用DOMは初回非表示でも必要である。
- 後続の [診断表示を初回表示時に読み込む](../task-261115055438-lazy-debug-panels/task.md) と [常設設定パネルを起動処理から分離して読み込む](../task-261115055438-lazy-settings-panel/task.md) に、採用・不採用の理由、実際の境界、必要な確認を個別に反映する。短い一時的な試作でしか判断できない場合は調査用に行い、実装差分を残さない。

## 観測結果と採否

対象は `7b40ad06c`。Node.js 24.21.0、Vite 8.3.5、Playwright CLI 0.1.22、Chrome 157.0.8103.78を使用した。配布ソースから `npm run dev -- --host 127.0.0.1 --port 5177 --strictPort` で起動し、専用の空プロファイルで `/simple-vrm/` を一度観測した。CDPの `Network.setCacheDisabled` でブラウザーキャッシュを無効化し、通信・CPUの追加制限は設けない。初回Vite変換を含むため、数値は比較可能な速度保証ではない。

`addInitScript` でResource Timingの容量を3000へ増やし、ヘッダーと開いた起動前ダイアログのDOM出現後、二度の `requestAnimationFrame` が終わる時刻を記録した。これは描画準備の確認時刻であり実際の画素表示時刻ではない。Paint Timingも別に採取した。開始操作・実機器・RTC接続は使わず、API未提供の案内を含む画面を観測した。

| 観測項目                             | 結果                                                                       |
| ------------------------------------ | -------------------------------------------------------------------------- |
| ヘッダー・起動前ダイアログの配置確認 | ナビゲーション開始から1796.1 ms                                            |
| First Contentful Paint               | 1868.0 ms                                                                  |
| 配置確認以前のスクリプト取得         | 441件（script起因または拡張子js/ts/tsx、重複URLの要求を含む）              |
| 診断React領域の取得                  | 33件、転送量353,911 bytes。メニュー・常設DOMも含み、全量が削減対象ではない |
| 常設設定入口の取得開始・終了         | 1558.8 ms / 1566.3 ms                                                      |
| 診断の初回表示                       | 操作前から表示確認まで79.9 ms、追加取得0件                                 |
| 設定の初回表示                       | 操作前から表示確認まで88.2 ms、追加取得0件                                 |

パネル観測は有効アプリの `dialog.close()` で開始前画面を閉じ、右側メニューから診断、設定の順に開いた。操作前の `performance.now()` から可視状態と二度の描画フレーム確認までを計測し、操作待機も含む。いずれも既に読み込まれており、動的importやActivityの記述だけでは初回取得を遅延できていなかった。

`npm run build` は成功した。本番のsimple-vrm入口も共通起動へ設定import関数を渡し、即時呼び出しにより `sincroControlPanel`（13.68 kB、gzip 4.89 kB）と依存を先読みする。診断表示は共通起動側の静的依存へ含まれる。Three、React、MediaPipeなどの共通資源はアプリ初期化からも必要であり、今回の分離による削減量に数えない。

- **診断は採用**。表示専用の詳細パネルとスナップショット購読を初回表示時に読み込む。`DebugConsoleManager`の生成・RTC停止操作、タブ、`rtcAudio`、`GazePreview`とportal先は常設する。`GazeDetails`を同居ファイルから分ければ、詳細側への静的経路を切断できる。機器や診断収集の開始を遅らせる必要はない。
- **常設設定は採用**。ページ別パネルの取得待ちをReact配置の前提から外せる。専用フックは表示用購読と操作の委譲であり、機器一覧の監視・更新は起動前ダイアログも使う `useSincroMediaDeviceState` と共有サービスが維持する。設定復元・VRM復元・初期化はControllerとページ入口が所有し、常設設定の配置には依存しない。共有入力部品・設定既定値は起動前画面にも必要なので初期取得へ残る。

両タスクの既存レビュー済み境界を採用する。後続に具体的な対象と確認を追記して `open` とした。固定時間や削減率を受入条件にはしない。既存タスクで必要な実装を覆えるため追加起票は不要と判断した。
