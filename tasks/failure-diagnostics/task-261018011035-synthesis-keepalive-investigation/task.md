# 音声合成WebSocketの生存確認タイムアウトを調査する

## 背景と目的

検証環境とVPSへの配備確認で発生した音声合成接続のタイムアウトについて、原因と音声欠落の範囲を特定する。
対象実装は `9f351157fa3ddb9c19805b57903b236ea5174068`。保存ログ、稼働コード、隔離した再現で調べ、実装・運用設定は変更しない。

## 完了条件

- [x] 実際の切断コード、発生元と処理順を確認する。
- [x] 同じ依存と実ワーカーで原因を再現し、比較条件で切り分ける。
- [x] 合成失敗と配送失敗・未受信を区別し、対処方針と確認の限界を記録する。

## 結論

Uvicorn 0.54.0の `websockets-sansio` による受信停止と、音声合成ワーカーの逐次処理、生存確認タイマーの組み合わせで発生する。
未処理要求が残る間はソケットの受信が停止し、クライアントが返したPongも読めない。一方、サーバーのPing送信と期限判定は継続するため、通信相手が応答していても `1011 / keepalive ping timeout` で切断する。

### コード上の経路

1. [起動処理](../../../sincromisor-server/voice-synthesizer/VoiceSynthesizerProcess.py)は `uvicorn.run` のWebSocket実装とPing設定を指定しない。稼働依存はUvicorn 0.54.0 / websockets 17.2で、`auto` は `WebSocketsSansIOProtocol`、Ping間隔・待機期限は各20秒だった。
2. [合成ワーカー](../../../sincromisor-server/voice-synthesizer/src/voice_synthesizer/VoiceSynthesizer/VoiceSynthesizerWorker.py)は1件受信し、`asyncio.to_thread(get_voice)` の完了と送信を待ってから次を受信する。イベントループ全体は止めないが、アプリの受信は合成中に進まない。
3. Uvicornの `send_receive_event_to_app` は要求をキューへ入れ、`transport.pause_reading()` を呼ぶ。`receive` がキューを空にしたときだけ受信を再開する。複数要求が溜まると、各処理が短くても受信停止が継続する。
4. `send_keepalive_ping` は受信停止を考慮せずPingを送り、`keepalive_timeout` はPongを処理できないまま接続を閉じる。これは音声合成HTTPの30秒読取り期限とは別である。
5. [Goの再初期化処理](../../../sincromisor-server/sincro-rtc/internal/pipeline/reset.go)はこの切断を受けて4接続を再作成する。未完了の合成要求は引き継がれず、応答音声が欠ける。

[Uvicorn 0.54.0の実装](https://github.com/Kludex/uvicorn/blob/0.54.0/uvicorn/protocols/websockets/websockets_sansio_impl.py)と[公式設定](https://uvicorn.dev/settings/)を2026-10-18に参照し、稼働コンテナ内のコードと照合した。
なお、通信契約文書に残るGoの「10秒ごとの能動Ping」は現在のコードに存在しない。今回の切断はPython側のPingであり、調査ではコードを根拠にした。文書の更新は行っていない。

### 配備時ログとの一致

両環境とも切断元はVoiceSynthesizerで、Goが受信した終了コードは1011、理由分類は `keepalive_ping_timeout` だった。
実ログの合成処理は26件すべて成功し、1件の最大所要時間は約5.513秒。内訳の最大値はクエリ生成約1.115秒、WAV生成等約4.711秒、音声変換約0.098秒だった。
各処理の失敗ではなく、連続要求の待ち行列が原因と整合する。実サービスに再起動・OOMはなかった。

| 確認環境 | RTCから合成へ送信成功 | RTCで合成結果を受理 | 再初期化時の結果未受信 | 合成成功後の送信失敗 |
| -------- | --------------------- | ------------------- | ---------------------- | -------------------- |
| 検証環境 | 20件                  | 17件                | 3件                    | 1件                  |
| VPS経由  | 11件                  | 7件                 | 4件                    | 1件                  |

前の配備報告の「各1件未配送」は、Pythonが合成を終えてから送信に失敗した件数だった。未処理要求を含むRTC側の結果未受信は3件・4件であり、影響を各1件だけに限定できない。
`discarded_text` と `discarded_audio` はともに0件。これらは内部キューの破棄数であり、結果未受信の否定にはならない。結果未受信件数を、そのままブラウザーの再生欠落数として扱わない。

### 再現確認

稼働コンテナ内の別プロセスで実 `VoiceSynthesizerWorker.communicate` を動かした。同期合成だけを待機処理に置き換え、実UvicornとWebSocketクライアントをループバックで接続した。VOICEVOX・Redis・S3は呼ばない。

| 条件                   | 1件の処理時間 | Ping間隔 / 期限 | 8件の結果             |
| ---------------------- | ------------- | --------------- | --------------------- |
| 現行実装・遅い処理     | 0.12秒        | 0.15秒 / 0.15秒 | 2件受信後に1011で切断 |
| 現行実装・速い処理     | 0.005秒       | 0.15秒 / 0.15秒 | 8件受信、切断なし     |
| 旧WebSocket実装で比較  | 0.12秒        | 0.15秒 / 0.15秒 | 8件受信、切断なし     |
| 現行実装・実運用の期限 | 6秒           | 20秒 / 20秒     | 6件受信後に1011で切断 |

実運用の期限での再現では、開始20.014秒でサーバーが受信停止中・キュー4件のままPingを送信し、クライアントも同時刻にPongを送信した。サーバーのPong処理は呼ばれず、40.016秒でキュー1件を残して切断した。合成中のワーカーが切断を検出したのは、結果を送ろうとした42.019秒だった。
遅い条件の切断コード、Pong送信、サーバーの未処理、受信停止とキュー残存、比較条件の全件受信をassertで確認した。
初回は観測用ログ設定がPong送信記録まで抑制してassertが失敗した。観測設定だけを修正して再実行し、全条件が通った。

## 対処方針と限界

恒久対応では、受信を停止している時間と生存確認の判定を整合させるか、要求の流量を制御して長時間の受信停止を避ける必要がある。単純な期限延長や無制限の受信キューは、長い応答や負荷増加に対する解決を保証しない。

比較に使った `ws="websockets"` はこの8件の条件では回避できたが、現行Uvicornで非推奨であり、将来は同じ指定がSansIOを指す旨の警告が出る。恒久対策として採用した結果ではない。`ws_max_queue` は公式設定上この旧実装だけが対象で、現行SansIOへ同じ効果を期待できない。

本調査では実運用中のソケットを直接計測していないため、過去の各接続でPongがOSへ到達した時刻までは確定しない。同じ実ワーカー・依存で観測した再現と、実ログの終了コード・処理時間から上記原因を特定した。ネットワークや合成エンジンを使わない再現でも発生する。
