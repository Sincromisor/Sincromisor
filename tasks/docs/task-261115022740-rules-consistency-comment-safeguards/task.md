# コメント品質規約を判断手順に沿って整理する

## 背景 / 目的

コメント品質の共通規約と言語別規約に、同じ要求の反復と、点検記録を作る条件の食い違いがある。ユーザーによれば、詳しい記述はCodexエージェントによる指示の無視・曲解への対策として増えてきた。同時に、要求を守るための注意書きの追加も文書肥大化の一因となっている。

既存の条項を「対象を決める→必要な説明を判断する→コードへ反映する→確認結果を報告する」の順に組み直し、実装者が取る行動を具体的に示す。

## 変更範囲と進め方

対象は `documents/rules/source-comments.md`、各言語の `coding-*.md` のコメント品質章とコメントの言語指定、`tasks/README.md` のコメント点検の説明とする。前回のタスクから、[確認手順・表記](../task-261115023755-rules-current-workflow/task.md)と[構造検査](../../frontend-tooling/task-261115023755-structure-check-targets/task.md)を分割した。本タスクは文書編集で完結する。

1. 共通文書に目的・適用範囲・判断手順をまとめ、言語別文書には固有の記法・対象・例と共通文書を読む案内を置く。各条項を意味で照合し、同じ判断を繰り返す箇所は統合する。
2. 条項の書き換えは既存の該当箇所を置き換える形で行う。補足が必要な場合は、適用条件と実装者が取る行動をその箇所へ組み込む。独自の判断材料を持つ例や強調は、その判断の近くに残す。
3. コメントの必要性は変更の安全性と処理の理解の両方から判断できる形にする。省略は目的・入出力・状態変化・前後関係・失敗や所有権を局所的に理解できるかで決める。短さや非公開といった属性は、この判断の材料として扱う。
4. 点検範囲は変更したシンボル・処理群・判断と直接の変更理解範囲とする。既存由来の説明不足もコード上で解消し、通常変更では結果を報告する。独立確認に必要な記録を作る条件は、共通規約§6とタスク管理で揃える。
5. Python・Goの公開向け英語コメントの許可を `AGENTS.md` の日本語方針へ揃える。識別子・公式名・正確な引用は原表記で扱う。

## 完了条件と確認

- [x] 共通文書と言語別文書の役割が明確で、点検対象・省略判断・記録条件が一致している。改訂した条項を変更前と照合し、現行の適用範囲と必要な説明事項を確認できる。
- [x] 通常変更の記録省略、既存の説明不足、短い非公開関数、公開APIだけ説明済みの4例で、改訂後の文書から必要な点検・修正を判断できる。実施結果は本タスクに短く記す。
- [x] リポジトリルートで変更MarkdownのPrettier整形・確認、参照先の確認、`npm run tasks:index:check` と `npm run tasks:check` が通る。

アプリの実行試験は対象外とする。共有する言語別文書は他タスクの最新内容を読んでから編集する。エージェント文書の同期が必要なら編集元を直し、既存の生成手順で反映する。

## 実施結果

共通規約を点検対象、必要な説明、省略判断、実コードの修正・点検、報告の順に整理した。変更前の必須対象・説明事項を照合し、言語別の重複する説明事項は共通規約§2.3へ、固有の記法・対象・例は各言語規約へ残した。PythonとGoの文書コメントも日本語方針へ統一した。

4例の判断を確認した。

- 通常変更の記録省略: 台帳は不要だが、§1の全対象を点検・修正し、§6に従って結果を報告する。
- 既存の説明不足: 直接の変更理解範囲にある不足は、既存由来でも§4・§5に従ってコード上で解消する。
- 短い非公開関数: 短さだけでは省略しない。§3の目的・入出力・状態変化・前後関係・失敗・所有権等を局所的に理解できる場合だけ省略する。
- 公開APIだけ説明済み: 内部の処理段階や状態遷移も§2.2・§5で確認し、理解に必要な説明を補う。

変更MarkdownのPrettier整形・確認、相対リンクの存在確認、`npm run tasks:index:check`、`npm run tasks:check`を実施し、すべて通過した。
