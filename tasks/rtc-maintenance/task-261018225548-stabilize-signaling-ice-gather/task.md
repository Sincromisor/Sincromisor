# シグナリング試験のICE収集タイムアウトを調査して安定化する

## 背景・目的

逐次音声対応の配備時に、Go全体のrace検査で `TestRealManagerAcceptsLegacyInitialOffer`と `TestRealManagerRejectsMalformedNonNullCandidate`がICE候補収集の時間切れによりHTTP 504となった。単独実行でも成功と失敗が混在した。ユーザーから原因調査と修正の起票・実行を依頼された。

## 範囲・方針

実Managerを使うシグナリング試験の設定、Pionの候補収集、期限と終了処理を調べ、観測した原因に対応する最小の修正を行う。正常系のHTTP応答と、不達STUNによる意図的な時間切れ・セッション解放の検証を維持する。調査原本に含まれる実ホストの情報は非公開領域へ置く。

通常のテスト環境の修正で解決する場合は本番設定・通信契約を変更しない。本番の不具合が見つかった場合は影響を明示して仕様を更新する。本タスクは調査・修正・検証・コミットを対象とする。

## 原因と修正

正常系テストは `ManagerConfig.API`を指定せず、Pionの既定ネットワークを使っていた。Offer所有者の1秒期限が始まった後、`SetRemoteDescription`からICEエージェントが遅延生成され、`stdnet.NewNet`が全インターフェースのアドレスを列挙する。この処理にmDNS初期化と全ホスト候補の生成が続いていた。正常系ではSTUNを設定しておらず、外部STUN応答待ちが原因ではない。

診断時のスタックで、`stdnet.UpdateInterfaces` → `Interface.Addrs` → `NetlinkRIB`とmDNS初期化を確認した。単独では成功しても期限に余裕が少なく、4件の並行初期化では4件すべてがHTTP 504となった。既存のエラーメッセージは「候補収集の時間切れ」だが、実際の期限にはこの初期化も含まれる。

テスト用APIを作り、標準ネットワークの列挙をOffer期限の外で済ませて既存の `ManagerConfig.API`へ渡す。実UDPのIPv4ループバック候補に限定し、名前解決を検証しない本試験ではmDNSを無効にした。模擬ブラウザーも同じ設定を使い、生成されたOffer・Answerに実際のローカル候補があることを検査する。正常系の1秒期限は維持した。

意図的な時間切れ試験は、応答しないローカルUDPソケットをSTUN先にし、正常系と同じ1秒期限を使う。HTTP 504とセッション解放に加え、STUN要求が届いたことを確認する。以前の5ms期限で初期化中に切れただけの結果を、この試験の成功と混同しない。

同じ並行条件の回帰試験を追加した。診断の一回の比較ではAnswer生成が711msから9.3msとなり、4件並行もすべて成功した。この時間は診断値であり、性能保証や新しい必須性能値ではない。

## 変更範囲と確認

変更はシグナリングのテスト2ファイルと、既存Pionパッケージ2件を直接参照へ移す `go.mod`のみ。依存バージョン、本番コード・設定・通信契約は変更していない。テスト限定の通常変更として、現在のワークツリーで実装した。

- 正常系2試験、意図的な時間切れ、4件並行の回帰試験を `-race -count=3`で実行し、すべて成功した。
- `go mod tidy -diff`は差分なし。変更したGoファイルは `gofmt`済み。
- `go vet ./...`とキャッシュを使わない `go test -race -count=1 ./...`は全パッケージで成功した。前回失敗した `internal/signaling`も成功した。

調査用の一時テストとテスト実行バイナリは削除した。実ホストの情報を含むスタック・トレース・診断ログは非公開領域に保持し、公開記録へ転記しない。ユーザーの未追跡辞書は変更していない。

未解消の失敗はない。今回の検証対象はローカル通信によるシグナリングであり、本番の外部ネットワーク性能を測定したものではない。テスト限定の変更のため、稼働環境への再配備は不要である。
