# RTCレビューで判明した通信境界と再接続の不備を修正する

## 背景 / 目的

RTC実装を通信契約、接続・再接続、音声、DataChannel、下流接続、終了処理の観点からレビューし、具体的な不具合を再現して修正する。
既存の[フロントRTC契約](../../../documents/design/contracts/frontend-rtc.md)と[音声パイプライン契約](../../../documents/design/contracts/audio-pipeline-websocket.md)を判断根拠とする。

初期調査で次を確認した。

- フロントのHTTP期限と中断購読が応答ヘッダー受信時に解除され、本文受信が停止すると交渉が完了しない。
- HTTP再試行の待機タイマーが接続世代の中断で解除されない。
- 初回Offerの要求IDと改訂番号が明示的な`null`でも、識別情報を省略した旧形式として受理される。

追加レビューで次の再現条件を確認し、同じタスクで対応する。

- Answer後のHTTP送信待ち候補には64件上限が適用されず、待機列が増え続ける。
- 初回候補送信中に切断猶予が満了すると再接続要求が失われる。接続後の候補送信中の更新Offerは旧候補と競合する。
- 新セッションへ置換したplaybackで旧発話番号を保持し、新周回のテロップを破棄する。
- 設定取得前の開始が捨てられ、取得失敗後の明示開始でも再取得されない。
- トラック差し替え待機中のミュートと停止が、まだsenderへ移っていない新トラックに反映されない。
- echo/playbackの構築失敗・期限切れで、存在しないCoordinatorを閉じて元のエラーを失う。
- DataChannelの空でないprotocolを拒否しない。
- 静的素材もHTTP応答確定用バッファへ全量格納し、大きなモデルを複製する。
- RTPの欠損により重複判定窓の古い記録が残り続ける。
- 折り返し診断の遅延中止で古いPCMが残り、処理再開後に再生される。
- 出力時計が予定発火時刻を現在時刻として扱い、処理遅延後の最初の音声を破棄できない。

## 完了条件

- [x] RTCの各責務と接続先の実装・既存テストを確認し、具体的な問題と確認限界を記録する。
- [x] 本文受信を含むHTTP実行を既存の期限で終了でき、停止時は実行・再試行待機を解除する。不正JSONは再送しない。
- [x] 初回Offerで省略と明示的な`null`を区別し、不正な識別情報を資源作成前に400で拒否する。
- [x] レビューで追加確認した不具合も、再現条件と回帰テストを添えて修正する。
- [x] 対象テスト、Goの静的検査・競合検査、フロントの型・整形・全体ゲート、独立評価を完了する。

## 設計判断・変更範囲

`src/features/rtc/`と`sincro-rtc/internal/`、接続先を確認対象とする。既存契約へ適合させる修正を基本とし、通信項目・設定・依存は増やさない。
HTTP処理は接続世代が所有する中断通知と既存の操作期限に従わせる。再試行中も要求本文・識別情報は固定する。
実装の分離が必要な既存変更はないため現在のワークツリーで作業し、通信境界と生存期間の変更について独立レビュー・評価を受ける。
公開記録にはソースから確認できる問題と固定データによる確認だけを残す。

## 確認方法

- フロント: RTC対象のVitest、応答本文が停止するストリームと中断の再現、型検査、全体ゲート。
- Go: 入力境界のHTTP試験、`go test ./...`、`go vet ./...`、`go test -race ./...`。
- 変更文書のPrettier、タスク状態と索引の検査。

## 文書同期

通信スキーマは維持する。READMEの候補エラー応答を修正し、[アプリの共通枠組み](../../../documents/design/frontend/app-shell.md)へ設定取得待ち・失敗時の再開始・停止の挙動を同期する。設計索引から両文書へ辿れることを確認する。

## レビュー範囲と結果

| 対象               | 照合した責務                                                | 対応                                                                           |
| ------------------ | ----------------------------------------------------------- | ------------------------------------------------------------------------------ |
| フロントのHTTP境界 | 期限、再送、本文解析、停止、HTTP状態の保持                  | 本文まで期限を適用し、待機を中断。本文破損でも404/410を維持                    |
| 接続状態と候補     | 初回・更新・置換、猶予、順序、保持件数                      | 旧候補と更新を直列化し、猶予満了を保持。Answer後も64件に制限                   |
| アプリとの接続     | 設定取得、機器差し替え、停止、ミュート、テロップ            | 設定完了待ちと再取得、停止世代の無効化、差し替えトラック保護、周回判定の初期化 |
| サーバーHTTP境界   | 初回・更新Offer、候補、識別子、容量、重複排除               | nullを省略と区別。静的配信をAPI応答バッファから分離                            |
| RTCセッション      | 生成、準備状態、再接続、終了、DataChannel、共有UDP          | 診断モードの失敗原因を維持。不正protocolを拒否                                 |
| 音声入出力         | RTP順序・欠損、Opus、再標本化、出力時計、PCM区間、モーラ    | 欠損時の履歴回収、現在時刻での遅延判定、古いechoの破棄                         |
| 下流と起動終了     | WebSocket、合成順序、世代更新、FFmpeg、Consul、プロセス停止 | 関連実装と既存試験を照合。追加で断定できる不具合なし                           |

レビューの対象はローカル／オンプレミスでの通常会話、診断、再接続である。TURN・IPv6など既存の対象外機能を追加せず、通信スキーマ・設定・依存関係は維持した。

## 確認結果

- 修正前にHTTP本文停止・待機中断の3試験、null識別情報の3入力、RTP欠損履歴、実タイマーと同じ予定時刻通知による出力時計の失敗を確認し、修正後の成功を確認した。
- RTC・アプリ接続の対象Vitestは12ファイル83件成功。再接続と旧候補の順序、猶予満了、世代置換、設定の遅延・再取得、ミュート・停止を確認した。
- `npm run gate`の整形・静的検査、型確認・ビルド、フロント全体テストが成功した。追加修正も対象試験と整形・型確認で再確認した。
- `go vet ./...`、`go test ./...`、`go test -race ./...`が成功した。実Pion接続、固定WebSocketサービス、実プロセスの起動終了を含む。
- 通常Go全体試験の初回は終了試験で候補収集時間切れとなったが、当該試験の単独再実行、最終状態の通常全体試験、競合検査付き全体試験は成功した。
- 独立した仕様レビューと実装評価を実施し、評価で見つかったHTTP状態保持と候補上限の不足も回帰試験付きで修正した。
- コメント点検: PASS。

実ブラウザーへの障害注入、実マイクと実下流モデルによる会話の通し確認、長時間の負荷試験は未実施。自動試験とコードレビューで確認した範囲を超えて、不具合が存在しないことを保証するものではない。
