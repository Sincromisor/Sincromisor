# 分割と無音の比較記録

## 変更と判断

Mastraの応答ごとに保留本文を所有する `SpeechPhrases` を追加した。最初の句はすぐ渡し、後続の読点句は8文字以上の読点または句点までまとめる。小数点と数値の桁区切りは次の一文字を待って判定する。句読点と本文は保持し、表情コードの除去・履歴確定は既存の共通モデルへ委ねる。句読点がない回答の待ちを減らすために単語途中を切る規則は追加しない。

前無音100msは接続内で受理した同一発話の先頭要求だけに残し、後続は0msとした。後無音100msと句読点休止は維持する。逐次キャッシュを `streaming-pcm-v2/<前無音>/<後無音>/` へ分離し、旧キャッシュの削除・読取代替は行わない。完全音声用のキー・通信フィールド・確定発話境界は変更していない。

## 実Engineの比較条件

固定のVOICEVOX ENGINE 0.26.0、スタイル0、CPU 4スレッド、48kHz、既存の先頭生成長0.43秒と本番HTTP・PCM変換を使った。最初にモデルを一度ウォームアップした。同じ本文を40ms/文字の固定SSE到着列とし、旧句読点分割、前無音だけの変更、8文字と12文字の候補を比較した。LLM生成速度の実測ではない。

[比較スクリプト](artifacts/compare-pacing.py)は要求受理可能時刻を再生し、各要求のPCM到着と正常終端を記録する。`TestRecordedEngineArrivals` は要求IDと終端を読み、本番RTCの要求ごとの300ms開始待ち、20ms時計、受信抑制と末尾端数の無音補完を通す。WebSocket・Pion・ブラウザーまでの実接続計測ではなく、実Engineから取得した到着列の再生である。再生PCMは入力と全サンプル一致を確認する。

初回の比較は全PCMを単一要求として連結していた。独立評価で限界を指摘されたため、要求IDと正常終端を含む到着列を取り直した。以下には要求単位で再生した結果を記載する。

## 固定文と読み

- 短い回答: 「はい、今日は、晴れなので、公園で、ゆっくり、散歩しましょう。」
- 句読点の少ない回答: 「今日は天気がよいので公園を歩きながらゆっくりとお話ししましょう。」
- 数値: 「値は3.14で、1,234.5円です。」

短文の8文字候補は「はい、」「今日は、晴れなので、」「公園で、ゆっくり、」「散歩しましょう。」の4要求になる。12文字候補は3要求まで減らすが、2要求目の配信が固定到着列で520msから680msへ遅れる。最初の句はいずれも120msで配信できる。8文字を採用候補とし、上限は文字数・時間による強制切断ではなく次の自然な句読点とする。

数値の旧分割は「値は3.」「14で、」「1,」「234.」「5円です。」となり、小数と桁区切りを壊す。変更後は「値は3.14で、」「1,234.5円です。」となり、Engineの読みクエリも `サンテン'/イチヨ'ンデ` と `セ'ン/ニヒャク'/サ'ンジュウ/ヨ'ンテン/ゴ'エンデ_ス` を保持する。数値は初動が遅くても読みを優先する。句読点の少ない文は一要求のままで、読みクエリと音声長も一致した。数値・句読点の少ない文は8文字と12文字で分割が同じため、比較表では取得した `min12` の音声を使う。

| 短文・前無音のみ変更     | 6      | 420ms / 4,840ms       | なし       |
| 短文・8文字              | 4      | 400ms / 4,720ms       | なし       |

| 句読点の少ない文・旧方式 | 1      | 1,640ms / 5,980ms     | なし       |
| 句読点の少ない文・変更後 | 1      | 1,640ms / 5,980ms     | なし       |
| 数値・旧方式             | 5      | 460ms / 4,880ms       | なし       |
| 数値・変更後             | 2      | 640ms / 4,600ms       | なし       |

短文の断片境界にある波形上の無音は、旧方式237〜269ms、前無音のみ変更144〜180ms、8文字候補170〜175ms、12文字候補148〜171msだった。これは各断片を連結したWAV上で振幅閾値500から求めた値で、RTCの開始待ち・末尾の20ms枠への補完とは区別する。合成条件の100msはEngineの音素フレームへ丸められ、実PCMでは96ms相当になる。

8文字と12文字で音声長はともに約4,395msだったが、12文字は次の要求が遅れて再バッファが発生したため採用しない。初回有声音の20ms差は一回の実行の揺れであり、分割規則による初動改善とは主張しない。読みと初動を保って後続の細分化を減らすことを採用根拠とする。[固定文・条件・集計](artifacts/measurements.json)に詳細を残した。

## 確認と残件

対象Python207件が成功した。その後の8文字採用と取消試験の補強は独立対象95件で再確認した。SSE受信境界、本文・表情・履歴、異常EOF・生成失敗・送信失敗・取消、次発話・新接続、Redis/S3の無音条件別キーとキャッシュ音声・モーラ一致を確認した。

Goの再生処理パッケージは実到着列を指定した `go test -race ./internal/media/output` が成功した。Pionのネットワーク情報参照がサンドボックス内では拒否されたため、同じ試験を許可されたホスト環境で実行して確認した。

本番Pythonの対象型検査、対象Ruff・整形が成功した。既存のCamelCaseモジュール名による `N999` だけは対象Ruffで除外し、改名は行っていない。設計索引から辿れるTextProcessor・VoiceSynthesizer設計を同期し、変更理解範囲のコメントを点検した。

実TTSの全断片でモーラ総長を48kHzへ換算したサンプル数とPCM総数が一致した。前無音0でも先頭モーラの位置を0から計算し、句読点の休止は既存の補正を通す。波形の閾値500による有音検出とクエリの読み確認は、耳による自然さ・誤読・音切れ判定の代替にはしない。

実聴取はこの実行環境で行えないため、比較WAVをユーザーへ提示して判定を依頼した。ユーザーは採用した8文字版の短文、句読点の少ない文、数値を含む文を確認し、「変更後は自然で、誤読・休止不足・音切れはない」と回答した。これにより残っていた聴取条件を満たした。自動計測とユーザーによる聴取を合わせて最終判定し、追加の実装修正は行っていない。
