# 合成音声の配信とキャッシュ保存の待機を分離する

## 背景と目的

現行はRedis、S3の順で完成音声を検索し、S3命中時のRedisへの書き戻しを待ってから音声を配信する。生成時は全WAV検証後にRedisとS3へ保存してから終端を返すため、次のテキスト断片の合成も保存に待たされる。キャッシュは再生成可能な補助であり、保存の遅れを読み上げの間延びへ持ち込まない。

## 設計判断

- 正常な音声終端はWAV全体の検証成功を意味し、キャッシュ永続化成功を条件にしない。検証前の音声を保存せず、全体の検証後に保存を予約して終端を返す。
- 保存とS3命中時のRedisへの書き戻しを、サービスが所有する専用の有限キューへ渡す。書込クライアントと実行器もサービス所有とし、接続所有の読取クライアント・HTTP Sessionとは共有しない。
- キューは予約中・実行中も含む件数と総バイト数を制限する。保存用の追加コピーや直列化より先に枠を予約し、予約後の失敗では枠を解放する。満杯時は再生成可能なキャッシュ書込だけを省略して固定理由を記録する。会話PCM・正常終端は省略しない。受理済み保存は接続切断で捨てず、サービス終了時に回収して書込クライアントを閉じる。
- 逐次合成用キー、保存DTO、Redis期限、S3命中をRedisへ戻す方針は維持する。保存ジョブは完成結果を所有し、後続要求から変更されない。途中失敗・全WAV検証前の取消では予約しない。
- S3クライアントには、認識側と同じ接続5秒・読取り30秒・1試行を明示する。Redisにも既存の上限を維持する。この変更だけで対話向けの短い待機予算を達成したとは扱わない。
- 読取りの直列順序、Redisの読取・破損エラーの伝播、S3失敗時の生成への代替は今回維持する。さらに短い検索期限や検索省略は、既存の取得元別計測で遅延・命中率を確認した場合の判断事項とし、未計測の一律値を追加しない。

## 完了条件

- [x] 遅いRedis書込・S3書込が、取得済み音声の先頭PCM、正常終端、次要求の合成開始を待たせない。
- [x] 検証済み完成音声だけを保存し、破損・不完全・取消済み生成を正常キャッシュにしない。書込失敗と省略を会話成功から区別する。
- [x] キューの上限、受理前後の取消、接続終了、サービス終了で無制限蓄積・二重終了・使用後解放を起こさない。
- [x] 同じ音声の反復要求は保存完了後に既存キーへ命中し、S3命中のRedis昇格も維持される。保存待ちの間の重複生成は許容し、新しい重複抑止機構は導入しない。
- [x] 本文なしで検索、書込待ち、書込実行、失敗・省略を区別できる。既存の診断と重複する大量ログは追加しない。

## 対象と同期先

[VoiceCacheManager](../../../sincromisor-server/voice-synthesizer/src/voice_synthesizer/VoiceSynthesizer/VoiceCacheManager.py)、[voice_stream](../../../sincromisor-server/voice-synthesizer/src/voice_synthesizer/voice_stream.py)、`VoiceSynthesizerProcess.py`、`VoiceSynthesizerWorker.py` と既存キャッシュ・終了試験を対象とする。資格情報と接続先は既存のProcess設定・サービス発見を引き継ぐ。

[合成設計](../../../documents/design/backend/services/voice-synthesizer.md)へ保存所有者と完了条件を反映し、[音声パイプライン契約](../../../documents/design/contracts/audio-pipeline-websocket.md)で終端がキャッシュ保存成功を保証しないことを明記する。Go側の要求枠解放、短音声の再生開始、終端検証も同時に確認する。MessagePackの形式とキャッシュ形式は維持する。

## 確認方法とリスク

遅い書込器を使い、先頭・終端・次要求が先へ進むこと、保存時だけ失敗する場合、上限と取消の境界を確認する。実WorkerとGo利用側の短音声の結合確認、ローカルのRedis/S3互換受け口への一往復と対象Python試験を行う。

保存所有者と音声終端の時点を変える高リスク変更として、独立仕様レビューと実装評価を行う。音声の正常完了と永続化の状態を取り違えない。

## 実行結果（2026-11-01）

保存をサービス所有の専用Redis/S3・有限キューへ分離した。予約中と実行中を含め4件・48MiBに制限し、満杯時はキャッシュ書込みだけを固定理由付きで省略する。生成結果のWAV化・保存DTO生成・コピー・直列化より先に枠を予約し、失敗時に枠を解放する。受理済み保存は接続取消で捨てず、サービス終了時に回収して専用接続を閉じる。

S3命中のRedis昇格は、取得音声のWAV全体を検証してから予約する。正常終端は検証成功を示し、保存成功は要求しない。S3の接続5秒・読取り30秒・1試行を明示し、検索順序・Redis読取失敗・S3失敗時の生成への代替・既存キーと保存形式は維持した。

### 確認

- 遅いRedis/S3、上限、予約中の終了、コピー失敗、受理前後の取消、接続/サービス終了、破損WAV、次の合成への進行を含む合成対象試験118件成功、中央ログ収集基盤の専用結合試験1件は今回の対象外として省略。型検査・対象Ruff・整形に成功した。
- 新規Pythonプロセスの実Workerで2,400サンプルの人工音声と正常終端を受信し、一時Redis/S3への保存・再取得・同一DTO・Redis昇格・読取/書込クライアントの独立を確認した。初回S3の割当枠不足は検証環境を修正して解消した。
- 実WorkerのMessagePackをGoの実再生処理へ渡し、300ms未満の短音声が正常終端後に3枠で再生されることをrace付きで確認した。既存のGo要求枠解放・終端検証も成功した。
- 独立初回評価で、生成音声の保存用WAV化が予約前に行われている指摘を受け、予約後の生成へ修正した。満杯時にWAV生成関数を呼ばず、PCM・終端・成功診断を維持する回帰試験を追加した。

保存待ちの間に同じ要求が再生成されること、強制終了時に未保存の受理済みジョブが残り得ることは設計どおりである。検索待機の短縮や重複生成の抑止は追加していない。独立評価の結果は[評価記録](eval.md)に示す。

修正後の独立評価はPASS。独立再試験74件と新規プロセスの実Redis/S3保存・期限・昇格確認に成功した。
