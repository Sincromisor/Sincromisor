# 逐次音声の先頭区間と再生開始条件を整合する

## 背景と目的

VOICEVOXへ先頭0.3秒の区間を要求し、Pythonは100ms単位のPCMにして送り、RTCは300ms以上または正常終端まで再生を待つ。既存Engine試験の28フレームを48kHzへ換算すると先頭は約298.7msであり、設定の0.3秒と実サンプル数は一致しない。

起票前の人工確認では、この先頭区間を現行 `iter_pcm` へ与えても次区間前に配信されるのは200msだけで、300ms分を得るには次の生成区間が必要だった。Engine実機での待ち時間は未計測であり、HTTPの読取境界や再サンプリングを含めた再現を実装前に確認する。

## 設計判断

- 対話の発話終端には触れず、確定後の合成に限って初期区間と転送・再生条件を整合する。
- 最初に、Engineの実サンプル数を基準に先頭生成長を最小限増やし、現行300msの再生条件を満たす案を確認する。固定300msの待ち時間を追加する意味ではなく、受信済み音声量の条件である。
- 初期・再開バッファを根拠なく200msやゼロへ削減しない。先頭区間を増やす案が適さない場合だけ、転送端数と開始条件を一緒に変更する。採用根拠には初回の有声音と途中の不足待ちを使う。
- HTTPのヘッダー・読取サイズ、PCMの区間化、Engineの丸め・段階拡大を通した出力で判断する。WAVの完全性検証と終端前の端数処理、モーラ同期を維持する。

## 完了条件

- [x] 採用Engineと本番用HTTPアダプターを通し、先頭区間のサンプル数、Python転送量、RTC開始条件を対応付けて現象を確認する。人工再現と実Engineの結果を分ける。
- [x] 次のEngine区間を意図的に待たせた試験で、十分な先頭音声が届けば次区間を待たずにRTCが再生を開始できる。短い音声は正常終端で再生できる。
- [x] 音声の欠落・重複・口形ずれ・不完全WAVの正常完了を生まない。入力不足時の再開条件と300ms付近の境界を確認する。
- [x] 同じ日本語文について、最初のPCMだけでなく初回有声音、再バッファ回数・時間、完了までを変更前後で比較する。初回だけ速くても音切れが悪化する案は採用しない。

## 確認方法とリスク

既存のWAV・区間・再バッファ試験に、丸めた先頭長と任意HTTP分割を加える。対象Go試験とPython試験を行い、実Engine→アダプター→RTCの主要経路を一度確認する。初回の無音PCM送信を発声開始と数えない。

複数段の音声時計と開始条件に関わるため、独立仕様レビューと実装評価を行う。性能目標の固定値や複数端末での網羅確認は追加しない。

## 実行結果（2026-11-01）

採用Engineと本番HTTP経路の実測に基づき、先頭生成要求だけを0.43秒（40フレーム）へ増やした。再サンプリング後の先頭19,920サンプルから、次区間を待たず300ms分を転送できる。初期・再開条件300ms、正常終端した短音声の扱い、20ms出力時計と通信モデルは維持した。

対象Python試験、Goのrace試験、固定日本語の到着列再生比較、実Engine→実Worker→RTC/Pionの結合確認、独立評価が成功した。同じ1文では初回有声音780msから380msとなり、再バッファは双方0回、全サンプルの一致を確認した。実Engineの再サンプリングを含まない人工換算とは結果を分けた。

[実装・計測記録](impl.md)に再現手順と数値を、[独立評価](eval.md)に判定を残した。ブラウザー聴取とEngineイメージに未同梱のpytest一式は未実施であり、実再サンプラーの直接確認・本番HTTPの境界試験・RTC実結合で対象条件を確認した。
