# 先頭区間の実測と採用判断

## 採用値

先頭要求を0.3秒から0.43秒へ増やした。RTCの初期・再開条件300ms、100msのPCM転送、20msの出力時計は維持した。

採用Engineの93.75fps丸め、24→48kHzの逐次再サンプラー、Content-Length応答の44byte WAVヘッダーと9,600byte読取りを通すと、次の差がある。

| 要求秒数 | Engineフレーム数 | 先頭の実サンプル数 | 次区間前のPCM転送量 |
| -------- | ---------------- | ------------------ | ------------------- |
| 0.3      | 28               | 13,280             | 100ms               |
| 0.4      | 38               | 18,260             | 200ms               |
| 0.42     | 39               | 18,260             | 200ms               |
| 0.43     | 40               | 19,920             | 300ms               |

0.43秒は100分の1秒刻みの候補で、必要な40フレームに到達する最小値である。模型での28フレーム＝14,336サンプルという単純換算は、逐次再サンプラー内の保持量を含まない。さらにHTTPのヘッダーが最初の読取り枠を消費するため、転送できるPCM量は先頭生成長と一致しない。

## 比較結果

同じ固定日本語文を実Engine→本番 `VoiceVox.query_synthesis_stream`→`iter_pcm`で処理し、到着時刻とPCMを一時ファイルへ保存した。`TestRecordedEngineArrivals`で本番 `output.Processor`の20ms時計と受信抑制を通して再生した。全262,144サンプルは各入力列と完全一致した。

| 条件         | 初回PCM / 有声音 | 再バッファ | 再生完了 |
| ------------ | ---------------- | ---------- | -------- |
| 変更前0.3秒  | 293.4ms / 780ms  | 0回・0ms   | 6,100ms  |
| 変更後0.43秒 | 225.9ms / 380ms  | 0回・0ms   | 5,700ms  |

これは同じ1文・同一ホストでの到着列再生比較であり、普遍的な改善率ではない。有声音は振幅500超の最初の20ms枠として数え、初期無音を発声開始と数えていない。意図的な不足・再開・モーラ位置の固定は既存Go試験で別に確認した。

実Engine→変更後実Worker→Go Synthesizerクライアント→RTC Session→Pion/Opusの実結合も成功した。初回有声音639ms、1,205,760サンプル、終端込み253メッセージ、正常再生完了。26秒弱の長文で、正常終端時刻は受信抑制を含むためEngine生成速度と同一視しない。この実結合時には一時S3の割当不足で書込みが失敗したが、音声は正常完了した。一時環境の割当枠を修正後、別の実Worker短音声でRedis/S3保存と再取得まで成功した。

## 確認

- `test_stream_start_alignment.py`: 3件成功。実Engineと同じ先頭量をContent-Length HTTPで送り、次区間を保留した状態で旧値100ms・中間候補200ms・採用値300msの転送を確認。全PCMの欠落・重複なし。
- Go `internal/media/output`、`internal/media/synthdecode`、`internal/pipeline/client`のrace試験が成功。14,399 / 14,400 / 14,401サンプルの開始境界、短い正常終端と既存の不足時再開・口形の回帰を確認。
- 実Workerが出した2,400サンプルの短音声は、Goで終端前に開始せず、正常終端後に3枠で再生した。
- 採用Engine内の再サンプラーで13,280 / 19,920サンプルと、40フレームの末尾回収後20,480サンプルをassert確認した。Engineイメージにはpytestと元のtestディレクトリがないため、`Docker/voicevox/check_streaming_segments.py`全体の再実行はしていない。追加条件は実Engineでの上記直接確認とHTTP境界試験により検証した。
- 全体ゲートの静的検査・ビルド・テスト、対象Ruff・整形が成功した。ブラウザーでの実聴取は未実施。

## 再現と検証環境

[到着列の取得](artifacts/capture-arrivals.py)を採用Python環境から `--segment 0.3` / `--segment 0.43`で実行する。出力した一時JSONを `SINCRO_STREAMING_ARRIVALS`へ渡し、Goで `go test ./internal/media/output -run TestRecordedEngineArrivals -v`を実行する。PCMを含む到着列は公開成果物へ添付しない。

VOICEVOXイメージを再利用し、直接Engineだけをループバック15022で一時起動した。イメージの新規取得・ビルドはない。キャッシュ検証用のRedis/S3も既存イメージを使いtmpfsに分離した。実装・検証の終了後に今回の一時Engine・Redis・S3を停止し、`--rm`による回収を確認した。一時WebSocketサーバーも正常終了した。既存イメージ・サービス・保存領域は変更していない。
