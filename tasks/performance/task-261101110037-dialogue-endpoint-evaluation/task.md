# MediaPipeの入力窓と対話の発話終端の評価基準を確定する

## 背景と目的

利用者の話を聞き終えてから応答し、言いよどみや息継ぎを途中確定しないことを、応答開始の速さより優先する。2026-11-01のユーザー指摘を受け、chatの無音閾値を1,000msから600msへ短縮することを既定の改善案にしない。

ユーザーから「現行の短い入力でもぎりぎり判定できることを過去に確認した」との情報がある。この実績を出発点とし、モデルの入力形状だけを理由に現行方式を不正と判定しない。現行方式を基準として成立条件と余裕を再確認する。

起票時のHEADは `749889b1`。現行の分類呼出しは16kHzの3200サンプル（200ms）、`AUDIO_CLIPS`、上位1分類とSpeechスコア0.6超で判定する。先行音声は500ms、Goが渡す無音閾値はchatが1,000ms、sincroが600msである。モデル入力窓、APIの最短受理長、アプリの判定周期、無音閾値を別の量として扱う。

## 起票時に確認した根拠

- 同梱 `sincromisor-server/assets/3rd_party/yamnet.tflite` のFlatBufferを読み、入力 `waveform_binary` がfloat32の `[15600]` であることを確認した。16kHzでは975ms相当。SHA-256は `4d8b4a53282dc83ef04e3e7dbc4fbc98082e34e44ed798e16c3a0cdd4c584faf`。
- [MediaPipe公式資料](https://developers.google.com/edge/mediapipe/solutions/audio/audio_classifier)はYAMNetを `1 x 15600` と記載する。2026-11-01参照。入力窓の参考とし、200ms入力の可否・精度の証明には使わない。
- [公式の音声テンソル化実装](https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/calculators/tensor/audio_to_tensor_calculator.cc)は非ストリーム入力の末尾ゼロ埋めを説明する。2026-11-01参照。上流masterの説明であり、採用MediaPipe 1.1.1の動作は本タスクで照合する。
- [過去設計](../../../documents/design/archive/legacy-flat/backend_speech_extractor.md)は3200サンプルとYAMNetで運用可能との判断を記すが、ユーザーの記憶に対応する実音声の精度測定原本は起票時には特定できていない。
- [直近の入力境界修正](../task-261031225710-extractor-buffer-boundary/task.md)は通常220msから200msへ変わる。境界試験の成功と実音声での判定成立を区別し、過去の実績がどちらの区間長か確認する。

## 完了条件

- [x] 採用版・同梱モデルで、200msの入力が受理される条件、ゼロ埋め・内部区間化、返却件数と時刻を確認し、例外なく動くことと発話を正しく判定できることを分けて記録する。
- [ ] 現行200msを基準に、旧220msとモデル窓相当の入力を必要な比較対象として使い、発話・無音・小声・息継ぎ・言いよどみ・語尾・短い応答を含む少数の日本語音声で判定を確認する。短縮も975ms化も採用前提にしない。
- [ ] 入力音声に「まだ話し途中」と「応答してよい終端」を事前に付け、途中確定・語頭語尾欠落・誤発話検出・終端から確定までの時間を併記する。現行閾値前後の間と、音声区間境界に語尾が重なる例を含める。
- [ ] 判定時刻を入力サンプル位置へ対応付ける。重複窓を試す場合は、同じ無音の二重加算や過去のSpeechによる終端遅延を評価する。`start_at` は現状で繰り返し更新されるため、発話終了の計測基準に流用しない。
- [ ] 現行維持または変更候補の採否と理由を決める。指定した「話し途中」の例で新たな途中確定・欠落を生む候補は、時間だけ改善しても採用しない。成立を確認した短入力の条件と更新時の回帰確認方法を残す。

## 範囲と判断

本タスクは採用版の検証、再現手順・必要最小限の試験、現行設計の説明補完までとする。本番の200ms判定周期、Speech閾値、先行音声、chat/sincroの無音閾値は変更しない。現行が成立するなら変更不要との結論で完了できる。修正が必要な場合は、再現した問題・入力窓・進め幅・終端判定の関係と変更範囲を具体化し、実装判断へ引き継ぐ。

MediaPipeとYAMNetを前提とし、外部APIや新しいモデル、先行LLM生成、割込み発話機構の導入へ広げない。フロントVADのゲートとサーバー終端判定は分け、まずサーバーへの固定PCM入力で比較する。

## 対象と確認方法

- [SpeechExtractorWorker](../../../sincromisor-server/speech-extractor/src/speech_extractor/SpeechExtractor/SpeechExtractorWorker.py)、同サービスの既存試験、同梱モデル、`uv.lock`。
- [Goの無音設定](../../../sincromisor-server/sincro-rtc/internal/pipeline/client/extractor.go)と[SpeechExtractor設計](../../../documents/design/backend/services/speech-extractor.md)。

無音・正弦波と偽分類器だけでは判定品質の確認を完了しない。権利・公開範囲を確認した日本語音声を採用モデルで処理し、期待区間と検出区間を比較する。非公開原本を公開タスクへ添付せず、再現手順と識別情報・集計だけを残す。実モデル確認ができない場合はその条件を未完として明示し、閾値変更の根拠にしない。

## 実行結果（2026-11-01）

- MediaPipe 1.1.1、同梱モデルSHA-256が起票時と一致することを確認した。`AUDIO_CLIPS`・16kHz・モノラル・float32で1、320、3,200、3,520、15,600サンプルを受理し、各結果は1件、時刻0だった。固定乱数入力を明示的に15,600サンプルまでゼロ埋めした結果と完全一致した。
- 15,601と31,200サンプルでは結果が2件、時刻0msと975msだった。短い入力のAPI受理・末尾ゼロ埋めと、975ms単位の内部区間化を7件の実モデル試験で確認した。分類品質の証明には使用していない。
- ユーザー確認では、息継ぎ・言いよどみ・小声を含む検証音声と過去の測定記録は存在せず、実地テストによる評価に留まる。同梱音声や合成音声をその代替として品質確認済みにしない。
- 本番設定は維持した。200msが不正という結論、975ms化、chatの無音閾値短縮は採用していない。現行方式の品質と余裕の再評価は未完である。

### 再開時の評価基準

音声を実モデルへ通す前に、16kHzの入力サンプル位置で発話開始・語尾・「まだ話し途中」の間・「応答してよい終端」を注釈する。無音、小声、息継ぎ、言いよどみ、短い応答、1,000msの前後に跨る間、200ms境界に語尾が重なる例を少数含める。原本は非公開領域に置き、公開記録は利用範囲を確認した識別子・ハッシュ・集計に限定する。

現行200ms、旧220ms、975msの非重複窓を同じPCMで比較し、各分類の入力先頭・末尾と、発話ごとの検出開始・確定送信位置を記録する。途中確定数、語頭語尾の欠落サンプル数、誤発話検出数、注釈終端から確定までの時間を併記する。重複窓は今回試していない。試す場合は無音加算を進め幅で一度だけ行い、過去Speechの残留による遅延を別に計測する。

指定した「話し途中」に新しい途中確定や欠落を生む候補は速度にかかわらず不採用とする。基準自体の途中確定も記録し、未測定を0件としない。モデル・MediaPipe更新時は同一ハッシュの音声と注釈で実モデル試験・品質比較を再実行する。
