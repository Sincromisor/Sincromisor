# レビュー: task-261101110038-recognition-storage-isolation

## 判定

APPROVED

## 理由・申し送り

- 現行の保存がWorkerの結果返却前・共有推論スレッド上にあることを確認した。保存を応答成功条件から外す挙動変更、サービス所有の保存処理、所有コピー、受理前後の取消と終了順が明記され、安全に実装できる。
- キュー飽和時に保存を黙って捨てず、モデルスレッドを解放して受渡しを待つ方針である。容量予約後にコピーを作り、予約中・実行中も上限に含める補足が反映され、投入待ちの所有コピーを無制限に増やさない方針も確定している。保存時間をrecognition_executionから切り離す診断変更も対象に含まれる。

## 自律補完

- なし。通常の実装判断はタスクに示した根拠と確認方法に沿って具体化できる。

## 実行前の独立再確認

APPROVED。現行Workerは保存まで共有認識スレッドで処理し、ProcessはS3クライアントを接続ごとに閉じる。保存所有権と満杯待ちの移動は、今回の問題を解くために必要な範囲である。

- 枠予約後にCPU音声、結果、補正追跡の独立コピーを作り、受信バッファ再利用と競合させない。推論取消では既存の設定復元・テンソル解放を回収し、保存受理の前後を一つの境界として扱う。
- 現行の累積認識音声には固定長の上限がない。単一ジョブが保存キューのバイト上限より大きい場合は空き待ちを永久化できない。`AUTO_FIX`として保存の明示的な失敗へ分類し、認識成功と区別して診断する。通常の満杯は指定どおりモデルスレッド外の取消可能な待ちとする。
- Opus生成物の共用とJSON・キー・補正追跡の維持を確認する。形式の往復確認には一時ディレクトリ、必要な場合の `opusenc`、ローカルS3互換受け口を使う。正常サービス終了では受理済み処理の回収後にサービス所有クライアントを閉じる。
