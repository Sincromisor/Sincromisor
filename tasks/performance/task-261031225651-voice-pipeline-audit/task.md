# 音声対話の全経路を調査し改善根拠を整理する

## 目的と完了条件

ユーザーの依頼に従い、マイク入力から応答音声の再生まで、処理量、待機、直列化、コピー、保存、既存の計測を調べる。構成要素ごとに改善を起票して実行し、実測できない候補と再現できる問題を区別する。

- [x] フロント、RTC入力・調停・出力、抽出、認識、文章処理、AgentServer・LLM接続、合成、キャッシュ・保存を確認する。
- [x] 改善を小さな独立タスクへ分け、根拠と対象確認を記載する。
- [x] 調査範囲・優先順位・未計測事項を以下に残す。

## 調査結果

基準は調査開始時のリポジトリ実装である。コードで確定できる処理量と待機条件を記載する。実機の発話終了から初回再生までの時間、GPU負荷、実ネットワーク遅延は測っていない。以下の順序は修正の確実性と影響範囲に基づき、実環境の遅延寄与率を示さない。

| 構成要素             | 確認した実装と所見                                                                                                                                                                                           | 対応・判断                                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| ブラウザー入力       | `userMediaAudioProcessor.ts` はWebAudioから送信トラックへ直接接続。`learnedVadWorkerClient.ts` は必要時だけWorkerを生成しPCMをTransferableで渡す。`sileroVad.worker.ts` は実行中の次候補を最新一件へ置換する | 無制限の推論待ちはない。ゲート・推論間隔は精度との関係があり、端末計測なしに縮めない                           |
| RTC入力              | `media/input/processor.go` は作業配列を再利用し、16kHz・20msへ変換。RTP欠落は64パケットの並べ替え窓で処理する                                                                                                | 正常入力へ固定64パケット分を加えるわけではない。欠落時の滞留はネットワーク試験が必要。今回の局所改善へ混ぜない |
| 調停・キュー         | `pipeline/runtime.go` は暫定認識にも全履歴を複製・転送し、`conversation.requests` へ保持。Pythonは暫定要求へ応答しない                                                                                       | 優先修正。不要な転送と世代終了までの保持を除去する                                                             |
| 音声抽出             | `SpeechExtractorWorker.__get_audio_buffer` は3200より大きい条件のため、通常入力で200msではなく220ms待つ。600msの無音確定も3区間660msになる                                                                   | 境界テストで再現。3200到達時へ修正。先行音声500msと分類閾値は維持する                                          |
| 分類器               | YAMNetは共有一本のスレッド。イベントループは解放済みで、接続間の実行は直列                                                                                                                                   | 推論時間・接続数次第の候補。モデルを増やす変更は実測後に判断する                                               |
| 音声認識             | `SpeechRecognizerNemoProcess.py` は差分音声を容量倍増配列に蓄積し、暫定結果ごとに累積全体を再認識。`SpeechRecognizerNemoWorker` は一要求内の追加デコードでエンコーダー出力を再利用済み                       | 長発話では処理対象の総音声長が二次的に増える候補。GPU実測なしに暫定結果を落とさない。待機・実行計測を追加する  |
| 認識の保存           | ローカル保存・音声エンコード・S3保存が共有認識スレッド上で結果返却前に実行され、既存query_timeには含まれない                                                                                                 | 計測漏れを修正する。保存分離には取消時の資源寿命と保存失敗契約の設計が必要で、推測だけで非同期化しない         |
| 文章処理             | `mastra_client.py` は接続内HTTPプールを再利用。`mastra_worker.py` は句読点で増分を合成へ渡す。受信キューは上限なし                                                                                           | 暫定要求の除去で不要な滞留を減らす。確定発話が生成を上回り続ける場合の上限制御は会話受付仕様と一緒に判断する   |
| AgentServer・LLM     | `agents/character.ts` は直近20件、semanticRecall等は無効、再試行0、ツール最大5ステップ。HTTP本文の逐次配信を利用                                                                                             | 生成初回、ツール、GPU競合は未実測。量子化・モデル・コンテキスト・句読点の変更は品質評価が必要                  |
| 合成・配信           | `voice_stream.py`、`stream_delivery.py` は100ms区間を逐次配送し、WAV全体と保存の完了後に終端を送る。生成HTTPは接続プールを再利用                                                                             | 完成音声を待つ旧方式の指摘は該当しない。保存I/Oが次要求を遅らせる候補は既存の操作別時間で確認可能              |
| 合成キャッシュ       | `VoiceCacheManager.load_cached_voice` はS3命中をRedisへ戻さない。通常取得では昇格している                                                                                                                    | 同じ音声の反復S3取得を修正。キー・保存形式・有効期限を維持する                                                 |
| RTC出力              | `media/output/frame.go` は無音を含め毎秒50回PCM配列を確保。300msの初期・再開バッファと20ms時計は途切れ防止の契約                                                                                             | 作業配列だけ再利用する。300msバッファを根拠なく短縮しない                                                      |
| ブラウザー再生・描画 | `rtcRemoteTrackHandlers.ts` は受信MediaStreamをmedia要素へ設定。音声はWebRTC再生で、口形とテロップはDataChannelから更新                                                                                      | 3D描画と音声全量のアプリ内蓄積は直列接続されていない。ブラウザーのジッター・端末再生遅延は実機計測が必要       |
| 観測・配備           | Pythonの段階別時間、Goの段階ログ・キュー・時計診断がある。Consul発見と接続は世代開始時                                                                                                                       | 通常発話ごとのサービス再接続はない。ログI/O・同一GPU競合の順位は稼働時計測を要する                             |

## 確認と残る制約

各対象のコード・呼出元・既存テスト・設計を照合した。変更は各タスクの対象テストで確認する。モデル精度・実端末・GPU・ネットワーク・長時間多接続の性能値はこの調査からは断定しない。稼働環境で測定する場合は、同じ人工入力について発話終了、抽出確定、認識の待機と実行、初回文章断片、合成の初回区間、RTC初回音声、ブラウザー受信・再生を対応付ける。起動直後とキャッシュ命中時を分け、認識本文や実音声を公開記録へ含めない。
