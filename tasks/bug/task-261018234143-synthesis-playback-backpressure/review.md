# レビュー: task-261018234143-synthesis-playback-backpressure

## 判定

APPROVED

## 理由・申し送り

- 要求14の先頭での切断と、`output.Processor.beginStream` の8要求上限、`Session.synthOutputLoop` の追加失敗時の切断が対応する。長い応答を順序どおり完走させる要件はユーザー要求に、有限保持・世代境界・取消・不正データ拒否は既存契約と安全性に根拠がある。
- `internal/rtc`、`internal/media/output`、直接関係する `internal/pipeline` を一緒に確認する範囲は妥当である。外部形式を変えず、既存の20ms時計と300msの再バッファ量を利用する方針は実装可能な最小候補である。
- 8要求が満杯になってから待つだけでは、先頭要求の最大120秒の再生を待つことがある。取り込む前の未再生PCMを300ms程度に制限し、ロック外で再試行する方針なら、通常の各待機を最大0.5秒の一区間程度へ抑えられる。終端と中止済み要求の遅着はこの待機に含めない。
- 再試行を返す場合は区間順序・再生項目・PCMを変更しないことが必要である。待機中は `Session.outboundMu` と `Processor.mu` を解放し、再試行ごとに世代境界を通す。不正区間を単なる満杯として無期限に再試行しない。
- 音声経路の待機を短くしても、`Synthesizer.SendResult` の未完了8件待機は要求全体の終端まで続く。そこで `processorLoop` が止まると、`Processor.Results` の配送を待つ `baseClient.readLoop` も止まり、文章処理サービスのPingへ応答できない。長い先頭要求と後続8件以上を使い、この経路も検証する。合成サービスだけの期限確認では完了条件を満たさない。
- 取消・世代更新中の再試行、不正区間と終端、有限保持、順序とテロップ、上流期限を確認する既存処理担当間の試験は、この変更のリスクに対応している。必須試験の失敗を記録するだけで完了する条件にはなっていない。VPS配備はタスクの必須完了条件ではない。
- コメント品質は [ソースコードコメント品質](../../../documents/rules/source-comments.md) を直接適用する。日本語のタスク名・説明と、範囲・確認方法はMarkdown規約に適合する。
