# 会話の話者と新着を支援技術へ伝える

## 背景 / 目的

2026-10-24のUIレビュー指摘6。優先度は中。会話の話者・エラー種別を画像と配置で表すが、画像の代替テキストは空で本文に話者名がない。新着の通知構造もない。原則§7・§9に基づき、支援技術で話者と更新を理解できるようにする。

## 完了条件（受け入れ条件）

- [ ] 発話と話者名、サービスの通知・エラーの関係を支援技術で読み取れる。位置や画像だけに依存しない。
- [ ] 新しい発話を適切に通知し、履歴全体、アイコン変更、再購読による既存履歴を新着として繰り返し読まない。
- [ ] 同一IDで更新される認識途中の本文やテロップの細かな更新を、その都度過剰に読み上げない。確定情報が契約にない場合に確定と推測表示しない。
- [ ] 視覚上の説明段落を増やさず、話者名と会話・通知の構造で意味を伝える。本文の読み上げを画像の代替テキストで重複させない。

## UIの判断基準

[Web UI・UX設計原則](../../../documents/rules/web-ui-ux.md)と、2026-10-24のユーザー指定「説明しなくても理解できるのがよいUI」を適用する。操作名、配置、まとまり、選択・処理状態、実際の動作で解決する。説明文、補助ラベル、免責文、確認ダイアログの追加を既定の解決策にしない。

追加する文言は、既存の表示から分からない利用条件・影響・失敗・回復方法に限る。追加時は、その文言が必要になる判断を実装記録に短く残す。項目名の言い直しや常時表示の注意書きは増やさず、操作名と支援技術の名前は保持する。

## 設計判断と変更範囲

既存の `speaker_name`、`message_type`、メッセージIDを調べ、表示上の話者名と通知方法へ利用する。名前がない場合の最小の代替名を定める。`system` を全てサービス通知と決めつけず、キャラクター発話を含む現行の生成元を確認する。

通信形式にない完了フラグを仮定しない。連続更新をまとめる等の必要最小限の通知方式を既存契約の範囲で選ぶ。通信契約追加、音声認識処理の変更、会話本文の編集機能は対象外。[指摘5](../task-261024223621-make-conversation-history-readable/task.md)の履歴表示と併せて適用できる構造にするが、履歴操作の実装自体は含めない。

## 確認方法

新着、同一IDの連続更新、アイコン変更、再表示を使う対象テストで通知対象を確認する。Playwright CLIでアクセシビリティ構造・話者名・通知領域を確認し、利用可能なスクリーンリーダーで一連の読み上げを一度確認する。実機で未確認の挙動をDOM検査だけで保証しない。対象の静的検査と型確認を行う。

## 文書同期

[共通枠組み](../../../documents/design/frontend/app-shell.md)へ話者の表現と更新通知の規則を同期する。通信形式は維持する。
