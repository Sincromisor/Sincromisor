# レビュー: task-261114152036-release-vrm-selection-object-urls

## 判定

APPROVED

## 理由・申し送り

- 選択処理が保存前に生成するURLと、復元時に生成するURLの双方に解放経路がない。問題と対象コードは一致し、URL所有者を選択側へ集約する方針は既存のCache Storage保存と両立する。
- GLTFLoaderの成功・失敗は非同期コールバックで通知される。コールバック内の例外も利用終了の通知を通すようにし、URL解放をモデルのGPU資源解放へ混ぜない。
- URL解放タスクはモデル交換の実装を要求せず、初回読込の利用開始・終了と、選択差し替えを安全に接続できる。後続タスクはこの窓口を再利用する。
- 生成・解放の回数と実際の読込境界を結ぶ確認は資源寿命の検証に必要であり、長時間のメモリー測定を必須としていない点も妥当である。

## 自律補完

- `AUTO_FIX`: 選択側の保持と進行中の読込利用の有無を追跡する最小構成を使う。汎用的な参照カウント基盤や複数アプリ間の資源管理機構は追加しない。根拠は、ページ単位で共有するDialogManagerと現在の単一シーン構成である。
- `AUTO_FIX`: 保存失敗時に保持する「現在の有効な選択」は、処理開始時に有効だった選択とする。保存成功後にURLを生成すれば失敗経路のURL生成自体を削減できる。新たな選択競合の扱いは、先行タスクの選択中開始抑止と同じ所有者へまとめる。
