# 入力機器の取得失敗を状態へ反映し再試行できるようにする

## 背景 / 目的

2026-10-24のUIレビュー指摘2。優先度は高。専用ブラウザーでマイク取得が `NotAllowedError` になった後も「接続中／running」が残り、「会話を開始」を再度押しても再試行されなかった。権限拒否にも「カメラまたはマイクが見つかりません」と表示する。原則§5・§6に基づき、設定を保って回復できるようにする。

確認基点は `d5eb90b4c0a546f37b459bfec871f767a71cb9d7`。再現時はバックエンド未接続であり、マイク取得失敗の確認とRTC接続成功は分けて扱う。

## 完了条件（受け入れ条件）

- [ ] マイク取得失敗が現在の開始処理へ伝わり、接続処理が進んでいないのに「接続中」のまま残らない。取得受理と成功を区別する。
- [ ] 権限拒否、機器不在、その他の取得失敗を区別する。未確定の原因を断定せず、通常表示に例外全文や内部状態名を流さない。
- [ ] 権限や機器を直した後、設定・モデルを保持して一つの明確な操作で再試行できる。押しても動かない開始ボタンを残さない。
- [ ] 再試行の連打や旧世代の成功・失敗で二重取得・二重接続を起こさず、終了後の結果から送信や機器使用を再開しない。
- [ ] 音声取得失敗だけで、独立して成立しているカメラ追跡を理由なく停止・再取得しない。音声失敗時も全体終了で残る機器を停止できる。

## UIの判断基準

[Web UI・UX設計原則](../../../documents/rules/web-ui-ux.md)と、2026-10-24のユーザー指定「説明しなくても理解できるのがよいUI」を適用する。操作名、配置、まとまり、選択・処理状態、実際の動作で解決する。説明文、補助ラベル、免責文、確認ダイアログの追加を既定の解決策にしない。

追加する文言は、既存の表示から分からない利用条件・影響・失敗・回復方法に限る。追加時は、その文言が必要になる判断を実装記録に短く残す。項目名の言い直しや常時表示の注意書きは増やさず、操作名と支援技術の名前は保持する。

## 設計判断と変更範囲

非同期取得、アプリ状態、RTC開始、再試行をまたぐ高リスク変更として独立レビュー・評価を行う。取得結果は音声入力制御から既存のアプリ制御へ返し、アプリ制御が失敗・再試行可否を所有する。音声と追跡の独立した開始方針を保ち、画面に別の成功判定を作らない。失敗表示のためだけに体験全体を停止済みにし、稼働中のカメラを再開始する実装は避ける。

短い状態表示と回復操作で解決し、毎回の警告ダイアログや長い対処文へ置き換えない。権限変更のようにUI内で代行できない操作だけ、必要な場面で短く案内する。診断詳細は既存の診断経路へ置く。

初回の音声取得失敗からの回復と、必要な開始・再試行状態が対象。一般のRTC再接続方式、サーバー契約、機器切り替え全般の再設計は対象外。

## 確認方法

- 結合テストで権限拒否・機器不在の状態遷移、再試行成功、連打、旧結果の無効化、取得中の終了を確認する。RTC開始回数とトラックの解放を観測する。
- Playwright CLIで権限拒否後の表示と再試行導線を確認する。ブラウザーの模擬機器を使う場合も、本番の音声取得処理から失敗・成功を伝える経路を通す。
- カメラ追跡中に音声だけが失敗した場合に、重複追跡や全体終了漏れがないことを確認する。
- 実装時は全体ゲートと独立評価を行う。再試行成功は本番のブラウザー音声取得経路から、現在の開始世代でRTC開始へ一度だけ進むことを確認する。利用可能な開発用バックエンドでの正常接続は補助確認とし、模擬確認と区別する。
