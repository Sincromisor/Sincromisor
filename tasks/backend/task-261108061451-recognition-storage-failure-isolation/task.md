# 認識記録の保存障害を保存先ごとに分離する

## 背景 / 目的

認識処理と保存処理を分離する既存設計に対し、次の例外経路で保存可能な記録まで失われる。

- S3クライアントの生成失敗でローカル保存へ到達しない。
- Opusの圧縮失敗で認識JSONも保存されない。
- 保存受渡しのコピー・投入失敗が認識の例外になり、成功した認識結果を返せない。
- ローカル保存で受信した会話IDを直接パスへ使うため、絶対パスや親ディレクトリ指定を受け入れる。

通常のGo経路では会話IDを生成・照合しているが、Recognizerの保存境界自体でも保存先の逸脱を防ぐ。

## 完了条件

- [x] S3の準備失敗時もローカル保存を試み、次の保存要求で再度準備できる。
- [x] Opus失敗時もJSON・追跡情報を保存し、ローカル音声は既存のWAV形式へ退避する。S3音声の省略は診断する。
- [x] コピー・投入失敗で予約枠を解放し、失敗を診断して認識結果を返す。取消は引き続き伝播する。
- [x] ローカル保存先が設定ディレクトリ外へ逸脱する会話IDを拒否する。設定配下から外への既存シンボリックリンクも拒否する。
- [x] 例外を注入する試験で上記と後続要求の継続、既存の所有コピー・枠上限・終了順序を確認する。

## スコープ境界と設計判断

RecognitionStorage、RecognitionStorageWriterと対応テスト、サービス設計を対象とする。
既存ファイルの削除、通信スキーマ変更、保存クライアントの自動再接続、追加の再試行ループは行わない。
保存失敗を警告し、既存の認識成功を維持する。受理済み保存の所有者と終了順序は変えない。
評価音声、実S3、開発用デプロイ環境を使わず、人工入力と一時ディレクトリで検証する。

保存境界の変更のため仕様と実装を独立確認する。並行実装や既存変更との競合がないため現在のワークツリーで作業し、変更・検証・タスクを一つのコミットにまとめる。

## 確認方法

対象pytest、Ruff、ty、変更Markdownの整形、タスク管理検査を実行する。
S3準備失敗、圧縮失敗、コピー失敗、投入失敗、ローカル書込み失敗、パス逸脱を個別に注入する。
既存の認識実行器と保存サービスの試験も実行する。
フロントエンドへ影響しない局所変更のため対象確認を完了判定とする。

## 文書同期

[SpeechRecognizer設計](../../../documents/design/backend/services/speech-recognizer.md)の保存障害時の挙動を同期する。

## 確認結果

- 認識パッケージのpytestは60件と7件の副試験が成功した。
- 独立評価では保存と実行器の28件の試験、対象Ruff・整形・ty・Markdown確認が成功した。
- S3準備、Opus圧縮、所有コピー、投入の失敗後も、保存可能な記録と認識結果が維持されることを確認した。
- 不正会話IDと全出力形式の既存リンクを拒否し、保存先外のファイルが変更されないことを確認した。
- 評価用音声、実S3、GPUモデルは使用していない。コメント点検はPASS。
