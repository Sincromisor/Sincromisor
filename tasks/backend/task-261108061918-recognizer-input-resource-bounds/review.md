# レビュー: task-261108061918-recognizer-input-resource-bounds

## 判定

APPROVED

## 理由・申し送り

- 音声メタデータ、累積PCM、推論キュー、切断検知の問題を現在の実装で確認した。入力境界と資源保護に根拠があり、評価音声を必要としない変更である。
- Goの送信は未応答1件であり、同じ発話の未送信差分だけを結合する。通番の欠番を許容しつつ、接続の会話ID、通番増加、発話の確定順序を検証すれば、正規経路を維持できる。
- 受信・処理のTaskGroupは接続が所有し、累積PCMを変更するのは処理側だけとする。切断時は兄弟タスクを取り消し、実行済み推論の回収後にPCMを解放する。受信側は次の入力を累積配列へ書き込まない。
- 推論枠は保存受渡しの待機へ持ち越さない。既存の保存所有コピーと取消回収を維持するため、保存ファイルを本タスクで変更する必要はない。
- 64MiB・32件・1MiB・5秒は既存の関連上限に根拠があり、認識精度やGPUで処理可能な発話長の保証へ拡張していない。対象確認の失敗を記録だけで完了扱いにする条件もない。

## 自律補完

- `AUTO_FIX`: 未確定発話中の別発話IDはGoと同様に拒否する。新しいIDだから累積音声を捨てる実装は「音声を黙って切り捨てない」と矛盾する。確定後の発話IDは増加を要求すれば、完了済みID一覧を無制限に保持せず再利用を拒否できる。
- `AUTO_FIX`: ThreadPoolExecutorの未開始Futureを取り消しても、内部の待ち項目は直ちに取り除かれない。取消直後に枠を返す場合は、待ち項目が音声参照を保持し続けない仕組みが必要である。長い推論中の取消・再投入でも保持量が増え続けないことを試験する。完了通知で枠を返すだけでは十分でない。
- `AUTO_FIX`: 正常な切断や空フレームによる終了でも、受信タスクが単に戻って処理タスクを待ち続けることがないよう、TaskGroup全体の終了を保証する。最初の切断・失敗を診断し、兄弟タスクの取消で原因を上書きしない。
- `AUTO_FIX`: 1MiBはアプリケーションで受理するフレームの上限とする。実WebSocketサーバーにも受信上限を反映し、復号前の巨大フレーム保持を避ける。実装確認では固定MessagePackによる本番受信処理と、実スレッドによる枠・取消の試験を分けて確認する。
