# 音声認識の入力検証と保持量の上限を設ける

## 背景 / 目的

Recognizerは音声メタデータを検証せず16kHz・モノラルとして推論し、同じ発話IDの差分を無制限に累積する。
共有ThreadPoolExecutorの待ち行列にも上限がない。無音終端を生じない入力や多接続で保持量が増え続ける。
また推論待ち中は次のWebSocket受信を行わないため、相手の切断を検出できず未開始推論を取り消せない。
既存契約の入力形式と発話順序を境界で検証し、音声を黙って切り捨てず過負荷を接続異常として返す。

## 完了条件

- [x] 16kHz・モノラル・int16・2バイトとPCM配列の整合、非負のID、有限時刻、接続内の会話ID固定、増加する通番と確定済み発話の再利用禁止を確認してから累積する。通番の欠番は許容する。
- [x] 累積音声を既存保存サービスの単独上限と同じ64MiBまでに制限し、倍増確保も上限を超えない。確定要求の処理終了で音声参照を解放する。
- [x] 共有推論の実行中・未開始を32件までとし、満杯時は即時失敗する。取消・失敗・投入失敗で枠を漏らさない。保存待ちは推論枠を占有しない。
- [x] 推論中も受信を待ち、切断時は未開始推論を取り消し、開始済みは既存実行器で回収する。受信キューは1件、1フレームはGoの上限と同じ1MiB、送信待ちは既存Extractorと同じ5秒までとする。
- [x] 人工PCM・固定MessagePack・実スレッドによる正常経路、通番欠番、形式違反、上限境界、取消と後続処理の回帰テストが通る。

## スコープ境界と設計判断

Recognizerの接続処理、累積バッファ、共有実行器と対応テスト、サービス設計を対象とする。
Goの未応答1件・差分結合契約に合わせ、正規クライアントの通信スキーマを変更しない。
64MiBと32件は品質・性能の達成値ではなく、既存の保存・推論基盤に合わせた資源保護上限である。GPUで処理可能な発話長を保証せず、超過音声の分割や認識精度の評価は行わない。
既存の単一モデル所有と取消回収を維持し、接続の受信・処理を同じTaskGroupで終了する。
現在ワークツリーで直接実装し、仕様・実装の独立確認を行う。別タスクの保存ファイルには実装変更を加えない。

## 確認方法

対象pytest、関連するGoパイプラインテスト、Ruffとty、変更Markdownとタスク管理検査を実行する。
実GPU、評価用音声、ブラウザー、配備環境は使用しない。
[音声パイプライン契約](../../../documents/design/contracts/audio-pipeline-websocket.md)のGo入力要件と照合し、[サービス設計](../../../documents/design/backend/services/speech-recognizer.md)へ上限と失敗条件を記載する。

## 確認結果

- 音声認識全テスト、共通WebSocket入口の認識器4ケース、Go/Pydantic互換試験は合計88件と7件の副試験が成功し、プロセスも正常終了した。
- `go test ./internal/pipeline/...` は調停・クライアント・サービス発見・プロトコルの4パッケージが成功した。
- 対象Ruff・整形・ty、Markdown確認が成功した。Ruffは変更前からある命名などの4種の指摘を除外した検査であり、当該新規モジュールには抑制を追加していない。
- 独立評価の初回で空フレーム終了時の取消漏れが見つかり、修正・回帰試験を追加した。再評価では別接続がモデルを占有したまま対象の未開始推論を取り消し、正常終了することを確認してPASSとなった。
- 全サービス入口を含めた追加試験では、対象外サービスの終了時にスレッド待ちが残ったため中断した。上記の認識器に絞った確認は正常終了し、対象外コードは変更していない。
- 評価用音声・実GPUモデルは使用していない。コメント点検はPASS。
