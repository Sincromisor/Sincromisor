# レビュー: task-261018215553-synthesis-request-backpressure

## 判定

APPROVED

## 理由・申し送り

- 配備中に再現した「未完了8要求の間に9件目が届くと音声が欠落する」不具合が根拠である。`synthesisRequests.add`は現在8件で即時エラーを返し、`Coordinator.processorLoop`が送信失敗として再初期化する。原因説明・対象ファイル・修正方針は現行コードと一致する。
- 8件という既存の容量と通信検証を保ち、枠の解放まで上流を待たせる変更は最小単位である。Python・フロント・通信形式の変更は不要で、実環境での会話確認は既存の配備タスクへ分離されている。9件以上の実WebSocket試験と取消・終了・競合の確認には、再現条件と接続の生存期間に基づく根拠がある。
- 題名・説明・完了条件は日本語で、観測可能な結果を示している。コメント品質は [ソースコードコメント品質](../../../documents/rules/source-comments.md) と [Go規約](../../../documents/rules/coding-go.md) を直接適用する。タスク文中に規約の複製や必須コメントを省略する条件はない。
- 本レビューでは `SendResult`の呼出元、受信・終端処理、接続終了、世代更新、既存試験を照合した。ソースコード・状態情報は変更しておらず、運用操作や実装後の検査は行っていない。

## 自律補完

- `AUTO_FIX`: 接続の所有権は既存の `baseClient`、要求ID・照合表は接続ごとの `synthesisRequests`、送信順は `Synthesizer`が維持する。待機は呼出元コンテキストと接続の生存期間に従い、完了受信または取消・終了で解除する。受信側が必要とするロックを保持して待たない。現行の `requestSendMu.Lock`で送信順を待つ呼出しも、取消・接続終了で収束できるようにする。具体的な同期手段は実装者へ委ねる。
- `AUTO_FIX`: 既存の要求ID契約から、枠を得る前に取消した呼出しはIDと未完了要求を予約せず、次の送信に欠番を作らない。正常な終端区間の検証後だけ完了枠を解放し、通常のPCM区間や不正な終端では解放しない。送信開始後の失敗は配送の成否が不確かなため、要求だけを巻き戻して接続を再利用せず、既存の接続終端処理に従う。
- `AUTO_FIX`: 枠待機は合成処理を待つ時間であり、既存の5秒のWebSocket書込み期限と区別する。新しい性能値や固定の枠待機期限は追加しない。試験は通知と同期で「8件の間は9件目が送られない」「最古の正常完了で進む」「取消・接続終了で全待機手が終了する」を観測し、既存試験用の期限は停止検出に使う。取消後の次要求のID連続性、欠落・重複の拒否、実WebSocket経由で全要求の正常終端も確認する。
- `AUTO_FIX`: 設計同期先は [音声パイプライン契約](../../../documents/design/contracts/audio-pipeline-websocket.md) と [RTC設計](../../../documents/design/backend/services/sincro-rtc.md) の上限制御・接続終了の説明とする。送信側の未完了要求上限と、出力側の未送信PCM上限を混同しない。通信の形式・要求ID・順序契約は維持する。
- `AUTO_FIX`: [失敗時の調査と継続](../../README.md#失敗時の調査と継続)を直接適用する。今回の変更による必須確認の失敗は、原因と証拠の記録だけでは完了・評価PASSにしない。原因を特定して最小修正と該当確認の再実行を行う。配備での再確認が失敗した場合の証拠保全と復旧は、配備タスクの手順に従う。
