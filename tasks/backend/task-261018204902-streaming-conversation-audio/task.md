# 会話音声を逐次合成・転送して生成完了前に再生する

## 背景・目的

ユーザーは、ストリーミング対応VOICEVOXの導入に続き、届いた音声から会話を再生する対応の起票・実行を求めている。
Engineは固定コミットで `/streaming_synthesis`を提供しているが、現在はPythonのVoiceSynthesizerがWAV全体を合成・変換してから
WebSocketへ返し、GoのRTC側も全体を復号してから再生キューへ載せている。
この全体待ちを解消し、キャッシュ未登録の長い応答でも音声生成完了前に返却音声の再生を開始する。

前提は完了済みの [Engine導入](../../infrastructure/task-261018200818-voicevox-streaming-engine/task.md)。
外部APIは導入せず、管理下のEngine・Python・Go/Pion・ブラウザーの既存経路を使う。

## 完了条件

- [x] 通常の会話経路がEngineの段階拡大合成を使い、全WAV受信・音声変換・キャッシュ保存の完了を待たずに音声区間をGoへ送る。
- [x] Goが受信区間を順次再生し、長い未登録入力で最初の有効音声がEngine生成完了前にPion出力へ届くことを、実Engineと本番用アダプターを使って確認する。
- [x] 区間の順序、同じ発話内の複数テキスト増分、先頭・末尾・完了を区別する。欠損・重複・逆行・途中切断・不正形式を成功した完全音声として扱わない。
- [x] 初期バッファと不足時の再バッファを設け、生成が遅れたときにPCMを飛ばしたり重複させたりしない。メモリー・キューに上限を設け、待機中も取消・世代更新・終了が進む。
- [x] 48kHz・モノラル・20msの連続Opusトラックとテロップ契約を保ち、音声サンプル位置に対応するモーラ・テロップを送る。区間境界で発話時刻や同じモーラの先頭を不必要にリセットしない。
- [x] 完成した音声だけをキャッシュへ保存し、途中失敗・取消時に不完全なエントリーを作らない。キャッシュ命中時も同じ再生経路を使い、既存データを削除しない。
- [x] 切断、HTTP失敗、受信途中の取消、再初期化でHTTP応答・スレッド/タスク・Goの状態・未送信音声を回収し、旧世代の音声や口形を後続へ混ぜない。
- [x] Python生成側とGo利用側、固定データと対象試験、現在設計を同期し、独立評価・必要な結合確認・全体ゲートを完了する。

## 設計と範囲

Python側はEngineへ48kHzモノラルのWAVを要求し、HTTPの任意の読取境界からWAVヘッダーとPCMを検証して区間へ切り出す。
生成区間は既存Engineの `segment_length=0.3` / `max_segment_length=2.4`を基準とする。
Goへの転送は全体のOpusファイル化を挟まずPCMを使い、既存のPion出力で20msごとにOpus符号化する。

WebSocket / MessagePackは区間転送への意味変更を含むため、破壊的変更として明記し、PythonとGoを同時に更新する。
区間には接続内の合成要求を区別する識別子、発話ID、順序・サンプル位置、完了情報、再生用メタデータを持たせる。
メタデータの詳細な形式と既存DTOの共有範囲は、既存の完全音声・診断再生との責務を踏まえて実装時に確定する。
接続内の要求IDは音声化対象のテキスト増分ごとに割り当て、区間の完了と会話応答全体の完了を区別する。
現在の一要求ずつの処理順を保ち、完了時に連続したサンプル範囲と総サンプル数を照合する。
既存の要求送信・結果受信件数も区間数へ置き換えず、要求単位で数える。

再生キューは合成要求ごとの状態を所有する。音声不足中は連続トラックの無音を送るが、発話内サンプル位置やモーラを進めない。
固定の待機だけで無音中断を完全に防げるとは扱わない。初期・再開のバッファ量はEngineの区間長と実測を根拠に決め、
既存の120秒・8発話などの上限と整合させる。処理遅延による既存の発話中止と受信不足を混同しない。
未完了区間の20ms未満の端数は次区間へ持ち越し、完了が確定した末尾だけを無音で埋める。
世代更新・終了と区間追加を同期させ、遅延で中止した要求への後続区間も再生キューを復活させない。
Pythonの接続所有者は合成用スレッドと有限長の区間受渡しを回収してからHTTP・キャッシュクライアントを閉じる。

発話内の時刻基準は合成要求先頭からの48kHzサンプル位置、連続トラックの時刻基準は既存の出力時計とする。
バッファ不足時にもトラック時計は進め、発話内の位置だけを停止する。処理時間・取消待機は各処理の単調時計で測り、
実結合の前後比較ではプロセス間の時計と観測点の対応を記録する。

キャッシュは完成した音声を保持する既存形式を基本とする。逐次受信用PCMの保存に別キーや形式が必要なら、
旧エントリーを削除せず、採用理由・命中条件を設計へ明記する。中断した要求の保存を成功扱いしない。

主な対象は `sincro-models`、`voice-synthesizer`、`sincro-rtc/internal/pipeline`、`internal/media`、`internal/rtc`と関連試験。
ブラウザーは既存の連続音声トラックを受けるため、不要なUIや別再生経路を追加しない。
既存フロントのテロップ受信処理との整合を確認し、公開スキーマを変える必要がある場合だけ同時更新する。
LLMの生成方式、GPU対応、全体のデプロイ、GHCR公開は対象外。

## 作業経路・失敗時

通信契約と複数の生存期間を変更する高リスク作業として、専用ワークツリー、独立仕様レビュー・実装評価を使う。
実環境確認は専用Composeと隔離キャッシュを基本とし、本体の停止・設定やユーザーの未コミット辞書を変更しない。
Docker操作は管理ルールの容量確認と作成物追跡・後片付けを行う。
失敗時は入力条件、順序、時刻、終了値と関連ログを音声・本文の公開を避けて保存し、原因修正後に対象確認をやり直す。

## 確認方法

- Python: HTTPの細切れ読取、先頭区間の早期配送、WAV完全性、完了時だけの保存、キャッシュ命中、取消・途中失敗、送信停滞を対象試験で確認する。
- Python / Go: 区間モデルの固定データをPythonで生成し、Goの厳格な復号・順序検証と突き合わせる。
- Go: 生成完了前の出力、初期待機・不足・再開、最終端数、複数要求、世代破棄、上限、遅延中止、モーラ時刻を決定的な試験で確認し、変更した並行処理にrace検査を行う。
- 実結合: 実Engine→実PythonのWebSocket→Go/Pion出力で長い未登録入力を一度確認する。最初の非無音PCM/Opus出力と合成完了の時刻を記録する。生成速度の数値目標や全負荷条件の再現は求めない。
- 既存のフロント受信契約を確認し、必要ならブラウザーで再生・口形を確認する。ブラウザー操作には `playwright-cli`を使う。
- 対象のRuff/型検査、Go vet/test/race、Markdown整形、タスク整合と `npm run gate`を行う。対象外の既存失敗は規約に従って分離する。

## 実装・確認結果

`VoiceSynthesizerChunk`へ通信を切り替え、生成途中のPCMをGoで順次再生する実装を追加した。
300msの初期・再開バッファ、端数保持、要求順序検証、世代破棄、正常完了時だけのキャッシュ保存を実装した。
実Engineの音素フレーム丸めと口形時刻を揃え、再バッファ後のフロント口形復帰も修正した。

実結合では25.12秒分の音声を対象に、最初の有声音739ms、HTTP受信完了より6,226ms早い出力を確認した。
HTTP EOFはEngine内部の生成完了時刻とは区別している。数値と再現手順は [確認記録](artifacts/verification.md)、
採用判断・検査・制約は [実装記録](impl.md) に記録した。

Python/Go/フロントの対象試験、Go race/vet、固定データ一致、中央ログ実結合、全体ゲートはPASS。
ブラウザーでの聴取・描画、全体デプロイ、イメージ公開は行っていない。

独立評価は [eval.md](eval.md) のとおりPASS。検証用のコンテナ・ネットワーク・空の匿名ボリュームは回収済み。
