# Opus音声と合成情報を使うRTCループ再生モードを追加する

## 背景 / 目的

マイク入力の内容に左右されず、下流サービスなしでRTCの返却音声・テロップ・口形同期を検証したい。
ユーザーはchat／sincroと同じ選択メニューから利用し、適当なディレクトリへ用意したOpus音声と音声合成クエリJSONのセットを再生する構成を希望している。
[echoと共通診断経路](../task-261011233435-rtc-echo-mode/task.md)に依存し、そのセッション単位の切り替えと終了処理を再利用する。

起票時のHEADは`f9b20e65`。既存の合成サーバーはOgg Opusを出力し、RTCの`synthdecode`は`audio/ogg;codecs=opus`をFFmpegで48 kHzモノラルPCMへ復号できる。
Goの送信処理はクエリ自体ではなく`mora_queue`から作った時刻情報を利用するため、素材JSONにはクエリと合成結果の付帯情報をまとめる。

## 完了条件（受け入れ条件）

- [x] メニューに「サンプル音声を繰り返す」を追加し、`talk_mode=playback`で利用できる。設定保存・復元、`talkMode`パラメーター、初回Offer、ICE再接続を同期する。
- [x] 同じRTCプロセスでchat／sincro／echo／playbackをセッション単位に選べる。playbackでは下流の探索・接続・再試行を行わず、起動時のモード指定を要求しない。
- [x] 規定ディレクトリにあるOgg Opus音声とJSONを読み込み、返却音声・口形・テロップを繰り返し再生する。配布可能な短いサンプル1組と準備・差し替え手順を用意する。
- [x] 初回利用時に素材を検証・復号し、成功した素材をメモリーに保持する。毎周回FFmpegを起動しない。
- [x] セッションごとに再生位置を持ち、周回ごとに`speech_id`を更新してテロップ時刻を先頭へ戻す。RTP送信時計は継続し、ループを無制限にキューへ先積みしない。
- [x] 既存の`text_ch`／`telop_ch`と共通の音声送信処理を使用し、固定文の表示と音声・口形同期を確認できる。周回するだけで同じチャット本文を履歴へ無制限に追加しない。
- [x] 素材の欠落、破損、JSON不正、音声長とモーラ時刻の不整合はplayback開始の明確な失敗として利用者へ伝える。プロセス起動とchat／sincro／echoを失敗させず、下流や別音声へ自動代替しない。
- [x] マイク・VADの入力経路と診断時の自動ミュート抑止はechoタスクの方針を維持する。入力音声はループ再生内容に影響せず、入力の読み取りを滞留させない。
- [x] 停止時に当該セッションの再生処理と待機を終了し、他セッションの再生・共有素材へ影響しない。
- [x] 素材配置をローカル実行と配布イメージで同期し、設計・手順と確認結果を記録する。

## 素材と公開契約

保存先は`sincromisor-server/sincro-rtc/assets/playback/default/`とし、`voice.opus`と`synthesis.json`を1組とする。
`voice.opus`はOggコンテナのOpus音声とし、JSONの`audio_format`は`audio/ogg;codecs=opus`とする。
JSONは既存の合成結果を基に`message`、`query`、`mora_queue`、`speaking_time`、`audio_format`を保存する。`voice`のバイナリと実行時の`speech_id`は含めない。
`query`は合成に実際に使用した値を保存し、加工前のクエリと完成音声を混在させない。

素材の供給元はリポジトリの上記ディレクトリ、消費先はRTCプロセス内の素材読み込み処理とする。
初期対応は既定の1組だけとし、OfferにファイルパスやURLを追加しない。任意ファイル取得・アップロード・素材選択APIは作らない。
実行時の規定配置と解決規則をREADMEで定め、Dockerイメージへも同じセットを配置する。モード切り替えの起動引数や必須環境変数は新設しない。
差し替えた素材の反映はプロセス再起動でよく、動的な再読み込みは要求しない。

`talk_mode`への値追加は公開通信契約の破壊的変更として明示し、フロント・サーバー・契約を同時に更新する。
既存のHTTPパス、DataChannel名と送受信JSONの形は維持する。

## 実装方針と生存期間

- `synthdecode.Decoder`で素材を既存の合成結果に適合させて検証・復号し、共通の出力処理へ渡す。OpusパケットをRTPへ直接流す専用経路は作らない。
- 検証済みPCMとモーラ情報はプロセス内で変更しない共有素材とし、再生位置、発話ID、送信待ちと中断はセッションが所有する。共有読み込み中の1セッション終了で他の利用者を失敗させない。
- 周回開始時にモーラ時刻を0起点とし、終了済み周回のテロップが次周回へ混入しない。音声の先頭・末尾の無音を含む時刻整合は既存の復号検証に従う。
- `text_ch`ではサンプルの文章をセッション開始時に1回表示し、周回中の表示と口形は`telop_ch`で更新する。ユーザーの認識結果は作らない。
- 素材の検証失敗はセッション終了とUIのエラー通知に結び付ける。通常経路と同じ下流再接続待ちへ入れない。
- FFmpegとOpusの既存依存を維持する。素材生成時にローカルの合成サービスを利用しても、再生時には必要としない。

## 主な変更範囲

- `sincromisor-server/sincro-rtc/internal/rtc/`、`internal/signaling/`、診断経路の実装: モード、読み込みと再生、失敗・終了処理。
- 同`internal/media/synthdecode/`、`internal/media/output/`: 既存の復号・検証・時刻付き出力の再利用。
- 同`assets/playback/default/`と素材の準備処理・説明、`Docker/sincro-rtc/Dockerfile`: ファイル形式と実行時配置。
- `sincromisor-server/voice-synthesizer/src/voice_synthesizer/VoiceSynthesizer/VoiceSynthesizer.py`: 素材書き出し時に再利用する合成結果・クエリとモーラ情報の参照先。Goへクエリ解釈を重複実装しない。
- フロントの設定メニュー、保存スキーマ、ページ初期値、RTC接続と診断表示: echoタスクで作った経路へplaybackを追加する。

## スコープ境界

既定素材1組のループ再生と表示同期を完成させる。複数素材の選択、再生速度調整、マイク不要接続、ファイルの動的更新、ブラウザーVADへの素材注入は含めない。
サーバーからの再生音声はブラウザーの入力VADを通らない。VADゲートの直接確認はechoで行い、playbackは返却経路・表示同期とスピーカー再生中のマイク側挙動の確認に使う。

## 確認方法

- Goの対象試験で素材の正常読み込みと欠落・破損・時刻不整合、複数周回の発話IDと時刻、有限キュー、共有素材と各セッションの終了の分離を確認する。先行タスクのechoと通常経路の関連試験も実行する。
- Pionの実接続で2周以上の非無音音声と`text_ch`／`telop_ch`の送信、連続する送信時計、停止後の解放を確認する。下流接続を呼ばないことも確認する。
- フロントの対象試験で新しい値の保存・復元・Offer伝播と失敗表示を確認し、ルートの`npm run gate`を実行する。
- 下流とConsulを起動しない開発環境で、メニューからplaybackを選び、2周以上の音声・テロップ・口形と停止・再接続をブラウザーで確認する。Playwright CLI規約とスキルに従う。
- 配布イメージの素材配置と読み込みを対象確認する。今回の変更による必須確認の失敗は修正後に再確認し、未確認のまま完了しない。

## 実行時に補完する事項

サンプルの文章・話者は未指定であり、公開可能な短い音声を採用し、出典・利用条件・生成方法を記録する。実ユーザーの録音は使わない。
素材は現時点で提供されていないため、実装時に適法に配布できる既存素材または管理下の合成環境で生成したセットを用意する。無音や適当なモーラを当てた音声で同期確認を代替しない。
内部の読み込みAPIと規定配置の解決方法は、既存の起動・配布方法に合わせて自律補完する。

## 実行結果

`talk_mode=playback`をメニュー・保存・URL・Offerへ追加し、共有素材の検証とセッションごとの有限ループ再生を実装した。
VOICEVOX:ずんだもんによる約4秒の配布素材と実合成クエリ、生成・差し替え手順を追加した。

Goの対象race試験、フロント全体ゲート（685件成功、3件skip）、Pionの複数周回・セッション終了分離、ブラウザーの音声・テロップ・口形・停止再接続、Dockerイメージの素材配置・復号・Offer成功を確認した。素材欠落時のHTTP 422と画面エラーも確認した。
独立評価はPASS。契約・設計・コメントを同期した。
Go全体試験で残った対象外の2パッケージの失敗は変更前でも再現した。追加依頼で原因を調査して解消し、Go全体のrace試験も成功した。詳細は[実装記録](impl.md)に記す。
