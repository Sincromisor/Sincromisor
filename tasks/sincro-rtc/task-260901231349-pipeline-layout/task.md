# 会話パイプラインの実装と試験を責務別に整理

## 背景 / 目的

`internal/pipeline` 直下は本番1,248行・試験2,226行で、`coordinator.go`（352行）、`coordinator_test.go`（1,071行）、`websocket_integration_test.go`（739行）が大きい。`client` にも500行超の試験と、公開境界・処理担当の英語コメントが残る。一方、`client`、`discovery`、`protocol` という既存の子パッケージ境界は実責務に沿っている。

## 完了条件（受け入れ条件）

- [ ] 既存の `pipeline` / `client` / `discovery` / `protocol` 境界を維持し、直下の `Coordinator` の構築・実行時設定・生存期間処理を責務別ファイルへ整理する。
- [ ] `coordinator_test.go` とWebSocket結合試験を状態遷移、キュー、再初期化、終了、固定データ処理・補助コードの観点へ分け、試験名から対象責務を追える。
- [ ] `client` の大きな試験と `set.go` / `connection.go` を既存の接続・送受信・終了責務に沿って整理する。
- [ ] 非公開状態を検証する試験は同じパッケージに残し、試験移動のために本番要素を公開しない。
- [ ] 世代、再初期化、キュー、WebSocket、処理担当、終了順序のコメントを日本語へ統一し、公開要素と変更理解範囲の不足を解消する。
- [ ] 下流4サービスのMessagePack、再接続、履歴、キュー満杯時の既存契約が変わらない。

## 設計判断

既に有効な子パッケージをさらに細分化しない。試験ファイルの数ではなく、本番責務との対応と補助コードの局所化を優先する。

## スコープ境界

対象は `internal/pipeline` と既存子パッケージのGoコード・試験である。下流Pythonサービス、契約固定データの内容、再試行値は変更しない。

## 実装方針

ファイル移動とコメント是正を中心にし、`Coordinator` や `ClientSet` の公開形は維持する。既存固定データを再利用し、新しい試験枠組みを追加しない。

## テスト

`go test ./internal/pipeline/...`、`go test -race ./internal/pipeline/...`、`go test ./...` を実行する。

## ドキュメント同期の要否

WebSocket契約は不変のため契約文書の仕様変更は不要。パッケージコメントと後続責務図を実配置へ合わせる。
