# レビュー: task-261011233435-rtc-echo-mode

## 判定

APPROVED

## 理由・申し送り

- 下流サービスを使わずにRTCの音声往復とブラウザー側VADを確認したいという要求に対し、`talk_mode=echo`、メニュー、設定保存、Offer、ICE再接続、診断表示を一貫して対象にしている。現在のフロントエンド保存スキーマ、Offer送信、サーバー側の許可値、更新Offerの同一モード検証と整合する。
- 公開RTC契約の許可値追加として、フロントとサーバーの同時変更、初回Offerと更新Offer、DataChannelと返却音声の契約文書を同期対象にしている。HTTPパス、DataChannel名、音声形式を維持する範囲も明確である。
- 既存の入力は16 kHzモノラルPCM、返却音声は48 kHzモノラルPCMを20 ms単位で送る。既存の出力時計と無音送信を再利用し、連続PCMだけを上限付きで保持して古い音声を破棄する方針は、診断目的と遅延を蓄積しない安全性の根拠に合う。容量と再サンプリング方式は既存実装に合わせて決められる実装詳細である。
- 高リスクとなるセッションの所有権と終了は、診断処理・送信バッファ・再サンプリング状態をセッション所有とし、停止・失敗時に中断と終了待機を完了して別セッションへの送出を防ぐ、と定めている。現在の `Session` の非同期cleanup、全resource join後のregistry除去、入力・出力処理の境界と矛盾しない。実装ではecho処理を既存のcleanup対象へ加え、通常経路だけがCoordinatorをcloseする所有境界を保つこと。
- 必須確認は対象Go試験、Pion実接続での返却と複数セッション分離、フロント対象試験、下流・Consulなしの開発環境での一度のブラウザー確認に絞られている。根拠のない性能値、長時間試験、環境組み合わせは必須化していない。今回の差分による必須確認の失敗を記録だけで完了させない条件も明記されている。
- スコープ、後続playbackとの分割、同期文書、コメント規約の直接適用が明確であり、コメント規約をtask.mdへ複製していない。題名と本文はMarkdown規約に沿う日本語で書かれている。

## 自律補完

- `AUTO_FIX`: echo用の入力受け渡しと出力キューの内部型、PCM保持上限、16 kHzから48 kHzへのストリーミング再サンプリング、診断表示の具体的位置は、既存の入力・出力・設定UIの実装に合わせて決める。いずれも公開契約、要求結果、セッション終了安全性を変更しない実装詳細である。
