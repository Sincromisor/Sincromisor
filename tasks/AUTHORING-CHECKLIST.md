# タスク起票チェックリスト（`task-reviewer` 評価観点の正本）

このファイルは **起票するエージェントの自己点検項目** であり、同時に **`task-reviewer` の評価観点の
正本**でもある。両者が同一の基準を共有することで、初回 `NEEDS_REVISION` の往復を減らすのが狙い。

> 使い方（`/new-task` フロー）: タスク立案は「対話による調査・検討」で行い、`/new-task タイトルまたは要約`
> を呼ぶ。**対話文脈を持つそのセッション自身が**雛形（`npm run tasks:new`）を起こし、本チェックリストの
> 観点で `task.md` を記述する。続けて **レビュー専用サブエージェント（task-reviewer、独立セッション）** が
> `task.md` 単体を独立レビューし、`NEEDS_REVISION` なら起票したエージェントが改訂・再レビューする
> （レビュー担当は `task.md` を書き換えない）。APPROVED 済みを `/run-task` に渡す。
> ライフサイクルの位置づけは [README.md](./README.md) の「起票フロー」を参照。

各観点は `task-reviewer` が **NEEDS_REVISION 判定の根拠**にする。起票時に潰しておくほど初回で通る。

## 1. 要件の明確さ（受け入れ条件が曖昧・欠落していないか）

- [ ] 完了条件が **検証可能な形**で書かれている（「〜を改善する」ではなく「〜のとき〜を返す」）。
- [ ] 各完了条件の **期待値が一意**に定まる（複数解釈の余地・「いずれか」が残っていない）。
- [ ] 異常系・境界（空入力 / 欠損 / 上限超過など）の期待挙動が定義されている。

## 2. 設計判断を着手前に確定（最頻出の NEEDS_REVISION 根拠）

実装者に「どちらでもよい」を残さない。選択肢があるなら起票時に **1 つに決め切り、根拠を書く**。

- [ ] 新規に導入する型・モジュール・データ構造の **所在（ファイルパス）と最小スキーマ**を明示した。
- [ ] 既存 API / データ表現に複数の解釈余地がある箇所（フォーマット・識別方式・経路）を
      **どれを採るか**確定し、不採用案を退ける理由を 1 行添えた。
- [ ] 外部境界（ネットワーク / 外部 API / LLM / DB など）の入力検証・失敗時挙動の方針を示した。

## 3. 既存コードベースとの整合性（file:line で裏取り）

- [ ] 触る既存箇所を **`file:line` で参照**し、前提（行番号・シグネチャ・契約）が現状と一致することを確認した。
- [ ] 矛盾する前提・命名・依存がない（プロジェクトの規約・設計資料
      〔`AGENTS.md` / `README.md` / `documents/design/` / `documents/rules/` / `tasks/README.md`〕と整合）。
- [ ] 過去タスクから引きずった **陳腐化した前提**（存在しないファイル・廃止 API）が残っていない。

## 4. スコープと責務分界（過大・過小でないか）

- [ ] スコープが過大／過小でない（1 タスク = 追跡可能な 1 つの変更束）。
- [ ] 依存タスクがある場合、**本タスクの作業と依存タスクの責務の境界**を明示した
      （「この拡張は本タスクで足す / 依存タスクが残した余地に乗る」を曖昧にしない）。
- [ ] スコープ外（やらないこと）を列挙した。

### 4.1 高リスク統合タスクだけに追加する確認

次のいずれかを含むタスクは「高リスク統合タスク」として扱う。通常の局所変更へこの追加確認を
一律適用しない。

- 複数のリソース所有者、非同期処理、状態機械を同時に変更する。
- HTTP / WebSocket / WebRTC / プロセス / 保存領域 / ブラウザー API など、複数の外部境界をまたぐ。
- 再試行、時間切れ、時刻、キュー、逆圧、安全な終了の複数を組み合わせる。
- 「すべてのコールバック」「厳密に 1 回」「同一順序」「全リソースの収束」などの全称条件を持つ。
- フェイク・モック内の状態だけでなく、本番用アダプター後の観測可能な出力が合否を左右する。

該当する場合だけ、次を確認する。

- [ ] 独立して検証可能な変更束へ分割できないか検討し、分割しない場合は、同一変更にする必要性を
      task.md に記録した。
- [ ] タスクに関係する不変条件を、対象に応じて所有権、生存期間、操作 × エラー、
      時刻・単位変換、イベント × 観測者のいずれかの表、または同等に機械照合可能な形で固定した。
      第 3 段階固有の表を全タスクへ要求せず、実際に存在するリスクだけを選ぶ。
- [ ] 全称条件は対象一覧と所有者を列挙した。「全て」とだけ書いて実装時の探索へ委ねていない。
- [ ] 各受け入れ条件について、少なくとも「検証層」「本番環境での観測点または状態」
      「一意な期待値」を対応付けた。テスト名は既存命名規則から一意に決められる場合だけ固定すればよい。
- [ ] フェイク・モックと本番用アダプターの意味が異なり得る場合、単体テストだけで完了せず、
      ローカル結合テスト、実アダプター、契約用固定データのいずれで対応を確認するか明記した。

直接依存タスクが未完で、その実装がコンストラクター、リソースの所有権、通信契約、状態機械、
時間切れ・時刻、本番環境向けテスト接続点を確定する場合は、後続タスクを先に APPROVED にしない。
依存実装に左右されない契約だけで完結するタスクは、この限りではない。

## 5. テスト可能性

- [ ] 各受け入れ条件に対応する **検証方法**（プロジェクトの 3 点ゲート: lint / 型・ビルド / テスト。
      まとめて `npm run gate`）が書かれている。
- [ ] テストの **期待値が一意**（観点 1 と対）。終端・分岐の網羅が条件化されている。
- [ ] 単体テスト、所有者間の結合テスト、本番用アダプターのどこまで必要かを変更リスクに応じて判断した。
      通常の局所変更へ不要な結合テストを一律要求しない一方、外部境界後の観測可能な出力を
      単体テスト用フェイクだけで証明したことにしない。

## 6. ドキュメント同期の要否（重大な指摘になりやすい）

公開 API / 通信契約 / 公開挙動を変えるタスクは、対応ドキュメント（API スキーマ / 利用例 / README /
設計資料など）の同期を **受け入れ条件として明記**する（lint / 型 / test で検出できない領域。漏れは
レビュー担当の重大な指摘になりやすい）。

- [ ] 公開 API / 通信契約 / 公開挙動への影響を判定した。
- [ ] 同期が **要**なら、同期先ドキュメントを **具体名**で受け入れ条件に書いた。
- [ ] 同期が **不要**なら、その理由（内部クローズドな変更等）を 1 行書いた。
- [ ] 公開バレル / 生成物（型定義・ビルド成果物など）を変える場合、その再生成とコミットを方針に含めた。

## 7. ソースコードコメント品質（本番コード）

本番コードを変更するタスクは、[documents/rules/source-comments.md](../documents/rules/source-comments.md) と
対象言語の `documents/rules/coding-*.md` に照らしたコメント点検・コメント受け入れ条件を `task.md` の
受け入れ条件へ含める。対象変更なのにコメント観点が無い場合、task-reviewer は受け入れ条件不足として指摘する。
公開 API と非自明な制約は必須の下限であり、調査時の理解支援を含めて対象と期待値を定義する。

- [ ] 本番コード変更の有無を判定した（テスト、固定データ、生成コード、文書のみなら対象外理由を書いた）。
- [ ] 公開 API、境界、スキーマ・構文解析、経験則・生存期間に加え、処理の組み立て・処理工程、
      状態遷移、イベント発生元、データ変換、非局所的な接続関係を追加または変更するか確認した。
- [ ] 変更したシンボル・処理群・判断・流れと、その変更を理解するために読む直接の補助関数、状態、
      イベント、生存期間、データ変換を変更理解範囲として受け入れ条件に含めた。
- [ ] 対象がある場合、`パス`、`シンボル・処理群・判断`、`種類`、`現在のコメント`、`読者の疑問`、
      `読者に必要な知識`、`判断`（`維持` / `書き直し` / `削除` / `追加`）、
      `対応または省略理由`、`レビュー担当者メモ` を含む点検表を受け入れ条件に含めた。
- [ ] 対象がある場合、docstring / JSDoc / TSDoc / Go の文書コメントと実装コメントの追加・更新だけでなく、
      弱い既存コメントの削除・書き直し条件を受け入れ条件に含めた。
- [ ] 公開 API の目的、契約、入力境界、戻り値、失敗条件、副作用、非対象のうち、
      変更対象に必要な情報を task acceptance に定義した。
- [ ] 内部処理の流れ、状態変化、データ表現、前後関係、後段へ委ねる責務のうち、
      読者が局所的に理解するために必要な情報をタスク受け入れ条件に定義した。
- [ ] ファイル・モジュールコメントへ集約する場合、対象シンボルと処理の流れの入力、出力、失敗条件、副作用、
      前後関係を具体的に覆い、責務要約だけで完了できない条件を定義した。
- [ ] コメントを省略する対象がある場合、横断規約の省略条件を満たす具体的な理由を
      受け入れ条件または実装ログ記録条件に含めた。
- [ ] `private`、`短い`、`型がある`、`testを読めば分かる`、`既存コードにもコメントがない` を
      単独の省略理由として認めないことを明記した。
- [ ] 新規ファイル・シンボルは現行規約を完全に満たし、既存コードのコメント不足を前例にしない条件を含めた。
- [ ] 対象がある場合、実装と矛盾する 古いコメント の削除・更新を受け入れ条件に含めた。
- [ ] TODO を追加または変更する場合、TODO 必須情報（理由、削除条件、canonical task/issue ID、
      期限または判断基準）を受け入れ条件に含めた。
- [ ] コメントで補う前に、命名、関数分割、型定義、options object、module / package 境界で
      明確化できないかを確認し、構造改善だけを理由に 読者向けコメント を省略しない条件を含めた。
- [ ] コメント改善タスクが 10 ファイルを超える広域一括作業を要求する場合、原則として範囲分割する。
      分割できない正当な理由がある場合も、変更対象と変更理解範囲の一覧は
      全件作成し、固定件数の抽出確認だけで未確認対象を完了扱いにしない。リスクに応じて照合順を
      付けることはできるが、点検対象自体を省略しない。
- [ ] 評価時は変更した対象と変更理解範囲の全件照合を原則とし、広域変更では
      公開 API、境界、処理の組み立て、状態・データの流れ、書き直し・削除判断、定型的な点検理由の
      疑いがある箇所を優先した照合範囲、未照合範囲、残リスクを `eval.md` に
      記録する条件を含めた。
- [ ] 評価時の照合範囲で、逐語説明、確認先だけのコメント、失敗モードのない経験則コメント、
      内部処理の流れの理解困難、既存の無コメントを根拠にした省略、定型的な点検理由があれば
      FAIL にする条件を含めた。

## 8. 文書の言語

- [ ] 説明文、見出し、チェック項目、表の列名は、原則として一般的な日本語で書いた。
- [ ] コマンド名、ファイル名、設定キー、識別子、規格名、固有の状態値など、正確さや検索性のために
      原文を保つ必要がある語だけを英語で残した。
- [ ] 英語を残す場合も、日本語の助詞や語間へ不自然に挟まず、必要に応じて初出で意味を補った。
