# 別端末からの利用と分散配置

## 目的と経路の選択

管理下のサーバーを別端末から使う、または処理を複数ホストへ分けるためのガイドである。
HTTPS終端・証明書・必要なネットワークは管理者が用意する。特定のクラウドや有料サービスは必須ではない。
このガイドだけでVPNや証明書を新規構築するものではなく、実際の到達性は配置先で確認する。

| やりたいこと                                  | 読む手順                                                    |
| --------------------------------------------- | ----------------------------------------------------------- |
| 処理は1台のまま、スマートフォンや別PCから使う | [サーバー1台を別端末から使う](#サーバー1台を別端末から使う) |
| RTCの入口とGPUを使う下流処理を別ホストに置く  | [処理を複数ホストへ分散する](#処理を複数ホストへ分散する)   |

`localhost` と `127.0.0.1` は、それを開いた端末自身を指す。別端末へ渡すURLやメディアの接続先には使わない。
ブラウザー用の到達先と、Consul・下流APIの管理用到達先は別の役割であり、インターネット越しの配置では異なるIPになることがある。
設定名と公開ポートの定義は [設定例](../../examples/compose.env) と [Compose設計](../design/infrastructure/compose.md#公開ポートの選択) を参照する。

## サーバー1台を別端末から使う

### 1. HTTPSの入口を準備する

READMEの `full,chat` 構成を起動し、サーバー自身から `http://localhost:8086/` が開くことを確認しておく。
標準の [Caddy設定](../../configs/Caddyfile) はHTTPの80番だけを待ち受け、ホストの8086番へ公開する。HTTPSや証明書は含まれていない。
LAN内でも `http://サーバーのIP:8086/` を開くだけでは、マイク・カメラを使うための安全な接続条件を満たさない。

管理者が管理下のHTTPS終端で次を準備する。

1. 利用端末から名前解決・接続できるホスト名とHTTPSのURLを決める。
2. そのホスト名に有効な証明書を設定し、利用する各端末・ブラウザーが発行元を信頼する状態にする。自己管理の認証局なら、その信頼設定も端末側で済ませる。証明書警告を無視する運用にしない。
3. HTTPS終端からフロントへ、静的ファイルと `/api/` を含むパス全体を転送する。終端が同じホストのプロセスなら転送先は `http://127.0.0.1:8086`、別ホストなら終端から到達できるサーバーのアドレスと8086番を使う。終端がコンテナ内なら、その `127.0.0.1` は終端コンテナ自身なので使わない。
4. ブラウザーには同じHTTPSオリジンから画面とAPIを提供する。APIだけを別のHTTP URLへ誘導しない。ブラウザーへ渡すURLはこのHTTPSのURLとする。

フロントへのHTTP転送区間は管理下の経路に限定する。既存のHTTPS終端を使う場合も、転送先と証明書を管理者が確認する。

### 2. メディアのIPv4とUDPを設定する

サーバーのリポジトリルートにある `.env` の `SINCRO_PION_PUBLIC_IPV4` を、利用端末から届くサーバーのIPv4へ変更する。
次の山括弧は説明用であり、実際の値へ置き換える。

```dotenv
SINCRO_PION_PUBLIC_IPV4=<利用端末から届くサーバーのIPv4>
SINCRO_PION_MEDIA_UDP_PORT=3479
```

LANだけで使うならサーバーのLAN IPv4でよく、インターネット上の公開IPは不要である。
既定の `127.0.0.1` のままでは別端末のメディアは届かない。HTTPS終端が別ホストでも、この値はRTCのメディアへ到達するIPにする。
単一ホストの `SINCRO_PION_SERVICE_BIND_HOST=sincro-rtc` やConsul設定はそのままでよく、別端末利用だけのために分散用Composeを追加する必要はない。

ブラウザーからRTCホストのメディアUDPへ到達できるよう、ホスト・ルーター・ネットワークの制限を確認する。
標準は3479番で、変更する場合は `.env` の値と許可するUDPポートを揃える。NATを経由する場合は広告先IPv4と同じUDPポートをRTCホストへ転送する。
HTTPSのTCP通信だけを通しても音声通信は成立しない。

現在はIPv4・UDPでの直接接続が前提で、TURNは未対応である。STUNを指定するだけではUDP遮断やNATの制約を解消できない。

### 3. 設定を反映する

利用中の会話を終了し、サーバーのリポジトリルートでRTCを再作成する。

```sh
docker compose config --quiet
docker compose up -d --no-deps sincro-rtc
docker compose ps sincro-rtc
```

`restart` だけでは `.env` の変更は反映されない。HTTPS終端の反映は、その管理手順に従う。

### 4. 別端末から確認する

1. 利用端末で用意したHTTPSのURLを開き、証明書警告がなく画面が表示されることを確認する。
2. 同じHTTPSのURLの末尾へ `/api/v1/RTCSignalingServer/statuses` を付け、APIの応答が返ることを確認する。
3. 会話画面でマイク・必要なカメラを許可して開始し、接続、認識された文字、応答音声を確認する。

画面が表示されてもメディア到達性までは確認できていない。実際の短い会話まで通す。
Mastra Studioの4111番とログ検索の9428番は、一般利用者向けに転送・公開しない。

## 処理を複数ホストへ分散する

### 1. 役割と管理ネットワークを決める

既存構成では、RTCホストが画面とWebRTCの入口を担当し、GPUのある下流ホストが音声処理・会話生成を担当する。
両ホストを管理LANまたは管理VPNで相互接続しておく。以下のコマンドは、それぞれのホストのリポジトリルートで実行する。

| 配置先                                  | `.env` のプロファイル                | Composeファイルと役割                                                                                                                                                   |
| --------------------------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RTC専用ホスト                           | `COMPOSE_PROFILES=rtc`               | `compose.yml:compose/distributed.yml:compose/management.yml`。RTC同梱フロントと収集を起動し、ホストのHTTPS終端からループバック8001番へ転送する。                        |
| 下流・中央ログのホスト                  | `COMPOSE_PROFILES=backend,chat,logs` | `compose.yml:compose/distributed.yml`。Consul、下流4サービス、依存先、AgentServer・LLM、中央ログを起動する。管理APIを使う場合だけ `compose/management.yml` も追加する。 |
| 下流とローカルの画面・RTCを兼ねるホスト | `COMPOSE_PROFILES=full,chat`         | 下流と同じ追加ファイルを使う。ローカルRTCも広告する場合は、そのホストのメディアIPv4を設定する。                                                                         |

中央ログは1台だけに置く。RTC専用ホストへ `frontend` や `logs` を追加しない。
TextProcessor・AgentServer・LLM、音声合成・Redis・S3・VOICEVOXは、この手順では下流ホストに同居させる。
これらをさらに分割するための接続・認証変更は、この既存配置の手順には含めない。

### 2. ホストごとの設定を揃える

既存 `.env` を上書きせず、役割に必要な差分を反映する。`COMPOSE_FILE` は表のファイル一式をLinuxの `:` 区切りで指定する。
イメージ固定などの既存追加ファイルがあれば、その選択も維持する。

| 設定                            | RTCホスト                   | 下流ホスト                                        |
| ------------------------------- | --------------------------- | ------------------------------------------------- |
| `SINCRO_CONSUL_PUBLISH_HOST`    | RTCホストの管理IPv4         | 下流ホストの管理IPv4                              |
| `SINCRO_CONSUL_ADVERTISE_ADDR`  | RTCホストの管理IPv4         | 下流ホストの管理IPv4                              |
| `SINCRO_CONSUL_SERVER_HOST`     | 下流ホストの管理IPv4        | 同居する `sincro-consul-server`                   |
| `SINCRO_PION_SERVICE_BIND_HOST` | RTCホストの管理IPv4         | ローカルRTCも使う場合は下流ホストの管理IPv4       |
| `SINCRO_PION_PUBLIC_IPV4`       | ブラウザーから届くRTCのIPv4 | ローカルRTCも使う場合は、その利用端末から届くIPv4 |
| `SINCRO_LOG_HOST`               | 例: `rtc-example`           | 例: `backend-example`                             |

下流側では `SINCRO_EXTRACTOR_PUBLIC_BIND_HOST`、`SINCRO_RECOGNIZER_PUBLIC_BIND_HOST`、`SINCRO_PROCESSOR_PUBLIC_BIND_HOST`、`SINCRO_SYNTHESIZER_PUBLIC_BIND_HOST` も下流ホストの管理IPv4へ揃える。
これらは別ホストへ知らせる接続先であり、コンテナ内の待受アドレス `0.0.0.0` を置き換える設定ではない。
ホスト識別子は全ホストで一意にする。各ホストの [journal準備](logging.md#起動前にjournalを準備する) と時刻同期も済ませる。

管理ネットワークでは、RTCから下流APIのTCP 8002〜8005、中央ログのTCP 9428へ到達できるようにする。
ConsulサーバーのTCP 8300・TCP/UDP 8301と、各ホストの担当エージェントのTCP/UDPも相互到達が必要である。
担当ごとの8311〜8321番は [Consulの接続設定](../design/infrastructure/consul.md#複数ホストの接続設定) に従う。
管理サービスは参加ホストに限定し、インターネットへ直接公開しない。中央ログの9428番には検索APIも含まれる。

### 3. 下流から順に反映する

下流ホストは [ローカル開発の初回準備](../design/infrastructure/local-development.md#初回準備) と [下流を兼ねる設定](../design/infrastructure/local-development.md#vpsの下流を兼ねる場合) に従い、構成確認・起動・準備完了を確認する。
RTC専用ホストは [VPS配備手順](../design/infrastructure/vps-deployment.md) に従い、ソースとイメージを揃えて反映する。この役割分担は管理下の別サーバーでも同じである。
各文書は日常開発または既存分散環境への配備・復旧の詳細を扱うため、ここではコマンド一式を複製しない。

RTC側のHTTPS終端は、画面とAPIを含めて `http://127.0.0.1:8001` へ転送する。これは `management.yml` を選んだ同じホストのプロセスからの転送先である。
証明書の信頼とブラウザー向けIPv4・UDPは、前節と同じ条件を満たす必要がある。

`--profile rtc` の追加だけでは、既存の `COMPOSE_PROFILES=full,chat` を置き換えられない。RTC専用ホストは `.env` 自体を `rtc` にする。
また、`-f` を指定すると `COMPOSE_FILE` の選択を置き換えるため、必要なファイルを省かない。

### 4. ホストをまたぐ接続を確認する

各ホストで `docker compose ps -a` を確認し、RTC側で `docker compose exec -T consul-agent-rtc consul members` により管理ネットワークへの参加を確認する。
メンバー一覧だけで下流の準備完了とは判断せず、Consulの各サービスのチェックがpassingかも確認する。
管理UI/APIを使う場合は下流ホストのループバック8500番へSSHなどの管理経路で接続する。

利用端末からHTTPSの画面とRTC API、短い会話の認識・応答音声まで確認する。
下流を兼ねるホストにも画面・RTCがある場合は、両方の入口を確認する。
中央ログで各 `host` の新着と収集・配送状態を確認する。下流ホストを止めると、RTCホストが動いていても会話生成と中央へのログ配送は利用できない。

## うまくいかないとき

| 症状                           | 確認すること                                                                                                                                                                    |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 画面が開かない                 | 利用端末の名前解決、HTTPS終端の待受・証明書・転送先を確認する。単一ホストのフロントは8086番、RTC専用ホストのホスト内転送先は8001番。別端末のlocalhostを開いていないか確認する。 |
| マイク・カメラを許可できない   | 信頼されたHTTPSか、ブラウザー・OSでそのサイトや機器を拒否していないかを確認する。HTTPのLAN URLや証明書警告の無視で代用しない。                                                  |
| 画面は開くが会話へ接続できない | 同じHTTPSオリジンでRTC APIが応答するか、`SINCRO_PION_PUBLIC_IPV4` とメディアUDPが利用端末から届くかを確認する。分散時はConsulの登録先・管理IP・下流APIの到達性も調べる。        |
| 接続後に応答がない             | 下流4サービスとAgentServer・LLMの準備完了を確認し、[ログガイド](logging.md)で会話IDを絞って失敗した処理を調べる。                                                               |

公開先やファイアウォールを無制限に広げて対処しない。Mastra Studio、ログ検索、Consul管理API、Redis・S3・VOICEVOXの公開制限は [Compose設計](../design/infrastructure/compose.md#公開ポートの選択) を維持する。
