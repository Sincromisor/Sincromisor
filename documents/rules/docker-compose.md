# Docker Compose管理ルール

## 目的と適用範囲

Docker Composeの構成変更、起動・停止、障害調査、保存領域の整理を行うエージェントは本書に従う。
対象は `compose.yml`、`compose/*.yml`、`examples/compose.env`と、それらを利用する操作手順である。
具体的な設定値・サービス配置は[Compose設計](../design/infrastructure/compose.md)、
データの保存・引継ぎは[保存領域設計](../design/infrastructure/storage.md)を参照する。

本書はインストール済みのDocker公式スキル `docker-compose-patterns`と
`docker-destructive-guardrails`を基に、Sincromisorの既存契約へ合わせた規約である。
スキルの一般例を理由に既存の配置・保存方式を置き換えない。

## スキルの使い分け

- Compose構成の作成・変更・起動障害の調査では `docker-compose-patterns`を読む。
- Composeのボリューム削除は同スキルの削除規則を使う。Compose管理外の削除やホスト全体の整理では `docker-destructive-guardrails`も読む。
- Dockerfileやビルド方法を変更する場合は `docker-build-strategies`、新しいプロジェクトのDocker構成を設ける場合は `docker-project-foundations`を使う。
- スキルはセッションの一覧から名前で探す。個人環境の絶対パスをリポジトリの手順へ固定しない。利用できない場合はその旨を記録し、本書と公式資料で確認できる範囲を進める。
- ユーザー要求とセッション内の許可を優先する。対象と影響が既に明示され、許可された操作について同じ確認を繰り返さない。

## 構成ファイルと変更範囲

- Docker Compose v2の `docker compose`を使い、リポジトリルートで操作する。`include`など利用中の機能を使えるバージョンか確認する。
- 入口は既存の `compose.yml`、サービス定義は `compose/*.yml`とし、ルートの `include`で組み立てる。スキルの推奨名 `compose.yaml`への改名や入口の二重化は行わない。
- 環境ごとの追加設定は既存の `compose/distributed.yml`、`compose/management.yml`と明示的なファイル選択に合わせる。開発用の追加設定が必要な場合も通常起動へ混入させない。Compose Watchは必要な開発用途がある場合だけ検討する。
- 操作前にDockerの接続先、Composeプロジェクト名、選択ファイル、プロファイル、対象サービスを確認する。プロジェクト名の変更は別のボリューム・ネットワークを作り得るため、単なる表示名の変更として扱わない。
- `-f`の指定は `COMPOSE_FILE`の選択を置き換える。追加ファイルだけを指定せず、必要な構成一式と順序を維持する。
- `include`先の相対パスはそのファイルのプロジェクトディレクトリを基準に解決される。複数の `-f`による上書きと混同せず、ファイル移動時はビルド・マウントの参照先を確認する。
- 変更前にサービスの利用側、Consul登録、死活確認、プロファイル、保存先、関連する検査を追跡する。変数の追加・変更は `examples/compose.env`、Compose、設定クラス、利用実装、設計を同期する。
- 配布設定を置いた後の `docker compose up`で起動できる契約を保つ。既存 `.env`をサンプルで上書きせず、設定名・公開ポート・保存方式の変更は移行方法と影響を記録する。

## サービスと起動依存

- サービス名は責務が分かる小文字とし、接続にはサービス名を使う。外部ツールの必要性がない `container_name`や固定コンテナIPを追加しない。
- 新規・更新する外部イメージは具体的なバージョンまたはダイジェストへ固定する。タグ省略や `latest`を新たな既定値にしない。
- 自前サービスの `pull_policy: build`とソースからのビルドを維持する。ローカルビルド用の既存タグは外部イメージの版固定と区別し、配布イメージを使う場合は[公開設計](../design/infrastructure/image-publishing.md)に従う。既存の未固定外部イメージを無関係な変更に便乗して一括更新しない。
- 常駐サービスを新設するときは原則 `restart: unless-stopped`とする。既存の `deploy.restart_policy`を変更する場合は再起動条件への影響を確認し、二重に指定しない。初期化処理は `restart: "no"`と正常終了待ちを使う。
- 接続先の準備完了が必要なら `depends_on`に `condition: service_healthy`を指定し、接続先へ `healthcheck`を定義する。初期化完了待ちは `service_completed_successfully`を使う。起動順だけで準備完了を保証しない。
- 各プロファイルで依存先と初期化処理も選ばれることを確認する。別ホストの依存先は `depends_on`では管理できないため、[Consul設計](../design/infrastructure/consul.md)と利用側の接続処理で扱う。
- データストアには死活確認を定義する。利用可能な標準クライアントや既存の確認処理を使い、プロセスの存在だけで準備完了としない。
- 死活確認の間隔・時間切れ・再試行・準備時間は対象サービスに合わせる。モデルの初回取得やGPUへのロードがあるサービスへスキルの例の秒数を機械的に転記しない。
- シェルや `curl`などは採用イメージに存在するものだけを使う。確認用の別コンテナは既存の確認方法で足りない場合に限り、起動・終了・監視の責務も定める。
- Composeの起動依存とConsulによる稼働中の監視を区別する。再起動や通信断への対処を起動時の死活確認だけへ任せない。

## 設定・秘密情報・公開範囲

- ルート `.env`によるComposeの変数展開と、コンテナへ渡す `environment` / `env_file`を区別する。`.env`に書くだけではコンテナへ渡らない。
- 必須値は利用する構成で未設定・空欄を拒否し、任意値だけに妥当な既定値を置く。未選択プロファイルの任意設定を理由に標準構成を使えなくしない。
- サンプルには秘密の実値を書かない。既存の認証初期化・専用ボリュームを使い、固定パスワードや追加の秘密配布経路を設けない。`env_file`も平文ファイルとして扱う。
- `.env`、生成トークン、会話・認識結果をGitや公開成果物へ含めない。秘密を含むファイルの読取り権限を制限する。
- `docker compose config`の全体出力や `config --environment`をログへ流さない。構文確認は `config --quiet`、一覧確認は必要な項目だけを出力する。警告・エラーやサービスログにも秘密が含まれ得るため、共有前に確認する。
- ホストへの `ports`は利用者・管理者・別ホストが必要とするものだけにする。管理用はループバック、分散用は設計で定めた管理IPへ限定する。内部通信のためだけに公開ポートを追加しない。
- 共有の `sincromisor-net`とS3の内部ネットワークを維持する。スキルの「通常は既定ネットワークで十分」という一般則で既存の分離を解消しない。新しいネットワークは分離要件がある場合だけ設ける。
- Dockerソケット、`privileged`、追加の権限は必要性と影響を説明できる場合だけ使う。GPUの予約、既存の実行UID、ログ収集に必要な読取り権限を変更時に確認する。

## 保存領域と削除操作

- 再作成後も必要なデータは名前付きボリュームなど明示した保存先へ置き、Composeで管理する名前付きボリュームはトップレベルの `volumes`に宣言する。
- モデルキャッシュ・GGUF・設定・ホストjournalなど、既存設計が使うバインドマウントを維持する。開発時だけに限定するスキルの一般則はこれらへ適用しない。読取り側は可能な限り読み取り専用とし、初期化側の必要な書込みを保つ。
- 保存先、マウント先、実行UID、権限を変更する場合は既存データの再利用と移行を確認する。権限エラーへの対処として保存先の削除、再帰的な所有者変更、過剰な権限付与を行わない。
- 削除前には対象プロジェクトと実際のボリューム名・パス、内容、利用サービス、復元の可否を特定する。認証領域の削除ではトークン再生成と接続先への影響も確認する。
- `docker compose down -v` / `--volumes`、`docker compose rm -v`、対象ボリュームの `docker volume rm` / `prune`は失うデータを具体的に示し、その削除への明示的な許可を得てから行う。単なる再起動・障害調査・容量整理の依頼をデータ削除の許可と解釈しない。
- `down -v`はComposeが管理する名前付きボリュームと付属する匿名ボリュームを削除する。`rm -v`は削除するコンテナの匿名ボリュームを削除する。`external: true`のボリュームはComposeによる削除の対象外だが、直接削除してよいという意味ではない。
- `down`だけでもコンテナの書込み層は失われ、匿名ボリュームは次回の `up`で自動再接続されない。名前付きボリュームが残ることだけを根拠にデータが安全と判断しない。
- 停止だけなら対象サービスの `stop`、設定変更のない再起動なら `restart`、設定反映なら `up -d`による再作成を選ぶ。稼働中の会話への影響を確認し、目的に不要な全体停止・再作成・`--remove-orphans`を加えない。
- ホスト全体の `prune`やボリューム実体ディレクトリの手動削除をComposeの修復手順にしない。別プロジェクトの資源へ対象を広げない。

## 変更時の確認

構成を変更したら、リポジトリルートで実際に使う環境ファイル・追加ファイル・プロファイルを選び、まず静的に確認する。
現行 `.env`を使う通常構成の例は次のとおり。

```sh
docker context show
docker compose config --quiet
docker compose config --services
```

配布サンプル自体の確認は、既存 `.env`へコピーせず次のように指定する。
シェルの環境変数も展開値に影響するため、検査時の選択条件を記録する。

```sh
docker compose --env-file examples/compose.env -f compose.yml config --quiet
docker compose --env-file examples/compose.env -f compose.yml config --services
```

- 変更したプロファイルや追加ファイルの組合せに絞り、依存先、公開先、マウント、イメージ選択が意図どおりか確認する。全組合せの検査を一律に要求しない。
- 構成検査は実際の起動・接続の成功を保証しない。起動方法や接続を変えた場合は、対象サービスの起動、準備完了、Consul登録、利用側からの接続を必要な範囲で確認する。GPUや別ホストが必要で未実行なら、その範囲を記録する。
- `restart`では環境変数・ポート・マウントの変更が反映されない。反映操作は対象と依存先を絞り、ビルド・取得が必要かを判断して既存の起動方針に合わせる。
- 調査は `ps`と対象サービスの必要な範囲のログから始める。キャッシュやデータを削除して証拠を失う前に原因を確認する。
- 文書だけの変更はMarkdownの整形・リンク・既存設計との整合確認で完了し、コンテナの操作を検査へ追加しない。
