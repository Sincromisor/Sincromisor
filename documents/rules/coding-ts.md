# コーディング規約(TypeScript)

> **対象範囲**: TypeScriptコードベース横断のコーディング規約(型運用 / エラー / ログ / テスト / import / null / 日付 / TODO / 環境変数 / 言語)
> **AGENTS.md との関係**: [AGENTS.md](../../AGENTS.md) は初動ガイドと関連文書へのリンクを保持する。サイズ閾値 / 分割判断 / 主要アンチパターンは [code-structure.md](code-structure.md)、コメント品質の横断基準は [source-comments.md](source-comments.md) に従い、本書は TypeScript 固有の横断ルールを保持する。

## 0. 設計思想

PoC では下記 2 軸を最優先する。

1. **負債が残りにくい方向を選ぶ** — 後から剥がす工数が大きいもの(型を緩める / null と undefined を混在させる / 環境変数直参照を許す)は最初から禁止する
2. **デバッグと更新がしやすい状態を維持する** — 「沈黙する失敗」「観測できない状態」「変更影響が読みにくい依存」を作らない

ルールは原則必須。**破る場合は同じ行に `// reason: <理由>` を付ける**(レビューでの差し戻し基準は理由の有無)。

## 1. TypeScript 型運用

| ルール                                               | 強制度 | 補足                                                  |
| ---------------------------------------------------- | ------ | ----------------------------------------------------- |
| `any` 禁止。外部 I/O は `unknown` で受けて Zod 解析  | 必須   |                                                       |
| 型アサーション (`as Foo` / `as unknown as Foo`) 禁止 | 必須   | `as const` のみ可                                     |
| nullでないことの表明 `!` 禁止                        | 必須   | ガード節 / Zod 解析で潰す                             |
| `@ts-ignore` 禁止                                    | 必須   | —                                                     |
| `@ts-expect-error` 可                                | 推奨   | 直後に `// reason: ... / 解消条件: ...` 必須          |
| 公開 (公開) 関数の戻り値型を明示                     | 推奨   | 型推論任せにすると変更時にシグネチャが静かに変わる    |
| `import type { X }` で型のみ import を分離           | 推奨   | 未使用コードの除去 + 「型を実体と取り違える」事故防止 |

**理由**: `any` / `as` / `!` は「型は通っているが実体が違う」状態を作り、デバッグを最も困難にする。PoC で導入すると剥がし切れずに負債化する。

**適用方法**: 既存コードに残っていたら、触った箇所から順に潰す。WebRTC DataChannel / 設定 JSON / ブラウザ API / 外部ライブラリの型不整合は、境界専用の変換層を一枚挟み、生のレスポンスやイベント値をそこで吸収する。

## 2. 静的検査 / フォーマッタ / コミット前チェック

| 項目                          | ツール                            |
| ----------------------------- | --------------------------------- |
| 静的検査 (TS / JS / JSON)     | **Biome**                         |
| フォーマッタ (TS / JS / JSON) | **Biome**                         |
| フォーマッタ (Markdown)       | **Prettier**(`*.md` のみスコープ) |
| 型チェック                    | TypeScript (`npm run build` 経由) |
| テスト                        | `npm run test`                    |

- Biome の設定は [biome.json](../../sincromisor-frontend/biome.json) を正本とする。静的検査は `recommended` を有効化し、PoC で支障が出る項目のみ明示オプトアウト
- `noExcessiveCognitiveComplexity` は認知的複雑度を見直す目安として扱い、上限超過だけで修正必須とはしない。警告の確認・記録は [タスク管理の警告方針](../../tasks/README.md#biomeの警告の扱い) に従う。
- Prettier は **Markdown 専用**。Biome 2.x が Markdown 未対応のため、ドキュメント整形だけ Prettier を残す。設定ファイルを導入する場合はリポジトリ直下に置き、`*.md` のみに適用する
- コミット前の確認項目:
    1. `npm run build`(型チェック + Vite ビルド)
    2. `npm run check`(Biome 静的検査+整形 / PrettierによるMarkdown整形)
    3. `npm run test`(変更レイヤ)
- 静的検査警告を局所的に抑制する場合は `// biome-ignore <rule>: <reason>` を付ける(本書 §0 の `// reason:` ルールに準ずる)
- コミット前フック (lefthook / husky 等) は現時点で未導入。コミット漏れによる手戻りが見えた時点で導入を検討する

**理由**: 静的検査と整形の取りこぼしは手動チェックでは必ず発生し、後で大量修正の負債になる。Biome は単一バイナリで TS / JS / JSON の静的検査 + 整形を兼ね、Prettier は Markdown 専用に限定することで設定衝突を最小化する。Biome が Markdown 対応した時点で Prettier を撤去する(本書 §2 を更新する宿題)。

**適用方法**: 現時点では `npm run build` と `npm run check` を最低確認とする。テスト対象を変更した場合は `npm run test` も実行する。CI 整備フェーズで上記 3 点(`npm run check` / `npm run build` / `npm run test`)を自動化する。

## 3. エラーハンドリング

- 例外は **throw 基本**。`Result<T, E>` 型は使わない(言語標準の流儀に揃える)
- `catch` で**握り潰し禁止**。最低でも `logger.error` してから再 throw、または明示的にハンドリング理由をコメント
- 再 throw は必ず原因チェーンを残す: `throw new MyError("msg", { cause: e })`
- 例外メッセージは英語、機密情報 / 個人情報 / ユーザーの音声認識結果全文を不用意に含めない

**理由**: `try { ... } catch {}` が一箇所でもあるとデバッグの時間が指数的に増える。原因チェーン欠落も同様。

**適用方法**: catch 節を書いたら必ずログ + 再 throw か、ハンドル理由のコメントを残す。

## 4. ログ / `console`

- `console.log` / `console.error` 直書き禁止。全体で用いるロガーを用意し、それを経由する。

- ログレベル指針:

| レベル  | 用途                                                                                |
| ------- | ----------------------------------------------------------------------------------- |
| `error` | 復旧不能 / ユーザー操作や接続継続に影響するもの                                     |
| `warn`  | 自動復旧した異常、代替処理、再試行後成功、ブラウザ差分による機能縮退                |
| `info`  | WebRTC 接続状態、デバイス選択、VRM / MediaPipe / HLS などの初期化開始・終了         |
| `debug` | SDP / ICE / DataChannel / VAD / 視線 / 動作など、開発時の原因調査に必要な中間データ |

### 4.1 デバッグダンプ方針

ブラウザ上の WebRTC / MediaPipe / 3D 描画は、環境依存の失敗が多い。開発時は再現に必要な診断情報を `debug` で出してよいが、常時出すとブラウザ console がノイズ化し、実ユーザー環境ではプライバシー上のリスクも上がる。

- `debug` レベルでは、SDP / ICE 候補の種別集計、DataChannel 送受信データのスキーマ検証結果、VAD や顔・姿勢の追跡の数値を出してよい
- 音声認識結果、チャット本文、デバイス表示名など、個人情報や機密情報になり得る値は必要最小限にする
- ログファイル / 追跡記録出力(`*.log`等)は `.gitignore` で除外。リポジトリに未加工の診断データをコミットしない

### 4.2 PoC でも常時禁止

- **機密情報(APIキー / Dify トークン / TURN 認証情報など)は生のままログに出さない**

### 4.3 ログ形式

- 構造化ログを既定 — `logger.info("rtc connection failed", { state, iceConnectionState })`。文字列補間で詰め込まない

**理由**: WebRTC / MediaPipe / 3D 描画のデバッグは、ブラウザ・デバイス・ネットワーク状態を後から追えることが生命線。一方、機密情報と個人情報は開発中でも解禁し得ないため、診断ログとは別軸の絶対禁止として分離する。

## 5. テスト

- ランナーは `npm run test` から呼び出す。実体のテスト実行ツールは導入時に決める
- 配置は対象コードと同階層の `__tests__/`(例: `RTC/__tests__/RTCTalkClient.test.ts`)
- ファイル名: `<対象>.test.ts`
- フィクスチャは `__tests__/fixtures/` に置く。プロダクションコードから import しない
- テストのためだけに内部要素を `export` しない — 必要な時点で純粋関数や境界処理を別ファイル化する

**理由**: PoC ではテスト網羅率より、「壊れたら気付ける場所」を堅く守るほうがデバッグコストを下げる。

## 6. import パス

- **パスの別名を使わない**。`tsconfig.json` の `paths` 未設定を維持し、相対 import を基本とする
- 同一ディレクトリは `./foo`、跨る場合は `../bar/foo`。`../../../` が 3 段を超えたら**配置を見直すサイン**
- 型のみの読み込みは `import type { X } from "./y"` または `import { type X } from "./y"` で分離(本書 §1 参照)
- import の並び順は **Biome `organizeImports` に従う**(`npm run check` で自動整列)。手で並び替える必要はない。デフォルトの順序は概ね「実行時組み込み → 外部依存 → 相対 import」

**理由**: 別名は移設時の負債(リネーム / 移動で別名設定も追従が必要)になりやすい。相対パスは「物理位置 = 依存方向」が一目で見え、デバッグ時の追跡が容易。

## 7. `null` / `undefined` / Zod 任意

- **アプリ内では `null` を使わない**。欠損は `undefined` で統一
- 例外: DB / 外部 API が `null` を返す境界のみ。境界で `?? undefined` 変換し、以後は `undefined`
- Zod は `.optional()` を既定。`.nullable()` は外部 I/O スキーマ(DB / 外部 API) のみ
- 既定値は `value ?? defaultValue` を使う。`value || defaultValue`(偽と評価される値全般を拾う)は禁止 — `0` / `""` / `false` が事故になる

**理由**: `null` と `undefined` を混在させると「どちらで欠損を表すか」を毎回局所判断することになり、デバッグ時に分岐網羅が困難になる。

## 8. 日付 / タイムゾーン

- **保存・契約 (Zod / DB / ログ) は UTC ISO8601 文字列** (`new Date().toISOString()`) で扱う
- **表示用(画面 / レポート / CLI 出力)のみ JST に変換**
- `Date` オブジェクトを契約に持たせない — 文字列で持ち、必要箇所で `new Date(s)` する
- 日付ライブラリは当面追加しない(`Date` + ISO 文字列で十分)。差分計算等が増えたら `Temporal` の導入を再検討

**理由**: 「TZ 違いで再現しない不具合」はデバッグが最も困難な種類のひとつ。境界で文字列に固定するのが最も負債を作らない。

## 9. TODO / FIXME / `@deprecated`

- 形式: `// TODO(task-<id>-<slug>): <内容>` — 標準化したタスク ID 紐付け必須。旧 `TODO(TASK-yymmddhhmmss): ...` は移行互換として許容する。ID 無しの TODO はレビューで差し戻し
- `FIXME` は使わない(`TODO` に統一)
- `@deprecated` を付けたら **同タスクまたは次タスクで削除**。残置禁止
- コメントに「あとで」「いずれ」だけ書くのは禁止 — 必ずタスク化する

**理由**: 紐付かない TODO は数ヶ月で誰も追えなくなる。`@deprecated` 残置は「使われていない死んだコード」を増殖させる。

## 10. 環境変数

- 全環境変数は env.ts に集約。Zod でスキーマ定義 + 解析
- コード本体で `process.env.X` / `Bun.env.X` / `import.meta.env.X` を直参照することは**禁止**
- 新規環境変数を追加したら同コミットで `examples/compose.env` やフロントエンド用環境変数サンプルを同期(値はダミーまたはプレースホルダ)
- 環境変数の読み込み方法は実行時に合わせる。Vite は `import.meta.env`、Bun 採用時は Bun の自動読み込みを env.ts の内側だけで扱う
- 機密情報系(APIキー等)はログに出さない。`.env` 本体は絶対にコミットしない(AGENTS.md と整合)

**理由**: 環境変数直書きは「どこで何を読んでいるか」が grep でしか分からず、配備時の差し替え漏れ温床になる。

| 対象                         | 言語                                                                                               |
| ---------------------------- | -------------------------------------------------------------------------------------------------- |
| 識別子(変数 / 関数 / 型)     | 英語                                                                                               |
| ログ / エラーメッセージ      | 英語(運用 / 検索しやすさ)                                                                          |
| ソースコード内コメント       | 日本語(AGENTS.md と整合)                                                                           |
| Markdown 文書                | 日本語。[coding-md.md](coding-md.md) に従う                                                        |
| ユーザー向け文言             | 日本語                                                                                             |
| Zod スキーマの `.describe()` | 日本語または英語。ユーザー表示用は日本語、開発者向け診断は英語でも可                               |
| コミットメッセージ           | 日本語。形式は [tasks/README.md](../../tasks/README.md) の Conventional Commits ベース規約に従う。 |

## 12. その他の負債抑制ルール

- **マジックリテラルの定数化** — モデル名 / タイムアウト / しきい値は `UPPER_SNAKE` 定数に `as const` で集約
- **一時的なフラグを制御処理 / サービス / 管理処理の引数に増やさない** — UI 状態 / 設定モデル / 環境変数経由で渡す(引数増殖は責務境界の崩れの起点)
- **コメントアウトでの「とりあえず無効化」禁止** — 不要コードは削除する(Gitの履歴が正本)
- **型 / Zod スキーマは境界ごとに正本を 1 箇所**。同型を別ファイルで再定義しない
- **「将来の差し替えのため」の抽象を作らない** — 必要になった時点で抽出する(Rule of Three 手前で動く / AGENTS.md と整合)

## 13. ソースコードコメント品質

コメント品質の目的、既存コードへの適用、省略条件、点検の記録形式は [source-comments.md](source-comments.md) に
従う。TypeScript でも、公開 API や非自明な制約は必須の下限であり、それだけで十分とは判断しない。
処理の全体像、処理工程の段階、状態遷移、データ変換、離れたコンポーネント / フック / Worker 間の
関係を、一般的な開発者が短時間で調査できるようにする。

コメント作業はコメント数を増やす作業ではない。変更したシンボル / 処理群 / 判断 / 処理の流れと
変更理解範囲を `keep` / `rewrite` / `delete` / `add` に分類し、安全な変更と理解支援の両方に
必要な読者に必要な知識を残す点検として扱う。

コメントで責務分割を代替しない。[code-structure.md](code-structure.md) の「コメントで段落分けしたくなったら
関数抽出を検討する」方針に従い、まず命名、関数分割、型定義、設定オブジェクトで明確化できないか確認する。

### 13.1 コメントが必須の対象と点検単位

コメント点検の最小単位はファイルではなく、対象シンボル / 処理群 / 判断 / 処理の流れである。次の対象は個別に
点検する。

- `export` される、または公開なクラス / 関数 / 型 / インターフェース / コンポーネント / フック / モジュール /
  業務上重要な `const`
- `schemaVersion` を持つ保存契約、再生ログ、診断用スナップショット、解析処理
- Worker / DOM / MediaStream / MediaPipe / WebRTC / ファイルシステム / 再生ログなどの境界モジュール
- 座標系、単位、左右定義、時刻基準、フレーム番号、信頼度 / 信頼性の意味
- しきい値、代替処理、機能低下、回復、待機期間、ヒステリシス、値の制限、左右の割り当て、ROI 判定などの
  経験則
- 後始末所有者、リソースの生存期間、例外を代替処理に落とす理由
- アプリ制御、会話、追跡、アニメーションなど複数段階を調停する処理の組み立て
- 状態 / モード遷移、イベント / コールバックの発生元と、後続処理を開始する条件
- ブラウザから得た未加工の / MediaPipe / WebRTC データから内部表現への変換と、後段へ委ねる処理
- 名前と型だけでは上位処理の流れにおける役割が分からない非公開関数 / 処理群

点検成果物の列と省略理由は [source-comments.md](source-comments.md) の「コメント点検」を使う。
ファイル単位の「モジュールコメントに集約」だけでは完了扱いにしない。

### 13.2 記法の使い分け

- 公開 / 公開API のコメントは原則 JSDoc / TSDoc とする。生成ドキュメントが無い場合でも、
  エディタカーソルを重ねたときの表示とレビューで契約を読める形にする。
- 実装内部の処理の流れ / 案内 / 状態 / データの補足は通常のブロックコメントまたは行コメントを使う。
  複数行を一段高い抽象度で要約し、現在の処理段階や前後関係を示すコメントを許容する。
- ソースコード内コメントの言語は §11 に従い日本語とする。エラーメッセージやログの英語方針は変えない。

例:

```ts
/**
 * replay log v2 の gaze sample を runtime で扱う正規化形式へ変換する。
 *
 * v1 log は `confidence` を持たないため `undefined` として受理する。
 * frame index が単調増加でない sample は、再生順序の復元に失敗するため reject する。
 *
 * @throws ReplayLogParseError 受理できない version または frame index の場合。
 */
export function parseGazeReplaySample(input: unknown): GazeReplaySample {
  ...
}
```

### 13.3 最低限含める内容

対象別に、コメントへ次の情報を含める。

| 対象                | 最低限書く内容                                                                                      |
| ------------------- | --------------------------------------------------------------------------------------------------- |
| 公開要素            | 責務、入力境界、返す値または観測可能な出力の意味、失敗条件、副作用、非対象                          |
| 境界モジュール      | 外部仕様、受け取る生の値、正規化後の契約、失敗時の扱い、後始末所有者                                |
| スキーマ / 解析処理 | 受理する旧ログ / バージョン、拒否する値、代替処理方針、呼び出し元に返る失敗の形、破壊的変更の確認先 |
| 座標 / 単位         | 座標系、単位、左右定義、時刻基準、フレーム番号の基準、信頼度の意味                                  |
| しきい値            | 値の意味、採用理由または由来、変更時に確認する表示・テスト、誤調整した場合の見え方または失敗モード  |
| 経験則              | 入力前提、値の意味、採用理由、変更時の確認先、誤調整した場合の見え方または失敗モード                |
| 生存期間 / 後始末   | リソースの所有者、解放タイミング、解放順序、二重解放やリークを避けるための不変条件                  |
| 代替処理 / 例外処理 | 例外を握り潰さず代替処理に落とす理由、ユーザー影響、ログや復旧の観測点                              |

### 13.4 省略とモジュール TSDoc への集約

コメントの省略条件は [source-comments.md](source-comments.md) の「コメントの省略条件」に従う。
非公開であること、短いこと、型があること、既存コードにコメントがないことは単独の省略理由にならない。
目的、上位処理の流れでの位置、入出力、状態変化、前後関係が局所的に読める場合だけ省略できる。

モジュール TSDoc へ個別公開の保守知識を集約できるのは、ファイル内の公開要素が単一責務を共有し、モジュール
コメントが各公開の入力境界、観測可能な出力、失敗条件、副作用、非対象を具体的に覆う場合に限る。
単なるファイルの責務要約、設計文書への誘導、または「各公開はモジュールコメントを参照」といった宣言だけでは
集約条件を満たさない。

### 13.5 必要な実装コメント

TypeScript の実装内部では、次の対象にブロックコメントまたは行コメントを置く。コードと同じ粒度の逐語説明ではなく、
複数行・複数シンボルの関係を一段高い抽象度で説明する。

- 複雑な分岐やアルゴリズムの不変条件
- 回避策と、その外部要因または削除条件
- 性能上の理由
- ブラウザ、MediaPipe、WebRTC、VRM など外部仕様由来の制約
- 後始末 / 生存期間 / 代替処理の安全条件
- 処理の組み立て / 処理工程の現在段階と、この段階で完了させる責務
- 状態 / モード遷移とイベント / コールバックの発生元
- 座標、フレーム、送受信データ、ブラウザ API 値などの変換前後
- コンポーネント、フック、Worker、制御処理、サービス間の非局所的な接続関係
- 意図的な早期返却、無処理、処理の延期、後段へ委ねる責務

`catch` で代替処理へ落とす場合は §3 に従い、ログ + 再 throw か、明示的なハンドル理由をコメントで残す。

### 13.6 禁止するコメント

- `// 値を返す`、`// ループする` のような処理説明だけのコメント
- 公開API と非自明な制約だけを機械的に埋め、内部処理の流れの理解困難を放置すること
- 古い実装経緯だけを残し、現在の判断や契約を説明しないコメント
- 「設計文書 / 対象を絞ったテストを確認する」とだけ書き、実コード上の入力境界、失敗条件、副作用、確認観点を
  説明しないコメント
- 名前や型から分かる責務要約だけのコメント
- 経験則 / しきい値の存在だけを書き、誤調整時の見え方や失敗モード、値の由来を説明しないコメント
- 点検成果物で外部公開のため追加、`既存コメントで十分` のような定型文だけを書き、
  シンボル / 判断固有の読者の疑問と読者に必要な知識を示さない理由
- `private`、`短い`、`型がある`、`既存コードにもない` だけを省略理由にすること
- 根拠のない `temporary`、`workaround`、`magic`
- 理由、削除条件、標準化したタスク / 課題 ID、期限または判断基準がない TODO
- 実装と同期しない設計メモ、更新されず古くなったになったコメント
- コメントアウトしたコードの残置。不要コードは削除し、必要な判断はタスクまたは ADR に残す
