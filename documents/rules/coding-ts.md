# コーディング規約(TypeScript)

> **対象範囲**: TypeScriptコードベース横断のコーディング規約(型運用 / エラー / ログ / テスト / import / null / 日付 / TODO / 環境変数 / 言語)
> **AGENTS.mdとの関係**: [AGENTS.md](../../AGENTS.md) は初動ガイドと関連文書へのリンクを保持する。サイズ閾値 / 分割判断 / 主要アンチパターンは [code-structure.md](code-structure.md)、コメント品質の横断基準は [source-comments.md](source-comments.md) に従い、本書はTypeScript固有の横断ルールを保持する。

## 0. 設計思想

PoCでは下記2軸を最優先する。

1. **負債が残りにくい方向を選ぶ** — 後から剥がす工数が大きいもの(型を緩める / nullとundefinedを混在させる / 環境変数直参照を許す)は最初から禁止する
2. **デバッグと更新がしやすい状態を維持する** — 「沈黙する失敗」「観測できない状態」「変更の影響が読みにくい依存関係」を作らない

ルールは原則必須。**破る場合は同じ行に `// reason: <理由>`を付ける**(レビューでの差し戻し基準は理由の有無)。

## 1. TypeScript 型運用

| ルール                                               | 強制度 | 補足                                                  |
| ---------------------------------------------------- | ------ | ----------------------------------------------------- |
| `any`禁止。外部I/Oは `unknown`で受けてZod解析        | 必須   |                                                       |
| 型アサーション (`as Foo` / `as unknown as Foo`) 禁止 | 必須   | `as const`のみ可                                      |
| nullでないことの表明 `!`禁止                         | 必須   | ガード節 / Zod解析で潰す                              |
| `@ts-ignore`禁止                                     | 必須   | —                                                     |
| `@ts-expect-error`可                                 | 推奨   | 直後に `// reason: ... / 解消条件: ...`必須           |
| 公開関数の戻り値型を明示                             | 推奨   | 型推論任せにすると変更時にシグネチャが静かに変わる    |
| `import type { X }`で型のみimportを分離              | 推奨   | 未使用コードの除去 + 「型を実体と取り違える」事故防止 |

**理由**: `any` / `as` / `!`は「型は通っているが実体が違う」状態を作り、デバッグを最も困難にする。PoCで導入すると剥がし切れずに負債化する。

**適用方法**: 既存コードに残っていたら、触った箇所から順に潰す。WebRTC DataChannel / 設定JSON / ブラウザAPI / 外部ライブラリの型不整合は、境界専用の変換層を介し、生のレスポンスやイベント値をそこで吸収する。

## 2. 静的検査 / フォーマッタ / コミット前チェック

| 項目                          | ツール                           |
| ----------------------------- | -------------------------------- |
| 静的検査 (TS / JS / JSON)     | **Biome**                        |
| フォーマッタ (TS / JS / JSON) | **Biome**                        |
| フォーマッタ (Markdown)       | **Prettier**(`*.md`のみスコープ) |
| 型チェック                    | TypeScript (`npm run build`経由) |
| テスト                        | `npm run test`                   |

- Biomeの設定は [biome.json](../../sincromisor-frontend/biome.json) を正本とする。静的検査は `recommended`を有効化し、PoCで支障が出る項目のみ明示オプトアウト
- `noExcessiveCognitiveComplexity`は認知的複雑度を見直す目安として扱い、上限超過だけで修正必須とはしない。警告の確認・記録は [タスク管理の警告方針](../../tasks/README.md#biomeの警告の扱い) に従う。
- Prettierは **Markdown専用**。Biome 2.xがMarkdown未対応のため、ドキュメント整形だけPrettierを残す。設定ファイルを導入する場合はリポジトリ直下に置き、`*.md`のみに適用する
- 確認範囲は[タスク管理の確認コマンド](../../tasks/README.md#確認コマンド)に従う。通常変更では変更ファイルの整形と対象を絞った静的検査・型確認・テストを行う。
- 全体確認が必要な場合は`npm run build`（型チェックとViteビルド）、`npm run check`（BiomeとMarkdownの検査）、`npm run test`（Vitest）を使う。
- 静的検査警告を局所的に抑制する場合は `// biome-ignore <rule>: <reason>`を付ける(本書 §0の `// reason:`ルールに準ずる)
- `npm run git:hooks:install`で`.githooks/commit-msg`を有効にし、コミットメッセージを検査する。コードの検査はこのフックでは実行しない。

**理由**: 静的検査と整形の取りこぼしは手動チェックでは必ず発生し、後で大量修正の負債になる。Biomeは単一バイナリでTS / JS / JSONの静的検査 + 整形を兼ね、PrettierはMarkdown専用に限定することで設定衝突を最小化する。BiomeがMarkdown対応した時点でPrettierを撤去する(本書 §2を更新する宿題)。

**適用方法**: 対象確認が通ったら完了処理へ進む。検査の拡大・再実行は追加変更、失敗、未解決の懸念がある場合に行う。

## 3. エラーハンドリング

- 例外は **throw基本**。`Result<T, E>`型は使わない(言語標準の流儀に揃える)
- `catch`で**握り潰し禁止**。最低でも `logger.error`してから再throw、または明示的に処理する理由をコメント
- 再throwは必ず原因チェーンを残す: `throw new MyError("msg", { cause: e })`
- 例外メッセージは英語、機密情報 / 個人情報 / ユーザーの音声認識結果全文を不用意に含めない

**理由**: `try { ... } catch {}`が一箇所でもあるとデバッグの時間が指数的に増える。原因チェーン欠落も同様。

**適用方法**: catch節を書いたら必ずログ + 再throwか、処理する理由のコメントを残す。

## 4. ログ / `console`

- `console.log` / `console.error`直書き禁止。全体で用いるロガーを用意し、それを経由する。

- ログレベル指針

| レベル  | 用途                                                                                |
| ------- | ----------------------------------------------------------------------------------- |
| `error` | 復旧不能 / ユーザー操作や接続継続に影響するもの                                     |
| `warn`  | 自動復旧した異常、代替処理、再試行後成功、ブラウザ差分による機能縮退                |
| `info`  | WebRTC接続状態、デバイス選択、VRM / MediaPipe / HLSなどの初期化開始・終了           |
| `debug` | SDP / ICE / DataChannel / VAD / 視線 / 動作など、開発時の原因調査に必要な中間データ |

### 4.1 デバッグダンプ方針

ブラウザ上のWebRTC / MediaPipe / 3D描画は、環境依存の失敗が多い。開発時は再現に必要な診断情報を `debug`で出してよいが、常時出すとブラウザconsoleがノイズ化し、実ユーザー環境ではプライバシー上のリスクも上がる。

- `debug`レベルでは、SDP / ICE候補の種別集計、DataChannel送受信データのスキーマ検証結果、VADや顔・姿勢の追跡の数値を出してよい
- 音声認識結果、チャット本文、デバイス表示名など、個人情報や機密情報になり得る値は必要最小限にする
- ログファイル / 追跡記録出力(`*.log`等)は `.gitignore`で除外。リポジトリに未加工の診断データをコミットしない

### 4.2 PoC でも常時禁止

- **機密情報(APIキー / Mastraトークン / TURN認証情報など)は生のままログに出さない**

### 4.3 ログ形式

- 構造化ログを既定 — `logger.info("rtc connection failed", { state, iceConnectionState })`。文字列補間で詰め込まない

**理由**: WebRTC / MediaPipe / 3D描画のデバッグは、ブラウザ・デバイス・ネットワーク状態を後から追えることが生命線。一方、機密情報と個人情報は開発中でも解禁し得ないため、診断ログとは別軸の絶対禁止として分離する。

## 5. テスト

- フロントエンドのテストは`npm run test`からVitestを実行する。ブラウザーの操作・画面確認は[Playwright CLI利用ルール](playwright-cli.md)に従う。
- 配置は対象コードと同階層の `__tests__/`(例: `RTC/__tests__/RTCTalkClient.test.ts`)
- ファイル名: `<対象>.test.ts`
- フィクスチャは `__tests__/fixtures/`に置く。プロダクションコードからimportしない
- テストのためだけに内部要素を `export`しない — 必要な時点で純粋関数や境界処理を別ファイル化する

**理由**: PoCではテスト網羅率より、「壊れたら気付ける場所」を堅く守るほうがデバッグコストを下げる。

## 6. import パス

- **パスの別名を使わない**。`tsconfig.json`の `paths`未設定を維持し、相対importを基本とする
- 同一ディレクトリは `./foo`、跨る場合は `../bar/foo`。`../../../`が3段を超えたら**配置を見直すサイン**
- 型のみの読み込みは `import type { X } from "./y"`または `import { type X } from "./y"`で分離(本書 §1参照)
- importの並び順は **Biome `organizeImports`に従う**(`npm run check`で検査し、`npm run format`で適用)。手で並び替える必要はない。デフォルトの順序は概ね「実行時組み込み → 外部依存 → 相対import」

**理由**: 別名は移設時の負債(リネーム / 移動で別名設定も追従が必要)になりやすい。相対パスは「物理位置 = 依存方向」が一目で見え、デバッグ時の追跡が容易。

## 7. `null` / `undefined` / Zod 任意

- **アプリ内では `null`を使わない**。欠損は `undefined`で統一
- 例外: DB / 外部APIが `null`を返す境界のみ。境界で `?? undefined`変換し、以後は `undefined`
- Zodは `.optional()`を既定。`.nullable()`は外部I/Oスキーマ(DB / 外部API) のみ
- 既定値は `value ?? defaultValue`を使う。`value || defaultValue`(偽と評価される値全般を拾う)は禁止 — `0` / `""` / `false`が事故になる

**理由**: `null`と `undefined`を混在させると「どちらで欠損を表すか」を毎回局所判断することになり、デバッグ時に分岐網羅が困難になる。

## 8. 日付 / タイムゾーン

- **保存・契約 (Zod / DB / ログ) はUTC ISO8601文字列** (`new Date().toISOString()`) で扱う
- **表示用(画面 / レポート / CLI出力)のみJSTに変換**
- `Date`オブジェクトを契約に持たせない — 文字列で持ち、必要箇所で `new Date(s)`する
- 日付ライブラリは当面追加しない(`Date` + ISO文字列で十分)。差分計算等が増えたら `Temporal`の導入を再検討

**理由**: 「TZ違いで再現しない不具合」はデバッグが最も困難な種類のひとつ。境界で文字列に固定するのが最も負債を作らない。

## 9. TODO / FIXME / `@deprecated`

- 形式: `// TODO(task-<id>-<slug>): <内容>` — 標準化したタスクID紐付け必須。旧 `TODO(TASK-yymmddhhmmss): ...`は移行互換として許容する。ID無しのTODOはレビューで差し戻し
- `FIXME`は使わない(`TODO`に統一)
- `@deprecated`を付けたら **同タスクまたは次タスクで削除**。残置禁止
- コメントに「あとで」「いずれ」だけ書くのは禁止 — 必ずタスク化する

**理由**: 紐付かないTODOは数ヶ月で誰も追えなくなる。`@deprecated`残置は「使われていない死んだコード」を増殖させる。

## 10. 環境変数

- 全環境変数はenv.tsに集約。Zodでスキーマ定義 + 解析
- コード本体で `process.env.X` / `Bun.env.X` / `import.meta.env.X`を直参照することは**禁止**
- 新規環境変数を追加したら同コミットで `examples/compose.env`やフロントエンド用環境変数サンプルを同期(値はダミーまたはプレースホルダ)
- 環境変数の読み込み方法は実行時に合わせる。Viteは `import.meta.env`、Bun採用時はBunの自動読み込みをenv.tsの内側だけで扱う
- 機密情報系(APIキー等)はログに出さない。`.env`本体は絶対にコミットしない(AGENTS.mdと整合)

**理由**: 環境変数直書きは「どこで何を読んでいるか」がgrepでしか分からず、配備時の差し替え漏れの温床になる。

## 11. 言語ポリシー

| 対象                        | 言語                                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------ |
| 識別子(変数 / 関数 / 型)    | 英語                                                                                             |
| ログ / エラーメッセージ     | 英語(運用 / 検索しやすさ)                                                                        |
| ソースコード内コメント      | 日本語(AGENTS.mdと整合)                                                                          |
| Markdown文書                | 日本語。[coding-md.md](coding-md.md) に従う                                                      |
| ユーザー向け文言            | 日本語                                                                                           |
| Zodスキーマの `.describe()` | 日本語または英語。ユーザー表示用は日本語、開発者向け診断は英語でも可                             |
| コミットメッセージ          | 日本語。形式は [tasks/README.md](../../tasks/README.md) のConventional Commitsベース規約に従う。 |

## 12. その他の負債抑制ルール

- **マジックリテラルの定数化** — モデル名 / タイムアウト / しきい値は `UPPER_SNAKE`定数に `as const`で集約
- **一時的なフラグを制御処理 / サービス / 管理処理の引数に増やさない** — UI状態 / 設定モデル / 環境変数経由で渡す(引数増殖は責務境界の崩れの起点)
- **コメントアウトでの「とりあえず無効化」禁止** — 不要コードは削除する(Gitの履歴が正本)
- **型 / Zodスキーマは境界ごとに正本を1箇所**。同型を別ファイルで再定義しない
- **「将来の差し替えのため」の抽象を作らない** — 必要になった時点で抽出する(Rule of Three手前で動く / AGENTS.mdと整合)

## 13. ソースコードコメント品質

点検範囲、必要な説明、省略判断、修正と報告は [source-comments.md](source-comments.md) の手順に従う。TypeScriptでは公開クラス・関数・型・インターフェース・コンポーネント・フック・モジュール・業務上重要な定数を対象とし、次の記法を使う。

### 13.1 記法の使い分け

- 公開APIのコメントは原則JSDoc / TSDocとする。生成ドキュメントが無い場合でも、
  エディタでカーソルを重ねたときの表示とレビューで契約を読める形にする。
- 実装内部の処理の流れ / 案内 / 状態 / データの補足は通常のブロックコメントまたは行コメントを使う。
  複数行を一段高い抽象度で要約し、現在の処理段階や前後関係を示すコメントを許容する。
- ソースコード内コメントの言語は §11に従い日本語とする。エラーメッセージやログの英語方針は変えない。

例

```ts
/**
 * 再生ログv2の視線サンプルを実行時の正規化形式へ変換する。
 *
 * v1のログは `confidence` を持たないため `undefined` として受理する。
 * フレーム番号が単調増加でないサンプルは、再生順序を復元できないため拒否する。
 *
 * @throws ReplayLogParseError 受理できない版またはフレーム番号の場合。
 */
export function parseGazeReplaySample(input: unknown): GazeReplaySample {
  ...
}
```

### 13.2 モジュールTSDocへの集約

モジュールTSDocへ個別公開の保守知識を集約できるのは、ファイル内の公開要素が単一責務を共有し、モジュール
コメントが各公開の入力境界、観測可能な出力、失敗条件、副作用、非対象を具体的に覆う場合に限る。
単なるファイルの責務要約、設計文書への誘導、または「各公開はモジュールコメントを参照」といった宣言だけでは
集約条件を満たさない。

### 13.3 TypeScript固有の点検対象

- `schemaVersion`を持つ保存契約、再生ログ、診断用スナップショットは受理する版、拒否する値、代替処理、呼び出し元に返る失敗、破壊的変更時の確認先を説明する。
- Worker / DOM / MediaStream / MediaPipe / WebRTC / VRM / ファイルの境界では外部仕様の制約、後始末の所有者、生存期間を示す。
- 座標系、左右の割り当て、ROI判定、待機期間、ヒステリシス、値の制限、信頼度などの経験則は、共通規約のしきい値・表現の説明事項を満たす。
- アプリ制御、会話、追跡、アニメーションの段階、イベント・コールバックによる状態遷移、コンポーネント・フック・Worker間の接続、未加工データから内部表現への変換は実装コメントで説明する。
- `catch`で代替処理へ落とす場合は §3に従い、ログ + 再throwか、明示的に処理する理由を残す。TODOの形式は §9に従う。
