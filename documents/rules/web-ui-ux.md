# Web UI・UX設計原則

## 目的と適用範囲

SincromisorのWeb UIは、利用者が望む体験に迷わず到達し、自分の意思で安心して続けたり終えたりできるように設計する。美しさ、楽しさ、キャラクターの魅力も品質の一部とし、理解しやすさと操作の確実さを両立させる。

本書は、利用者向け画面、設定、管理・診断画面、今後追加する機能に共通する設計規約である。現在の実装の説明や達成状況を示す文書ではない。既存画面の都合を原則の根拠にせず、新規設計と変更時の判断に適用する。

画面構成、色、寸法、部品、技術の選択は個別設計で定める。本書では満たすべき体験と判断基準を定め、特定の見た目や操作方式を恒久的な正解にしない。現在の構成は[設計索引](../design/index.md#フロントエンド)から参照する。

## 1. 利用者の目的から設計する

- 各画面と操作について、誰が、どの状況で、何を達成するために使うかを定める。サービス内部の構成や開発上の分類を、そのまま利用者の操作手順にしない。
- 目的の達成に必要な判断、入力、記憶、待ち時間を減らす。操作回数だけを減らして、結果の予測や誤操作からの回復を難しくしない。
- 主な目的と次にできることが、画面を見て分かるようにする。補助操作や装飾が主な操作と注意を奪い合わないようにする。
- 初回利用では必要な前提だけを、その情報が必要になる場所で説明する。長い説明や設定の完了を、体験開始の一律の条件にしない。
- 慣れた利用者には、繰り返し操作を省ける経路を用意する。初めて使う人が発見できる通常の経路も保つ。

## 2. 情報の関係と現在地を明確にする

- 利用者が理解する目的や対象で情報をまとめ、名称と階層をサービス全体で揃える。同じ語を異なる意味で使わない。
- 見出し、余白、配置、文字の強弱で、情報のまとまりと優先順位を表す。読解や選択に役立たない見出し、枠、重複説明を増やさない。
- 詳細や高度な選択肢は必要に応じて開けるようにする。利用の可否、重要な影響、失敗、停止方法は隠さない。
- 移動先、現在の対象、戻る先を把握できるようにする。戻る操作で入力や閲覧位置を不必要に失わせない。
- 同じ役割の操作は、名称、見た目、配置の関係、振る舞いを揃える。異なる結果を生む操作は区別できるようにする。

## 3. 操作の結果を予測できるようにする

- ボタンには実行する動作、リンクには移動先が分かる名前を付ける。アイコンだけの操作には、支援技術が読める名前と、見た目から意味を確認できる手段を設ける。
- 操作できる要素と、表示だけの要素を識別できるようにする。選択、押下、処理中、無効の状態を区別する。
- 保存、即時反映、送信、取り消しの境界を明確にする。同じ種類の設定で反映方法が変わる場合は、操作前に分かるようにする。
- 無効な操作には、使えない理由と利用可能にする方法を示す。理由の確認を、無効な要素へのマウス操作だけに依存させない。
- ブラウザーの戻る操作、リンク、キーボードなどの標準的な振る舞いを尊重する。独自操作を採用する場合も、発見可能で確実に使える経路を設ける。
- 通常の操作は滞りなく進められるようにする。確認ダイアログは、利用者が実行前に影響を再判断する必要がある場面に絞る。

## 4. 入力の負担と誤りを減らす

- 目的に必要な情報だけを求める。既に入力済みの情報は、再確認が必要な理由がある場合を除き再入力させない。
- 入力欄には常に確認できるラベルを付け、必要な形式、単位、必須・任意の区別を入力前に示す。入力例をラベルの代用にしない。
- 安全で理解しやすい初期値を選ぶ。利用者の明示的な選択を、画面の再描画や自動調整で上書きしない。
- 貼り付け、入力補完、パスワード管理など、利用者が使う入力支援を妨げない。
- 入力途中の状態を性急に誤りと決めつけない。修正が必要な場合は対象と理由、直し方を近くに示し、他の入力を保持する。
- 未保存の内容を失う移動や終了では、保存、破棄、作業継続を選べるようにする。自動保存を使う場合は、保存状況と失敗を確認できるようにする。

## 5. 状態を正直に伝え、待ち時間も設計する

- 操作を受け付けたら、結果を待つ間も受理されたことを伝える。処理の受理と完了を混同した表示にしない。
- 初期状態、読み込み中、空の状態、処理中、成功、失敗、中断、利用不可を、必要な場面ごとに設計する。情報がない状態と取得に失敗した状態を区別する。
- 進行状況や残り時間は、根拠がある範囲で示す。分からない進捗を数値で装わず、待つ対象と次にできることを伝える。
- 長い処理には、中断、別の作業、後からの確認など、その処理に適した選択肢を設ける。処理中も無関係な操作や停止操作を妨げない。
- 通信や処理の遅れがあっても、入力への応答と画面の安定を保つ。読み込みによる位置のずれで、読みかけの内容や押そうとした操作を移動させない。
- 通知の強さと持続時間は、緊急性と必要な行動に合わせる。作業を止める表示は即時の判断が必要な場合に限り、重要な結果を一時的な通知だけで済ませない。
- 状態が変化しても、入力中の内容、フォーカス、読み進めている位置を不用意に奪わない。

## 6. 失敗しても理解し、回復できるようにする

- 誤操作を防ぐとともに、取り消しや復元を設計する。取り消せない操作は、対象、範囲、失われるものを実行前に示す。
- 失敗時には、何ができなかったか、変更が適用されたか、次に何ができるかを伝える。原因が未確定なら推測を断定しない。
- 再試行で入力を失わせず、同じ送信や破壊的操作が重複しないようにする。完了したか不明な場合は、その状態を確認してから再実行できるようにする。
- 接続断、権限拒否、機器の利用不可、再読み込みなどからの復帰を設計する。利用者の判断や修正を必要としない障害は、可能な範囲で自動回復する。
- 回復時に送信や機器の使用を再開する条件を明確にする。利用者が停止した操作を自動再開しない。
- エラーを利用者の責任にする表現や、行き止まりの案内を避ける。利用者向けの回復手段と、必要に応じて開ける診断情報を用意する。

## 7. アクセシビリティを設計の前提にする

Web UIの基準には[WCAG 2.2](https://www.w3.org/TR/WCAG22/)の適合レベルAAを採用し、A・AAの達成基準と適合要件を満たす。参照日は2026-10-24とし、適用範囲は画面全体と目的達成までの一連の操作とする。以下は設計で特に意識する観点であり、規格の要件を置き換える一覧ではない。

- キーボードで操作でき、フォーカスの位置と順序が分かるようにする。ダイアログの開閉後も、自然な位置から操作を続けられるようにする。
- 見出し、入力、操作、状態には意味が伝わる構造と名前を与え、支援技術でも情報の関係と変化を理解できるようにする。
- 色、音、動き、位置だけで意味を伝えない。文字と操作要素のコントラスト、拡大時の読みやすさ、操作対象の大きさと間隔を確保する。
- 音声や映像で伝える情報には、その内容と目的に応じた文字や代替表現を設ける。重要な操作を、発話や精密な身振りだけに依存させない。
- 動きを減らす設定を尊重し、不要な点滅、視点移動、自動再生を避ける。継続する演出や音は停止・調整できるようにする。
- 理解や操作に必要な時間を確保する。認証や時間制限によって、支援技術の利用や入力の継続を不必要に妨げない。

規格への適合は品質の最低条件とする。実際の利用で目的を達成できるかも確認し、規格が網羅しない困難を放置しない。

## 8. 利用環境が変わっても目的を達成できるようにする

- 画面幅、向き、拡大率、文字量に応じて情報を再配置する。小さい画面でも主要な情報、操作、回復手段を失わせない。
- マウス、タッチ、キーボードなど、利用可能な入力方式に合わせる。ホバーや複雑なジェスチャーだけを必須経路にしない。
- 特定の端末名や寸法を前提に画面を固定しない。対応環境と品質の基準は、利用場面と確認結果から個別設計で定める。
- 処理能力や通信品質が足りないときは、主要な操作と内容を優先し、演出や描画の負荷を調整できるようにする。利用できない機能は理由と代替手段を示す。
- 翻訳、長い名称、異なる文字サイズでも、意味や操作対象が欠けないようにする。日付、数値、単位は利用者が解釈できる表記にする。
- 利用環境の変化や自動調整が体験を大きく変える場合は、その理由を示し、可能な範囲で利用者が調整できるようにする。

## 9. 意思、プライバシー、信頼を守る

- マイク、カメラ、保存、共有などの許可は、必要になる時点で目的と影響を説明して求める。拒否した場合に使える範囲と、後から変更する方法を示す。
- 収集、送信、保存、公開を区別し、何がどこで扱われるかを確認できるようにする。ローカル実行を理由に、記録や機器使用の説明を省略しない。
- 機器の使用中、送信中、録音・録画中の状態を識別できるようにし、停止操作にすぐ到達できるようにする。
- 初期設定は必要最小限の収集・公開とし、任意の利用を同意済みにしない。開始と同程度に、停止、同意の撤回、保存データの管理へ到達しやすくする。
- 拒否や終了を隠す、誤解を招く強調をする、不安や罪悪感で継続を促すなど、意思決定を歪める設計をしない。
- AIの生成内容、推測、認識途中の内容は、確定した事実や実行済みの結果と区別できるようにする。誤認識や生成結果を訂正・破棄し、必要ならやり直せるようにする。
- 利用者が理解・判断できる言葉で伝える。内部の構成名や技術用語は、利用者の判断や問題解決に必要な場面で説明とともに示す。

## 10. 美しさと没入を、使いやすさと両立させる

- 文字、余白、配色、形、動きに一貫した意図を持たせる。装飾は、情報の理解、操作の手応え、体験の魅力に役立つものを選ぶ。
- キャラクターや利用者の活動を主役にし、操作の必要がないときは周辺UIの主張を抑える。停止、状態確認、重要な通知は必要なときに見つけられるようにする。
- 背景やキャラクターが変わっても、文字と操作要素を読み取れるようにする。テーマや演出の違いによって、同じ操作の意味を変えない。
- 動きは状態変化や関係を理解する助けとして使い、操作を待たせるために使わない。文字、音、動きが同時に注意を要求し続ける演出を避ける。
- 会話では、入力を受け付けているか、応答を待っているか、再生中かを把握できるようにする。割り込み、訂正、停止、再開を利用者の意思で行えるようにする。
- キャラクターの表現と、サービスの状態・同意・エラーの説明を識別できるようにする。世界観の表現によって、重要な判断の意味を曖昧にしない。

## 11. 原則を保ち、具体策は更新する

- 共通化するのは、意味、操作の約束、品質の基準とする。画面の目的が異なる場合まで同じ配置や部品を強制しない。
- 色、文字、余白、部品の具体値は、共通の表現体系として個別設計で管理する。テーマ、入力方式、機能が増えても原則を適用できるようにする。
- 操作回数、画面数、性能値などに一律の目標を設けない。利用場面に応じて必要な品質と根拠、確認方法を定める。
- 複数の原則が競合するときは、安全、アクセシビリティ、利用者の意思を満たしたうえで、目的の達成と理解しやすさを優先して具体策を選ぶ。
- 具体策の変更は、利用者への効果と確認結果で判断する。既存実装との一致、流行、実装の容易さだけを採用理由にしない。
- 原則を満たせない案は、代替案と満たせない理由、利用者への影響を個別設計に記録する。例外を前例として一般化せず、前提が変わったときに見直す。
- 新しい技術や知見で原則自体の改訂が必要になった場合は、守るべき利用者の利益と根拠を示して更新する。未検証の新しさだけで品質基準を弱めない。

## 12. 利用者の行動で品質を確かめる

設計時には、対象の変更に関係する利用場面を選び、次の問いで確認する。確認の規模は変更の影響と不確実さに合わせる。

- 初めて見る人が、目的、現在の状態、次の操作を理解できるか。
- 最初の操作から目的の達成、終了まで、不要な説明や試行錯誤なしに進めるか。
- 待ち時間、空の状態、失敗、権限拒否でも、次にできることが分かるか。
- 誤操作や中断から、入力と意図を保って回復できるか。
- キーボードや支援技術、画面の拡大、異なる入力方式でも目的を達成できるか。
- 機器の使用、データの扱い、反映される変更を理解し、拒否・停止・取り消しを選べるか。
- 演出と情報量は、理解、操作、会話への集中を助けているか。

自動検査に加え、関係する一連の操作を実際に試す。不確実な設計は試作や利用者の観察で確かめ、完了できたか、どこで迷ったか、誤操作から戻れたかを改善の根拠にする。滞在時間や操作回数の増加だけを成功としない。評価に必要な記録も、目的と同意に応じて最小限にする。
