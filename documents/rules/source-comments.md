# ソースコードコメント品質

> **対象範囲**: Python / TypeScript / Go を含む本番コード横断のコメント品質、必須対象、省略条件、既存コードへの適用、コメント点検。
> **言語別規約との関係**: 本書はコメントの目的と品質基準を定める。docstring、JSDoc / TSDoc、Go の文書コメントなどの記法と言語固有の対象は [coding-py.md](coding-py.md)、[coding-ts.md](coding-ts.md)、[coding-go.md](coding-go.md) を参照する。

## 0. コメントの目的

ソースコードコメントには、次の 2 つの独立した目的がある。

1. **安全な変更を可能にする** — 契約、制約、失敗条件、副作用、判断理由、リソースの所有権など、誤って変えると壊れる条件を残す。
2. **調査時の理解時間を短縮する** — 処理の全体像、段階、状態遷移、データ表現、離れたコード間の関係を示し、実装を逐一逆解析しなくても目的と流れを把握できるようにする。

公開 API、境界、非自明な制約へのコメントは**必須の下限**であり、それだけ満たせば十分という意味ではない。
安全性を説明していても処理の位置づけが読めないコメント、処理を要約していても変更条件が読めないコメントは、
対象に必要な目的の片方しか満たしていない。

コメントで責務分割を代替しない。ただし、命名や分割を改善したことだけを理由に、複数の処理段階の関係、
業務領域上の意味、非局所的な前後関係まで省略しない。構造とコメントは競合せず、異なる読解コストを下げる。

## 1. 必須対象

### 1.1 契約と変更安全性

次の対象は、言語別の標準文書コメントまたは近接する実装コメントを必須とする。

- 外部公開するモジュール、型、クラス、関数、メソッド、部品、フック、業務上重要な定数
- 通信規約、直列化、保存領域、ファイルシステム、ネットワーク、ブラウザー API、プロセスなどの境界
- スキーマ・構文解析、版、互換性、入力検証、拒否・代替条件
- リソース所有者、後始末、終了処理、goroutine・スレッド・処理担当、ロック、キュー、チャネル
- しきい値、再試行、時間切れ、再試行間隔、緩衝領域、破棄、機能低下、回復などの運用判断
- 座標系、単位、左右定義、時刻基準、フレーム番号、信頼度、`nil`・ゼロ値の意味
- 外部仕様由来の制約、回避策、性能上の判断、壊してはいけない不変条件

### 1.2 調査と理解支援

公開・非公開を問わず、次の対象はコードだけを順に追うより、要約を置いた方が調査時間を短縮できる場合に
コメントを必須とする。

- ファイル・モジュールがシステム内で担当する役割と、隣接モジュールとの責務境界
- 処理の組み立て・処理工程、複数段階の変換や検証を順番に実行する処理
- 状態機械、動作モード切り替え、イベント・コールバックの発生元と状態遷移
- 未加工入力から業務モデル、座標、時刻、フレーム、送受信データなどへの表現変換
- 複数の補助関数、サービス、処理担当、キュー、コールバックにまたがる処理の接続関係
- 名前と型だけでは、上位処理における役割や呼び出し順序が分からない非公開関数・処理群
- 意図的な無処理、早期終了、処理の延期、後段へ委ねる責務
- 一見不要に見える順序、重複、キャッシュ、コピー、待機、値の制限、正規化

「最終的には実装を追えば分かる」は省略理由にならない。コメントは、調査者が読むべき実装範囲を狭め、
現在位置と次に確認すべき処理を判断できるようにするために置く。

## 2. 許容する「何をしているか」のコメント

禁止するのは、コードと同じ粒度で一行ずつ読み上げる逐語説明である。次のように、複数行を一段高い抽象度で
要約し、コード単体には現れない関係を示すコメントは積極的に書く。

- この処理群・関数が処理全体のどの段階にいるか
- 入力をどの表現からどの表現へ変換するか
- この段階で完了させる責務と、後段へ委ねる責務
- 複数の分岐や補助関数が共同で成立させる業務領域上の処理
- イベント、状態、リソースの前後関係

例:

```ts
/*
 * MediaPipe座標をVRMのlocal座標へ正規化する。
 * smoothingとIK補正は後段で行うため、ここでは座標系の変換だけを完了させる。
 */
```

次のような逐語説明は追加しない。

```ts
// 配列をループする。
for (const sample of samples) {
    // sampleを変換する。
    convert(sample);
}
```

## 3. 既存コードへの適用

- **既存コードにコメントがないことは、新規・変更コードでコメントを省略する理由にならない。**
- 周辺コードは命名、契約、依存関係の参考にするが、コメントの量と品質は現行規約に従う。
- 新規ファイル・シンボルは、最初から本書の基準を満たす。
- 既存コードを変更する場合は、変更したシンボル・判断だけでなく、その変更を理解するために読む必要がある
  直接の補助関数、状態、イベント、生存期間、データ変換を **変更理解範囲** として確認する。
- 変更理解範囲に説明不足があれば、今回の変更を安全かつ効率的に調査できる範囲でコメントを
  追加・更新する。無関係なファイル全体の一括改善までは要求しない。
- 未変更範囲で見つけた広域なコメント負債は、対象シンボル、読解上の問題、推奨する改善単位を
  タスク成果物または後続タスクへ記録する。

この方針は既存ファイル全体への無制限な対象拡大を求めるものではない。一方で、変更箇所だけを機械的に見て、
理解に不可欠な近接処理の説明不足を残すことも認めない。

## 4. コメントの省略条件

コメントを省略できるのは、読者が局所的なコード、名前、型から次を誤解なく判断できる場合に限る。

- 上位処理における目的と位置づけ
- 入力と出力、主要な状態変化
- 前後の処理との関係と、順序に意味があるか
- 失敗、副作用、リソースの所有権の有無
- 業務領域固有の表現、単位、制約がないこと

次は単独では有効な省略理由にならない。

- 非公開・内部用である
- 関数や処理群が短い
- 型が付いている
- テストや設計文書を読めば分かる
- 実装を最後まで追えば分かる
- 既存コードや同じディレクトリにコメントがない
- 命名や関数分割を改善した

省略判断に迷う場合は、まず命名、型、関数分割、引数オブジェクト、パッケージ・モジュール境界を改善する。その後も
上記の読者向け情報がコード上に現れない場合はコメントを書く。

## 5. 記法と配置

- 外部公開する API は言語別の標準文書コメントを使い、編集環境・`go doc`・IDE の説明表示から読める形にする。
- ファイル・モジュールコメントは責務一覧だけで終わらせず、処理全体での位置、主要な入力と出力、隣接責務を示す。
- 処理群コメントは対象処理の直前に置く。離れた設計メモとして残さない。
- コメントから設計文書やテストへ誘導する場合も、実コード上の役割、契約、確認観点を近接箇所に書く。
- ソースコード内コメントの言語は各言語規約に従う。エラーメッセージやログの言語方針とは分離する。

## 6. コメント点検

本番コードを変更した場合は、変更したシンボル・処理群・判断と、§3の変更理解範囲を全件点検する。§1の必須コメントの欠落、必要な読者向け情報の不足、古くなったコメントが1件でも残る場合は完了できない。既存コード由来でも、変更理解範囲に含まれる不足は今回の変更範囲として解消する。

通常変更では対象一覧や監査台帳を作らず、実コード上のコメントを修正して、最終報告に `コメント点検: PASS` とだけ記す。コメント数は合否基準にしないが、§4を満たさない省略は認めない。

公開契約、複数の所有者・状態機械、安全な終了などを扱う高リスク変更で、独立レビューのために点検成果物が必要な場合だけ作成する。その場合も、実際の変更リスクに関係する対象へ絞り、少なくとも次の列を持たせる。

| 列                       | 内容                                                                 |
| ------------------------ | -------------------------------------------------------------------- |
| `パス`                   | 対象ファイル                                                         |
| `シンボル・処理群・判断` | 公開シンボル、非公開処理の流れ、状態遷移、境界、経験則など           |
| `種類`                   | API、案内、処理の流れ、データ、生存期間、制約、代替処理など          |
| `現在のコメント`         | 既存コメントの有無と、有る場合に説明している内容                     |
| `読者の疑問`             | コメントがない場合に読者が逆解析しなければならない問い               |
| `読者に必要な知識`       | 安全な変更または短時間の理解に必要で、局所コードだけでは読めない情報 |
| `判断`                   | `維持` / `書き直し` / `削除` / `追加`                                |
| `対応または省略理由`     | 実施した編集、または §4 を満たす具体的な省略理由                     |
| `レビュー担当者メモ`     | レビュー担当・評価担当が実コードと照合する観点                       |

成果物を作る場合、「公開要素のため追加」「既存コメントで十分」「自明」のような定型理由だけでは完了扱いにしない。
何を安全に変更できるようにしたか、またはどの読者の疑問を局所的に解決したかを対象ごとに記録する。

## 7. 禁止事項

- コードを同じ粒度で読み上げるだけのコメント
- 名前や型の言い換えだけで、役割、前後関係、契約のいずれも追加しないコメント
- 公開 API と非自明な制約だけを機械的に埋め、内部処理の流れの理解困難を放置すること
- 「設計文書・テストを参照」とだけ書き、実コード上の目的や確認観点を説明しないコメント
- 古い実装経緯だけを残し、現在の判断を説明しないコメント
- 根拠や削除条件のない「一時的」「回避策」「特別扱い」、TODO
- 実装と同期しない古いコメント
- コメントアウトしたコードの残置

## 8. 実装・レビュー・評価時の読者観点

実装担当、親Codex、レビュー担当、評価担当はコメント数を評価しない。変更差分と変更理解範囲を読み、一般的な開発者が
次の問いへ局所的に答えられるかを確認する。

- このファイル・シンボル・処理群は処理全体のどこを担当するか。
- 入力は何を意味し、どの表現や状態へ変換されるか。
- なぜこの順序、分岐、待機、代替処理が必要か。
- リソースと非同期処理の所有者は誰で、いつ終了するか。
- 失敗、欠損、時間切れ時に何が起きるか。
- 次に読むべき具体的な処理はどこか。

答えるために複数ファイルの実装を広く逆解析する必要があり、命名・型・分割だけでも解消されていない場合は、
読者向けコメントが不足している。新規・変更コードで「既存にもコメントがない」を根拠に省略している場合も
不適合とする。
