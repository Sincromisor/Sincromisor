# コード構造ルール

> **対象範囲**: Python / TypeScript / Go / Markdown をまたぐ物理構造、分割判断、主要アンチパターン。
> **AGENTS.md との関係**: AGENTS.md は初動ガイドと関連文書へのリンクだけを保持する。本書はファイルサイズ、関数サイズ、責務分割の基準を定める。

## 0. 設計思想

読み流せない長さのファイルや関数はバグ温床になる。
行数だけで判断せず、責務の混在、変更時に読む範囲、テストや観測のしやすさも分割判断に含める。

## 1. サイズ閾値

| 区分                | ソフト | ハード | 備考                                                                                 |
| ------------------- | ------ | ------ | ------------------------------------------------------------------------------------ |
| **ファイル**        | 200 行 | 300 行 | import / コメント / 空行を除く。超過時は分割を**検討**(ソフト)/ **原則実施**(ハード) |
| **関数 / メソッド** | 40 行  | 60 行  | 中括弧と返却文を除く。超過時は非公開関数 / 別モジュールへ抽出                        |
| **関数の引数数**    | 3 個   | 4 個   | 超えるなら設定オブジェクト / 要求モデル / 設定モデルに集約                           |
| **ネスト深さ**      | 3 段   | 4 段   | 早期返却 / ガード節 / 関数抽出で平坦化                                               |

「UI 更新 / 外部 I/O / 純粋計算」が同一ファイル・同一関数に混在し始めたら、行数に関わらず分割する。

## 2. 基本原則

- **1 ファイル = 1 主要責務**を基本とする。
    - TypeScript / Python は制御処理 / サービス / 管理処理 / コンポーネント / スキーマ群のいずれかを主役にする。
    - Go は同じ責務を構成する関連公開宣言を同一ファイルに置いてよい。パッケージ全体の凝集度を優先する。
- `index.ts` は **再公開の窓口専用** とし、実装ロジックを書かない。
- 補助関数 / 内部型はファイル内非公開に留め、2 箇所目で利用された時点で別ファイルへ抽出する。
- テスト都合だけで内部要素を公開しない。必要になった時点で独立モジュール化する。
- 「将来のために」分割しない。必要になってから変える。
- コメントで段落分けしたくなったら関数抽出を検討する。ただし抽出後も、複数段階の関係や処理全体での
  位置づけが局所コードから読めない場合は、読者の理解を助けるコメントを残す。
- コメントは責務分割の代替ではないが、構造改善も処理の全体像、状態遷移、データ表現、非局所的な関係を
  説明するコメントの代替ではない。詳細基準は [source-comments.md](source-comments.md) に従う。
- コメント改善中に責務混在、命名不足、型不足、関数分割不足を見つけた場合は、コメントで覆わず構造を直す。
  同タスクで直せない場合は後続対応として、対象シンボル、構造上の理由、推奨する分割単位をタスク成果物
  または後続タスクに記録する。

## 3. 責務分割

- UI 更新、外部 I/O、純粋計算、状態管理、スキーマ検証は混ぜない。
- WebRTC / WebSocket / ファイルハンドル / スレッド / 処理担当などの所有者を明確にし、生成した層が後始末の責務を持つ。
- 環境変数 / 設定は境界で解析し、実装本体では型付き設定として扱う。
- 送受信データ / スキーマ / Pydantic モデル / Zod スキーマ / Go の境界構造体は境界ごとに正本を 1 箇所にする。
- 制御処理 / サービス / 管理処理の引数が増え始めたら、状態や設定の所有境界を見直す。

## 4. アンチパターン

| パターン                                           | 代わりに                                    |
| -------------------------------------------------- | ------------------------------------------- |
| `utils.*` / `helpers.*` / `common.*`               | 責務名で命名する (`ids.ts` / `errors.go`)   |
| `index.ts` に実装を書く                            | 再公開の窓口専用、実装は別ファイル + 再公開 |
| 1 ファイルに複数制御処理 / サービス / 管理処理定義 | 1 ファイル 1 主役                           |
| 100 行超の単一関数                                 | 段階的に非公開関数へ抽出                    |
| テスト用に内部関数を `export`                      | 境界処理や純粋関数を別ファイルへ抽出        |
| コメントアウトで無効化したコードを残す             | 不要コードは削除し、必要ならタスク / ADR    |
| 同じ送受信データ型を複数箇所で再定義               | 契約または境界スキーマを正本化              |

## 5. 例外の扱い

ルールを破る場合は、言語別の `reason` ルールに従って理由を残す。

- Python: 同じ行または直前行に `# reason: <理由>`
- TypeScript: 同じ行に `// reason: <理由>`
- Go: 同じ行または直前行に `// reason: <理由> / 解消条件: <条件>`
- Markdown: 同じ箇条書きまたは直前行に `<!-- reason: <理由> -->`

### フロントエンドの構造検査

フロントエンドの TypeScript / TSX では、`npm run tasks:check:frontend-structure` を使って
`sincromisor-frontend/src/**/*.ts` と `*.tsx` の物理行数を確認する。この検査は既存の 300 行超
ファイルを一覧として一覧化し、`git diff main --name-only -- sincromisor-frontend/src` で
取得した変更ファイルだけを厳格な検査として扱う。`**/__tests__/**`、`*.test.ts`、`*.test.tsx`、
`*.d.ts` は対象外とする。

厳格な検査対象のファイルが 300 行を超える場合は分割する。やむを得ない例外は同じファイル内に
`// reason: structure-threshold-exception <理由>` を置く。このコメントはフロントエンドの構造検査
専用の固定形式であり、理由なしの例外は認めない。
