# コーディング規約(Go)

> **対象範囲**: Go コードベース横断のコーディング規約(モジュール / パッケージ / 型 / エラー / コンテキスト / 並行処理 / ログ / テスト / 設定 / コメント)
> **AGENTS.md との関係**: [AGENTS.md](../../AGENTS.md) は初動ガイドと正本リンクを保持する。サイズ閾値 / 分割判断 / 主要アンチパターンは [code-structure.md](code-structure.md)、コメント品質の横断基準は [source-comments.md](source-comments.md) を正本とし、本書は Go 固有の横断ルールを保持する。

## 0. 設計思想

Go では、言語と標準ツールが用意する単純な流儀を優先する。

1. **負債が残りにくい方向を選ぶ** — 過剰な抽象、暗黙の goroutine、未検査の外部入力、場当たり的な環境変数参照を増やさない
2. **失敗と生存期間を追跡可能にする** — エラーの連鎖、コンテキスト、リソース所有者、goroutine の終了条件を呼び出し側から読める状態にする
3. **機械的な判断をツールへ任せる** — 整形と import 整列を手作業で調整せず、標準ツールの出力を受け入れる

ルールは原則必須。破る場合は同じ行または直前行に `// reason: <理由> / 解消条件: <条件>` を付ける。
公開 API の文書コメントと競合する場合は、文書コメントの後、対象行の直前に置く。

## 1. Go バージョン / モジュール / 依存関係

- Go バージョンとツールチェーンバージョンは `go.mod` の `go` / `toolchain` ディレクティブを正本とする。文書や CI に別のバージョンを重複定義しない
- モジュールは配備 / 公開の単位ごとに 1 つを基本とする。明確な独立公開理由なしに `go.mod` を増やさない
- アプリケーションコードは原則 `internal/`、実行起動処理は `cmd/<command>/` に置く。外部モジュールから import させる契約があるパッケージだけを `internal/` の外へ置く
- `go get` による依存関係追加は、標準ライブラリで足りない理由と保守状態を確認してから行う
- 依存関係を追加・削除した変更では `go mod tidy` 後の `go.mod` / `go.sum` を同じコミットに含める
- `replace` / `exclude` ディレクティブは一時回避に限定し、`// TODO(task-<id>-<slug>):` で削除条件を追跡する

## 2. 整形 / 静的検査 / コミット前チェック

| 項目           | ツール                 |
| -------------- | ---------------------- |
| 整形           | `gofmt`                |
| import 整列    | `goimports`            |
| 静的検査       | `go vet`               |
| テスト         | `go test`              |
| データ競合検出 | `go test -race`        |
| モジュール整合 | `go mod tidy -diff`    |
| Markdown 整形  | Prettier (`*.md` のみ) |

- すべての `.go` ファイルは `gofmt` 済みにする。整形と import 順序の手整形をレビュー論点にしない
- `goimports` を導入したモジュールでは、その出力を import の正本とする。未導入時も標準ライブラリ / 外部提供 / ローカルのグループを分ける
- コミット前の確認項目:
    1. `gofmt -l .` の出力が空
    2. `go vet ./...`
    3. `go test ./...`
    4. 並行処理を変更した場合は `go test -race ./...`
    5. 依存関係を変更した場合は `go mod tidy -diff`
- 静的検査警告抑制は規則名、必要な理由、解消条件を同じ箇所に残す。ファイル / パッケージ全体の警告抑制は禁止する
- モジュール固有の静的検査ツールを追加する場合は、バージョンと設定ファイルをモジュール内で固定し、本節と実行スクリプトを同じ変更で更新する

## 3. Package / 命名 / API

- パッケージ名は短い小文字の単数形を基本とし、アンダースコアや `util` / `common` / `misc` / `types` のような責務不明の名前を使わない
- ファイル名は小文字の snake_case を基本とし、実行環境 / アーキテクチャ / テスト接尾辞は Go ツールチェーンの規約に従う
- 識別子は `MixedCaps` / `mixedCaps` を使う。頭字語は `ID` / `URL` / `HTTP` / `JSON` のように一貫させる
- パッケージ名を公開名に重複させない。`signaling.SignalingClient` ではなく `signaling.Client` のように、import 後の読み方で命名する
- getter に `Get` を付けない。フィールドが `owner` なら `Owner()` とし、setter が必要な場合だけ `SetOwner(...)` とする
- receiver 名は短く、型内で統一する。`this` / `self` / 型名の省略形がファイルごとに揺れる命名を避ける
- 公開シンボルは互換性契約である。必要になるまで公開せず、アプリケーション内部のパッケージは `internal/` に閉じる
- 名前付き戻り値は、defer で結果を書き換えるなど意味が明確な場合だけ使う。長い関数での戻り値を省略した返却は禁止する

## 4. 型 / インターフェース / ジェネリクス

- 構造体は有効なゼロ値を持たせることを優先する。ゼロ値で使用不能な型はコンストラクタと不変条件を文書コメントに書く
- コンストラクタは検証、依存関係注入、リソース確保が必要な場合に置く。フィールド代入だけの `NewX` を機械的に作らない
- インターフェースは原則利用側側で、必要なメソッドだけを定義する。実装パッケージが「将来の差し替え」のために大きなインターフェースを先回りして置かない
- 関数は具体型を返すことを基本とし、呼び出し元が必要とする最小インターフェースを引数で受ける
- `interface{}` ではなく `any` を使う。ただし外部 I/O の一時受け口に限定し、検証後に業務領域の型へ変換する
- インターフェースへのポインタは使わない。ポインタレシーバと値レシーバは型内で混在させず、変更、コピーのコスト、`sync.Mutex` 所有の有無で選ぶ
- ジェネリクスは複数の具体型で同じアルゴリズム / コンテナの重複を除ける場合に使う。業務領域の契約や依存関係注入を曖昧にする目的では使わない
- コピー禁止の値 (`sync.Mutex`、`sync.Once` など)を含む構造体を値渡ししない

## 5. エラー処理 / panic

- 失敗し得る処理は `error` を返す。エラーを `_` へ捨てず、その場で処理するか呼び出し元へ返す
- エラーに操作と最小限の診断文脈を加える: `fmt.Errorf("decode offer: %w", err)`
- 呼び出し元が原因を判定する必要があるエラーだけ `%w` でラップする。ラップしたエラーは API の一部になるため、抽象化の境界を越えて漏らすかを意図的に決める
- エラー判定は文字列比較や直接 `==` ではなく `errors.Is` / `errors.As` を使う。`io.EOF` など標準契約が明示する例外はその契約に従う
- 判定用の定義済みエラー / 独自エラー型は呼び出し元が分岐する必要がある場合だけ公開する
- エラー文字列は英語の小文字で始め、末尾に句点を付けない。機密情報 / 個人情報 / 送受信データ全文を含めない
- 同じエラーを複数層でログしない。回復・破棄・プロセス境界のいずれか、運用判断を行う層で一度だけログする
- `panic` は実装上の誤り、起動時の回復不能な不変条件違反に限定する。通常の I/O、検証、設定不備を panic で処理しない
- `recover` はサーバー / 処理担当のプロセス境界で可用性を守る場合に限定し、未知の panic はスタックを記録して再 panic または安全にプロセスを終了する
- `os.Exit` / `log.Fatal` は `main` の最終的な終了判断に限定する。下位パッケージで呼ばず、`defer` による後始末を飛ばさない

## 6. `context.Context` / 時間切れ

- 要求、セッション、外部 I/O に紐づく処理は `context.Context` を第一引数 `ctx` で受け、呼び出しの連鎖全体へ伝播する
- `Context` を構造体フィールドに保存しない。標準 / 外部提供インターフェースとの適合で避けられない場合は `// reason:` を残す
- `nil` コンテキストや独自のコンテキスト型を使わない。要求の範囲の値を独自引数の入れ物としてコンテキストに詰め込まない
- ライブラリ / 業務領域層で `context.Background()` に置き換えて中断を切らない。最上位のコンテキストは `main`、テスト、明示的な親から独立したタスクの境界だけで生成する
- `context.WithCancel` / `WithTimeout` / `WithDeadline` の中断関数は生成直後に `defer cancel()` するか、所有者へ明示的に渡す
- ネットワーク / プロセス / ブロッキング I/O には期限を設ける。時間切れ値は型付き設定に集約し、処理途中へ特別扱い数値を置かない
- 再試行 / キュー待機 / チャネル送信は `ctx.Done()` で中断可能にし、中断エラーを別の一般エラーに潰さない

## 7. 並行処理 / リソースの生存期間

- goroutine を開始する関数は、終了条件、中断方法、エラーの観測先、終了待機責務を文書コメントまたは近接する生存期間を説明するコメントに書く
- 完了を待たない goroutine は禁止する。プロセスの生存期間と一致するバックグラウンドタスクも最上位のコンテキストと終了処理待機を持たせる
- チャネルは通信と所有権の移転に使い、単純な相互排他をチャネルで再実装しない
- チャネルを終了するのは送信側の所有者とする。受信側や複数生成側が無秩序に終了しない
- チャネルのバッファ容量は処理が追いつかない場合の流量制御の契約である。値の根拠、満杯時の挙動、破棄 / 処理群方針をコメントまたは設計文書に残す
- 共有変更可能な状態は `sync.Mutex` / `RWMutex` / 不可分な操作などで保護し、どのフィールド群を守るロックかを明確にする
- ロック保持中にネットワーク I/O、コールバック、長時間処理を行わない。ロックの取得順序が複数ある場合は不変条件をコメントする
- タイマー / 周期タイマー / 応答本文 / ファイル / 接続は生成した層が停止・終了の責務を持つ。`defer` だけでは遅すぎるループ内リソースは反復処理ごとに明示解放する

## 8. ログ

- 構造化ログは標準ライブラリの `log/slog` を基本とし、パッケージ内で全体で使うロガーを増やさず依存関係として渡す
- `fmt.Print*` / `log.Print*` の直書きは、CLI の利用者向け出力と起動処理中の最終エラー表示を除いて使わない
- メッセージは英語の固定文字列、可変値は型付き属性で渡す。検索語が変わる文字列補間を避ける
- 要求 / セッションを追跡する ID は短縮または仮名化した値を使い、音声認識結果やチャット本文を既定で記録しない
- 機密情報、認証情報、トークン、署名前 URL、個人情報はログに出さない

| レベル  | 用途                                                                     |
| ------- | ------------------------------------------------------------------------ |
| `Error` | 要求 / セッション継続不能、手動対応が必要な失敗                          |
| `Warn`  | 代替処理、再試行、機能縮退、回復済みだが観測すべき異常                   |
| `Info`  | サービスの生存期間、接続、セッション、処理担当の開始・終了               |
| `Debug` | スキーマ検証、キュー長、再試行回数など、原因調査に必要な非機密の中間状態 |

## 9. 外部 I/O / 直列化 / 時刻

- JSON / msgpack / DB / サービス間送受信データは境界専用構造体で受け、検証後に業務領域の型へ変換する。`map[string]any` を内部へ流さない
- 構造体タグは外部契約である。フィールド改名、`omitempty`、`nil` と空のスライス / map の差を破壊的変更として確認する
- 新しい内部管理 API は未知フィールドを拒否する厳格な復号を基本とする。公開済み契約では前方互換性を確認して選ぶ
- `time.Time` は内部計算に使い、地域を明示する。保存・通信は UTC の RFC 3339 文字列を基本とし、表示時だけ JST へ変換する
- `time.Now()` を純粋な業務ロジックに埋め込まない。時刻依存の判断は時刻取得関数 / インターフェースを注入してテスト可能にする
- バイト数、サンプル数、フレーム数、継続時間の単位を型名・フィールド名・コメントのいずれかで明示する

## 10. テスト

- テスト実行ツールは `go test` を使い、ファイル名は `*_test.go`、テスト関数は `TestXxx` とする
- 入出力の組み合わせを検証する場合は表形式のテストと `t.Run` を基本とし、事例名に失敗条件が分かる説明を付ける
- 表明検査のライブラリを前提にせず、失敗メッセージに `got` / `want` と判断に必要な入力を含める。機密情報 / 個人情報は含めない
- `t.Parallel()` は全体共通の状態、ポート、ファイルシステム、時計を共有しないテストにだけ付ける
- `time.Sleep` で非同期処理の完了を待たない。チャネル、フック、模擬時計、期限付きの成立条件で同期する
- 固定データ / 期待結果ファイルは `testdata/` に置き、生成・更新条件をテストまたはタスク成果物に残す
- 解析処理、直列化、外部入力境界には相互変換の往復テスト、不正入力のテスト、必要に応じてファジングテストを置く
- ネットワーク、GPU、実機器、外部サービスに依存する結合テストは通常の単体テストと明示的に分離する
- goroutine、チャネル、ロックを変更した場合は、正常終了だけでなく中断、時間切れ、エラー、早期終了のリークを検証する

## 11. 環境変数 / 設定

- 環境変数 / フラグは `main` 近傍の設定読み込み処理に集約し、検証済みの型付き設定を下流へ渡す
- 業務領域 / サービス本体で `os.Getenv` / `os.LookupEnv` を直参照しない
- 必須値の欠損、不正な継続時間 / URL / 列挙値は起動時にフィールド名を含むエラーとして返す。機密情報の値自体は含めない
- 新規環境変数は同じ変更で [examples/compose.env](../../examples/compose.env)、Docker Composeの環境変数設定、設定読み込み処理、関連設計文書を同期する
- 既定値は一箇所に置き、環境変数の設定例、フラグ、実装で重複定義しない

## 12. 言語ポリシー

| 対象                     | 言語                                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------- |
| 識別子                   | 英語                                                                                            |
| ログ / エラーメッセージ  | 英語（運用時に検索しやすくするため）                                                            |
| ソースコード内のコメント | 日本語。外部利用を前提とする公開モジュールは英語も可                                            |
| Markdown 文書            | 日本語。[coding-md.md](coding-md.md) を正本とする                                               |
| 利用者向けメッセージ     | 日本語                                                                                          |
| コミットメッセージ       | 日本語。[tasks/README.md](../../tasks/README.md) の Conventional Commits ベース規約を正本とする |

Go の文書コメントは日本語で書く場合も、公開シンボル名または `Package <name>` から始め、
`go doc` で単独表示されても契約が分かる完全な文にする。

## 13. TODO / 廃止予定

- 形式: `// TODO(task-<id>-<slug>): <内容> / 削除条件: <条件>`。標準化したタスク ID と削除条件のない TODO は禁止する
- 旧 `TODO(TASK-yymmddhhmmss): ...` は移行互換として許容する。新規 TODO には使わない
- `FIXME` / `HACK` は使わず TODO に統一する
- 廃止予定な公開シンボルは `// Deprecated: <代替と削除条件>` 形式にし、同タスクまたは後続タスクで削除を追跡する
- コメントアウトしたコードを残さない。不要コードは削除し、判断履歴はタスク / ADR に残す

## 14. ソースコードコメント品質

コメント品質の目的、既存コードへの適用、省略条件、点検の記録形式は [source-comments.md](source-comments.md) を
正本とする。Go でも公開API、境界、非自明な判断、リソースの生存期間は必須の下限であり、
それだけで十分とは判断しない。パッケージ内の処理の組み立て、goroutine 間の接続、状態遷移、
データ変換を一般的な開発者が短時間で調査できる状態にする。

### 14.1 必須対象

- パッケージコメントとすべての公開型 / 関数 / メソッド / const / var
- 単位、ゼロ値、`nil`、所有権、検証条件が名前と型だけでは分からない公開フィールド
- 通信規約 / 直列化 / ファイルシステム / ネットワーク / プロセスなど外部境界
- goroutine、チャネル、ロック、後始末所有者、終了処理順序
- 時間切れ、バッファ容量、再試行、再試行間隔、破棄、代替処理などの運用判断
- 単位、時刻基準、バージョン、互換性、`nil` / ゼロ値の意味
- 複数の関数 / goroutine / チャネルを接続する処理の組み立てと終了までの処理の流れ
- 状態遷移、イベント生成元、未加工の送受信データから業務領域構造体への変換
- 名前と型だけではパッケージ内での役割が分からない非公開関数 / 処理群

公開シンボルの文書コメントはシンボル名から始め、完全な文にする。日本語の場合も `ParseOffer は...。` の形式を使う。

```go
// ParseOffer は外部から受信した SDP offer を内部表現へ変換する。
//
// 未知の type と空の SDP は、下流の PeerConnection を生成する前に拒否する。
// JSON の field 追加は受理するが、既存 field の意味変更は契約変更として扱う。
func ParseOffer(raw []byte) (Offer, error) {
	// ...
}
```

### 14.2 最低限含める内容

| 対象                     | 書く内容                                                                |
| ------------------------ | ----------------------------------------------------------------------- |
| 公開API                  | 責務、入力境界、戻り値、エラー条件、副作用、非対象                      |
| 境界 / 解析処理          | 生の値、検証、互換性、拒否条件、呼び出し元に返すエラー                  |
| 並行処理 / 生存期間      | 所有者、開始・終了条件、中断 / 終了待機、終了順序、リークを防ぐ不変条件 |
| しきい値 / 代替処理      | 値の意味と根拠、発動条件、誤調整時の失敗モード、変更時の確認先          |
| 単位 / 時間 / バージョン | 単位、基準時刻、バージョンの意味、変換・丸め・互換性条件                |

非公開補助処理は、名前、型、周辺 API から責務が明らかで、境界 / 経験則 / 生存期間を持たない場合に限り
コメントを省略できる。ただし非公開、短い、型がある、既存コードにコメントがないことは単独の省略理由に
ならない。上位処理の流れでの位置、状態変化、前後関係まで局所的に読めるかを確認する。

### 14.3 点検と禁止事項

コメント点検はファイル単位ではなくシンボル / 処理群 / 判断 / 処理の流れ単位で
`keep` / `rewrite` / `delete` / `add` を判断する。変更した API、境界、goroutine、経験則と
変更理解範囲を確認し、読者の疑問と読者に必要な知識を記録する。
関連する古くなったコメントは同じ変更で更新または削除する。

禁止するコメント:

- `// error を返す`、`// goroutine を開始する` のような処理説明だけのコメント
- 公開API と生存期間だけを機械的に埋め、内部処理の流れの理解困難を放置すること
- 名前や型から分かる責務要約だけで、失敗条件、副作用、所有権を説明しない文書コメント
- しきい値 / バッファ容量の存在だけを書き、根拠や満杯時の挙動を説明しないコメント
- 「設計文書やテストを参照」とだけ書き、実コード上の契約を示さないコメント
- 理由や削除条件のない `temporary` / `workaround` / TODO
- `private`、`短い`、`型がある`、`既存コードにもない` だけを省略理由にすること
- 実装と同期しない履歴メモ、古くなったコメント、コメントアウトしたコード

## 15. その他の負債抑制ルール

- 特別扱い数値 / 文字列は業務領域上の意味を持つ名前へ集約する。ただし一度しか使わず意味が自明な値まで定数化しない
- パッケージ全体の変更可能な状態を避ける。必要な状態と依存関係は所有者構造体に集約する
- `init()` は登録など避けられないパッケージ初期化に限定し、I/O、goroutine 起動、設定読み込みを行わない
- `defer` のエラーを無視しない。書き出し / 終了の失敗が結果へ影響する場合は名前付き補助処理などで呼び出し元に返す
- `reflect` / `unsafe` / `//go:linkname` は標準的な型表現で実現できない場合に限定し、理由、不変条件、テスト、削除条件を残す
- ビルドタグと環境固有のファイルは対象環境と代替処理を明示し、通常ビルドで実装欠落を起こさない
- 「将来の差し替え」のためのパッケージ、インターフェース、生成処理を作らない。具体的な複数実装またはテスト用の差し替え境界が必要になった時点で抽出する

## 16. 参照した外部規約

- [Error Values FAQ](https://go.dev/wiki/ErrorValueFAQ): ラップされたエラーと `errors.Is` / `errors.As` の扱い
- [Data Race Detector](https://go.dev/doc/articles/race_detector): `go test -race` の適用範囲と制約
- [`log/slog` パッケージ](https://pkg.go.dev/log/slog): 構造化ログとレベル / 属性の標準 API
