# 質問回答レポート：単眼WebカメラによるVRM上半身モーション品質改善

本回答は、**MediaPipe Pose / Hand / Face Landmarker + VRM-1.0 + Three.js** を前提に、設計・実装担当者がパラメータ設計や実装順序を決めるための回答として整理します。MediaPipe Pose は2D画像座標と3D ワールド座標の特徴点、Hand Landmarker は手の特徴点・ワールド座標の特徴点・左右判定、Face Landmarker は3D 顔の特徴点・ブレンドシェイプ・顔の変換行列を出力できますが、ここでは表情・視線は扱わず、身体・頭部・腕・手首・指の制御に限定します。([Google AI for Developers][1])

---

## 1. 最初に品質差が出る領域と実装順

結論として、**最初に品質差が出るのは「信頼度評価」と「時系列処理」**です。IKは重要ですが、入力が不安定なまま高品質なIKを実装しても、肘反転、手首暴れ、肩崩れを増幅することがあります。

推奨順は次です。

| 順位 | 領域                                        | 理由                                                     |
| ---: | ------------------------------------------- | -------------------------------------------------------- |
|    0 | 記録・再生・デバッグ表示                    | 調整結果を再現できなければ品質改善が不可能               |
|    1 | 最小キャリブレーション                      | 肩幅・腕長・正面基準がないと、IK以前にスケールが破綻する |
|    2 | 信頼度評価                                  | 悪い観測値をそのまま使わないための土台                   |
|    3 | 時系列処理                                  | 細かな揺れ、一時欠損、再検出ジャンプを直接抑える         |
|    4 | 基本IK / 動作の変換                         | 安定した目標をVRMボーンへ変換する                        |
|    5 | 詳細キャリブレーション / アバターの調整情報 | モデル差、VRoid体型差を吸収する                          |
|    6 | セマンティック動作化                        | 「かわいい」「意図が伝わる」動作へ昇華する               |

実装上は、**IKを後回しにする**というより、最初のIKは簡素でよいので、同時に信頼性 → 時系列状態 → 標準状態の流れを先に作るのが重要です。

MediaPipeのWeb向けLandmarkerは `detectForVideo()` 系が同期実行でUIスレッドをブロックするため、必要に応じてWeb Workerに分離できます。これは単なる性能最適化ではなく、検出タイミングの揺れを抑える意味でも有効です。([Google AI for Developers][1])

## 2. かわいい/自然に見せる上で最も避けるべき破綻

専門家視点では、避けるべき順序は次です。

| 優先度 | 破綻                            | 理由                                                       |
| -----: | ------------------------------- | ---------------------------------------------------------- |
|      1 | **胴体・頭部の細かな揺れ**      | キャラクター全体が不安定に見え、生命感ではなく故障感になる |
|      2 | **肘反転**                      | 腕の構造が一瞬で裏返り、視覚的に非常に目立つ               |
|      3 | **肩崩れ / 肩が胴体にめり込む** | VRoid系では肩・胸・袖まわりの破綻が見た目に直結する        |
|      4 | **手首ロール暴れ**              | 手先の回転は小さくても目立ち、操り人形感が出る             |
|      5 | **腕の伸び切り**                | かわいさより「硬い」「無理している」印象になる             |
|      6 | 指のちらつき                    | 目立つが、腕・肩・頭ほど致命的ではない                     |

最も重要なのは、**大きい部位ほど安定、小さい部位ほど表現的に動かす**という設計です。胴体・頭・肩は控えめに、手・指・短いジェスチャーはやや表現的に、という分担が自然です。

## 3. 初期キャリブレーションで取ってもらう姿勢

推奨は、**Tポーズではなく「正面自然姿勢 + 軽いAポーズ」**です。TポーズはWebカメラでは手が画面外に出やすく、肩も不自然に上がるため、上半身用途では実用性が低いです。

現実的な手順は次です。

| 手順 |       時間 | 姿勢                                                 | 取得する値                       |
| ---: | ---------: | ---------------------------------------------------- | -------------------------------- |
|    1 | 1.5〜2.0秒 | 正面を向き、肩の力を抜く。両肩・顔・肘・手首が画面内 | 中立姿勢体幹、肩幅、頭部中立姿勢 |
|    2 | 1.5〜2.0秒 | 腕を体から20〜30°ほど開く。肘は軽く曲げる            | 上腕・前腕長さ、肘平面初期値     |
|    3 |      1.0秒 | 両手を胸〜腰の高さで軽く開く                         | 手倍率、指中立姿勢               |
|    4 | 任意 1.0秒 | 顔を少し左右に向ける                                 | 頭部ヨー代替処理確認             |

合計で **4〜6秒程度**が現実的です。UI上は「両肩と両手が画面に入る位置で、正面を向いてください」から始め、次に「肘を軽く曲げ、腕を少し開いてください」と案内するのがよいです。

## 4. 初期キャリブレーション失敗時の症状とオンライン補正

初期キャリブレーションに失敗すると、見た目には次の症状が出ます。

| 失敗項目             | 見た目の症状                              |
| -------------------- | ----------------------------------------- |
| 肩幅過小             | 腕が胴体に寄りすぎる、胸の前で潰れる      |
| 肩幅過大             | 腕が常に外へ開く                          |
| 上腕 / 前腕長過小    | 腕がすぐ伸び切る、手先が届かない          |
| 上腕 / 前腕長過大    | 腕が曲がりすぎる、手が不自然に届きすぎる  |
| 中立姿勢体幹ヨー失敗 | キャラが常に斜めを向く                    |
| 頭部中立姿勢失敗     | 首が常に傾く                              |
| 手倍率失敗           | 指曲げ判定が過敏または鈍くなる            |
| カメラ距離推定失敗   | 奥行き方向の動きが大きすぎる / 小さすぎる |

オンラインキャリブレーションで安全に補正できる項目と、避けるべき項目は分けます。

| 分類         | 項目                                | 方針                                                   |
| ------------ | ----------------------------------- | ------------------------------------------------------ |
| 安全に補正可 | 肩幅の低速更新                      | 高信頼度・正面・中立姿勢に近い時のみ、数十秒単位で更新 |
| 安全に補正可 | 体幹中心 / 中立姿勢ヨーの微修正     | 急に変えず、非常に低い係数で更新                       |
| 安全に補正可 | カメラ画面内の構図 / 身体寸法の倍率 | カメラ距離変化への追従として有効                       |
| 安全に補正可 | 手開閉基準                          | 高信頼度の開き手・閉じ手を蓄積して補正                 |
| 原則固定     | アバターの骨の長さ                  | モデル固有値なので変えない                             |
| 原則固定     | VRM 初期姿勢の回転補正量            | 動的変更するとモデル全体が崩れる                       |
| 原則固定     | 左右判定対応付け                    | オンラインで揺らすと左右入れ替え事故が起きる           |
| 原則固定     | 関節可動域                          | ユーザー姿勢に合わせて変えると破綻を許容してしまう     |
| 原則固定     | 手のひらの基底の軸定義              | 実装規約なので動的補正しない                           |

オンライン補正は、**「人間側の観測基準」はゆっくり補正し、「アバター側の構造」は固定**が基本です。VRM-1.0ではモデルごとの初期姿勢の回転や任意ボーン差分を考慮する必要があり、NormalizedLocalRotationのような中間形式で吸収する設計が示されています。([GitHub][2])

## 5. MediaPipe ワールド座標の特徴点で信用できる成分

単眼Webカメラでは、ワールド座標の特徴点を絶対3D位置として扱うべきではありません。ただし、全てが無価値ではありません。

| 成分                       | 信用度 | 使い方                                 |
| -------------------------- | -----: | -------------------------------------- |
| 画像上の左右 `x`           |     高 | 肩幅、手の左右位置、開き具合           |
| 画像上の上下 `y`           |     高 | 手上げ、頭/肩/腰の相対高さ             |
| ワールド座標の左右相対方向 | 中〜高 | 肩→肘、肩線                            |
| ワールド座標の上下相対方向 |     中 | 腕仰角、体幹の上方向                   |
| ワールド座標の奥行き `z`   | 低〜中 | 前出し具合の補助。単独判定は禁止       |
| 接続された関節の相対角度   |     中 | elbowFlexionHint、腕の向き             |
| 骨の長さの絶対値           |     低 | モーションには使わず、信頼度評価に使う |
| 身体ヨー                   |     中 | 肩線単独ではなくFaceと混ぜる           |
| 手首絶対位置               |     低 | アバター手先目標に直結しない           |

実装方針は、**左右・上下・相対方向は使う、奥行きは圧縮して使う、絶対距離は信頼度評価に回す**です。

## 6. 標準化した腕状態の安定推定

`elevation / forwardness / openness / elbowFlexionHint` は、特徴点座標そのものではなく、体幹ローカル空間で計算します。

まず体幹基準を作ります。

```text
U = normalize(shoulderCenter - hipCenter)        // 上
R = normalize(rightShoulder - leftShoulder)      // 右
F = normalize(cross(R, U))                       // 前
```

腕ごとの特徴量は次のように計算します。

| 状態量           | 推定方法                                           | 注意点                                             |
| ---------------- | -------------------------------------------------- | -------------------------------------------------- |
| 仰角             | `dot(shoulder→wrist, U)` または `dot(upperArm, U)` | 手首だけだと手先ノイズに弱いため`upperArm`も混ぜる |
| 開き具合         | `dot(shoulder→wrist, ±R)`                          | 左右の符号を正規化し、体から横に開く度合いにする   |
| 前出し具合       | `dot(shoulder→wrist, F)`                           | ワールド座標 zだけでなく2D短縮・手サイズも使う     |
| elbowFlexionHint | `angle(shoulder-elbow-wrist)`                      | 腕が伸び切ると不安定なので信頼度を下げる           |

「前に出す」と「横に広げる」の判定は、単一値ではなくスコアで行います。

```text
sideScore =
  正規化した手首の左右方向の変位
+ 正規化した肘の左右方向の変位

forwardScore =
  圧縮したワールド座標z方向の手首変位
+ 投影による腕の短縮
+ 手の見かけの大きさの増加
- 左右方向への開きに対する減点
```

目安は次です。

| 判定       | 条件例                                      |
| ---------- | ------------------------------------------- |
| 横に広げる | `openness > 0.55` かつ `forwardness < 0.35` |
| 前に出す   | `forwardness > 0.45` かつ `openness < 0.55` |
| 斜め前     | `forwardness > 0.35` かつ `openness > 0.35` |
| 不明       | 手・姿勢信頼度低、または腕が画面端          |

奥行きは弱いため、`forwardness` は必ずヒステリシスを入れます。例えば、前方向に入る閾値を0.50、抜ける閾値を0.35にします。

## 7. 肘曲がる方向ベクトルのブレンド比率と状態遷移

肘曲がる方向ベクトルは、実測値・前フレーム・体幹代替処理を状態に応じて混ぜます。

| 状態       | 条件                          |     実測肘 | 前フレーム |   代替処理 |
| ---------- | ----------------------------- | ---------: | ---------: | ---------: |
| Stable     | 腕信頼度 > 0.75、肘角度が安定 | 0.65〜0.80 | 0.15〜0.30 | 0.05〜0.10 |
| Uncertain  | 0.45〜0.75、奥行き不安定      | 0.25〜0.45 | 0.40〜0.60 | 0.10〜0.20 |
| Extended   | 腕が伸び切り気味              | 0.10〜0.25 | 0.50〜0.70 | 0.20〜0.30 |
| Lost       | 信頼度 < 0.45が数フレーム継続 |       0.00 | 0.60〜0.80 | 0.20〜0.40 |
| Recovering | 再検出後200〜400ms            |  0.20→0.70 |  0.60→0.20 |  0.20→0.10 |

破綻防止の条件は次です。

```text
if dot(measuredPole, previousPole) < 0:
    measuredPole を拒否、または重みを大幅に下げる

if angularChange(measuredPole, previousPole) > 60°/frame:
    measuredPoleWeight *= 0.2

if elbowFlexion < 15°:
    poleは実測ではなく previous + fallback 優先
```

代替処理は、左右の肘が体の外側へ出るように設計します。

```text
leftFallbackPole  = normalize(-R * 0.8 + -U * 0.2 + F * 0.1)
rightFallbackPole = normalize( R * 0.8 + -U * 0.2 + F * 0.1)
```

## 8. VRoid系の小柄・大きな頭キャラ向け圧縮比率

VRoid系キャラクターでは、現実の人間より頭が大きく、肩幅が狭く、腕が短く見えることがあります。したがって、実写の手先位置をそのまま使わず、**到達距離・肩幅・奥行きを圧縮**します。

初期値としては次が使いやすいです。

| 項目               | 初期値 | 推奨レンジ |
| ------------------ | -----: | ---------: |
| 腕到達距離倍率     |   0.92 | 0.88〜0.96 |
| 左右方向肩倍率     |   0.90 | 0.80〜0.98 |
| 上下方向腕倍率     |   0.95 | 0.90〜1.00 |
| 奥行き圧縮         |   0.60 | 0.45〜0.75 |
| 肘外向き偏りの補正 |   0.25 | 0.15〜0.35 |
| 手首ロール反映率   |   0.40 | 0.25〜0.60 |
| 胸追従             |   0.55 | 0.40〜0.70 |

特に重要なのは奥行きの圧縮です。単眼カメラの奥行きをそのまま使うと、手を前に出したときに腕が伸び切ったり、顔や胸にめり込みやすくなります。

実装では、次のように部位別にスケールします。

```text
avatarTarget.x = humanLocal.x * lateralScale
avatarTarget.y = humanLocal.y * verticalScale
avatarTarget.z = humanLocal.z * depthCompression
avatarTarget   = clampToReach(avatarTarget, armReachScale)
```

## 9. 肩・鎖骨・胸の補正目安

肩・鎖骨・胸の補正は、上半身品質にかなり効きます。腕を上げても`upperArm`だけを回すと、肩が胴体に刺さったように見えます。

腕の仰角別の目安は次です。

| 腕の高さ | 肩ボーン | `upperChest` |     胸 |
| -------- | -------: | -----------: | -----: |
| 0〜30°   |    0〜3° |           0° |     0° |
| 30〜70°  |    3〜8° |        2〜6° |  0〜3° |
| 70〜110° |   8〜15° |       6〜12° |  3〜8° |
| 110°以上 |  12〜20° |      10〜18° | 5〜12° |

分配の考え方は次です。

```text
armRaiseAssist = smoothstep(30°, 110°, armElevation)

shoulderLift = armRaiseAssist * 15°
upperChest   = armRaiseAssist * 10°
chest        = armRaiseAssist * 5°
```

片腕だけ上げる場合は、胸全体を大きく傾けすぎないようにします。両腕を上げる場合は、`upperChest`と胸を少し後ろへ倒すと自然です。

| ケース           | 補正                                       |
| ---------------- | ------------------------------------------ |
| 片腕上げ         | その側の肩を主に使い、`upperChest`は控えめ |
| 両腕上げ         | `upperChest`・胸を少し使う                 |
| 肩ボーンなし     | `upperChest`と`upperArm`側へ分配           |
| `upperChest`なし | 胸へ60〜70%、背骨へ30〜40%吸収             |

VRM-1.0では `upperChest` や `leftShoulder` などはモデルによって存在しない場合があり、任意ボーン差分を考慮する必要があります。([GitHub][2])

## 10. 頭部姿勢：Face 行列とPose由来代替処理

頭部姿勢は、Face Landmarkerの顔の変換行列を主入力にするのがよいです。Face Landmarkerは顔特徴点に加えて、エフェクト描画などに使える変換行列を出力できます。([Google AI for Developers][3])

推奨ブレンドは次です。

| 状態        |  Face 行列 | Pose 鼻・目・耳 | 前フレームの値・胸 |
| ----------- | ---------: | --------------: | -----------------: |
| Faceが安定  | 0.80〜0.95 |      0.05〜0.15 |         0.00〜0.05 |
| Face 中程度 | 0.45〜0.65 |      0.20〜0.35 |         0.10〜0.20 |
| Face 不安定 | 0.10〜0.30 |      0.30〜0.50 |         0.30〜0.50 |
| Face 未検出 |       0.00 |      0.00〜0.30 |         0.70〜1.00 |

Face 行列を信用する条件は次です。

```text
facePresence > 0.70
trackingConfidence > 0.70
顔外接矩形が画面端に近すぎない
前フレームからの角度変化が大きすぎない
顔特徴点の左右対称性が極端に崩れていない
```

Pose 代替処理では、鼻・目・耳から頭の向きを推定できますが、耳が片側しか見えない横向きでは不安定になります。そのため、Pose由来は主に **ヨーの補助** として使い、ピッチ・ロールは弱く扱います。

欠落時は、頭を即中立姿勢に戻さず、**`upperChest`の向きへ0.5〜1.0秒程度で戻す**のが自然です。

## 11. 手のひらの基底による手首姿勢で信用する軸・捨てる軸

Hand Landmarkerは21点の手特徴点とワールド座標の特徴点を返します。手の特徴点の `z` は手首を原点とする奥行きで、値が小さいほどカメラに近いと説明されています。([Google AI for Developers][4])

手首姿勢では、次の基底を作ります。

```text
palmRight  = normalize(indexMcp - pinkyMcp)
palmUp     = normalize(middleMcp - wrist)
palmNormal = normalize(cross(palmRight, palmUp))
```

ただし、状況に応じて信用する軸を変えます。

| 手の見え方     | 信用する軸                    | 捨てる/弱める軸        |
| -------------- | ----------------------------- | ---------------------- |
| 手のひらが正面 | palmRight, palmUp, palmNormal | ほぼ全て使用可         |
| 手の甲が正面   | palmRight, palmUp             | 法線の符号反転に注意   |
| 手が横向き     | palmUp / 指方向               | palmNormal, 手首ロール |
| 顔や物で隠れる | 前フレームの値手首向き        | 手のひらの基底全体     |
| 指が重なる     | 手首→中指方向                 | 指の開き, ロール       |
| 手が小さい     | 低周波成分のみ                | ロール, 細かな回転     |

手首ロールは最も暴れやすいため、次の扱いにします。

```text
手首ピッチ・ヨー: 中程度に反映
手首ロール: 強く平滑化、または前腕ねじれへ分配
```

目安は、ロール成分の反映を **25〜60%** に抑え、残りは前腕ねじれまたは中立姿勢へ逃がします。

## 12. VRMキャラで破綻しにくい指制御の粒度

指は、各関節の3D回転を完全再現しようとしない方が安定します。推奨優先順位は次です。

| 優先度 | 粒度                     | 内容                                 |
| -----: | ------------------------ | ------------------------------------ |
|      1 | 全指まとめた開閉         | 最も安定。初期実装向き               |
|      2 | 親指だけ別 + 他4指まとめ | サムズアップ、握り手の自然さが上がる |
|      3 | 親指・人差し指・他3指    | 指差し、ピースの準備になる           |
|      4 | 各指曲げのみ             | 実用上の高品質ライン                 |
|      5 | 各指曲げ + 限定指の開き  | 表現力は上がるがちらつきやすい       |
|      6 | 各関節3D回転             | 単眼Webカメラでは非推奨              |

最初の品質ラインとしては、**親指・人差し指・中指・薬指小指グループ**の4系統で十分です。

```ts
type PracticalFingerPose = {
    thumb: { curl: number; oppose: number };
    index: { curl: number; spread?: number };
    middle: { curl: number };
    ringLittle: { curl: number };
};
```

VRM指ボーンへの割り当ては、曲げを各関節へ分配します。

| 指ボーン | 曲げ配分 |
| -------- | -------: |
| 基部     |  50〜60% |
| 中間部   |  30〜40% |
| 末端     |  10〜20% |

指の開きは入れるとしても、人差し指・小指に限定し、±10〜15°程度から始めるのが安全です。

## 13. 手が一時的に消えた場合の部位別挙動

手が消えたときに全てを即中立姿勢へ戻すと不自然です。部位ごとに挙動を変えます。

| 部位                         | 0〜200ms                                      | 200〜700ms                       | 700ms以降          |
| ---------------------------- | --------------------------------------------- | -------------------------------- | ------------------ |
| 腕                           | Pose 手首があれば継続。なければ速度減衰で予測 | 無理のない自然姿勢へゆっくり戻す | 初期姿勢寄りに安定 |
| 肘曲がる方向                 | 前フレーム保持 + 代替処理混合                 | 代替処理比率を上げる             | 代替処理中心       |
| 手首                         | 直前姿勢保持                                  | 前腕に沿った中立姿勢へ戻す       | 中立姿勢維持       |
| 指                           | 直前姿勢保持                                  | 半開き中立姿勢へ戻す             | 力を抜いた手       |
| 意味に基づく動作ジェスチャー | 200〜300msだけ保持                            | 徐々に弱める                     | 非アクティブ       |

推奨状態遷移は次です。

```text
Tracked
  ↓ 信頼度低下 2〜3 フレーム
Suspect
  ↓ 200ms復帰なし
Predicted
  ↓ 700ms復帰なし
Lost
  ↓ 再検出
Recovering
  ↓ 200〜500ms 合成
Tracked
```

Hand Landmarker自体も映像・実時間のストリームモードでは手存在確率や追跡信頼度に応じて検出器と追跡を切り替える設計になっているため、アプリ側でも同様に状態を持つべきです。([Google AI for Developers][5])

## 14. フィルタの使い分けと推奨パラメータ

フィルタは1種類で全身にかけるのではなく、目的別に使い分けます。One Euro Filterは、低速時に細かな揺れを抑え、高速時に遅延を減らすための速度適応型低域通過フィルタで、公式ページでも `mincutoff` と `beta` を段階的に調整する手順が示されています。([Géry Casiez][6])

| フィルタ             | 使いどころ                                       |
| -------------------- | ------------------------------------------------ |
| EMA                  | 低周波の品質スコア、キャリブレーション値、UI表示 |
| One Euro Filter      | 手首目標、頭部、標準化したスカラー               |
| カルマンフィルタ     | 手・関節の一時欠落、予測、再検出復帰             |
| クォータニオン平滑化 | 最終ボーン回転、頭部・胸・手首回転               |

初期値の目安です。One Euro Filterの `beta` は実装単位に依存するため、以下は**体長正規化座標・角度正規化値**を前提にした出発点です。

| 部位              | minCutoff |   速度係数 | 備考                       |
| ----------------- | --------: | ---------: | -------------------------- |
| 体幹回転          |  0.5〜0.8 | 0.05〜0.15 | 安定重視                   |
| 胸 / `upperChest` |  0.7〜1.2 | 0.05〜0.20 | 胴体細かな揺れ抑制         |
| 頭部回転          |  1.0〜1.8 | 0.10〜0.30 | 会話用途では遅れすぎに注意 |
| 手首目標          |  1.5〜2.5 | 0.20〜0.60 | 手の反応性重視             |
| 肘の曲がる方向    |  0.8〜1.5 | 0.05〜0.20 | 反転防止を優先             |
| 手首ロール        |  0.5〜1.2 | 0.03〜0.15 | 強く抑える                 |
| 指の曲げ          |  3.0〜6.0 | 0.20〜1.00 | ヒステリシス併用           |

遅延許容量の実用目安は次です。

| 部位 | 追加遅延の目標 |
| ---- | -------------: |
| 指   |       30〜60ms |
| 手先 |       50〜90ms |
| 頭   |      50〜100ms |
| 胴体 |      80〜150ms |
| 肩   |      80〜150ms |

会話アプリでは、**手・頭の体感遅延は100ms前後以内**を目標にしたいです。WebパフォーマンスのRAILモデルでも、ユーザー入力に対する可視応答は100ms以内を目標とする考え方が示されています。アバターモーションは通常のUI入力とは異なりますが、体感の基準値として有用です。([web.dev][7])

## 15. Pose起点Hand/Face ROI化の効果と判断基準

Pose起点でHand/FaceのROIを切る方式は、特に**手が小さく写る場合、速く動く場合、左右取り違えが起きる場合**に効果が大きいです。

MediaPipe Holisticの設計では、まず姿勢を推定し、その特徴点から左右の手と顔のROIを導出し、元の解像度の切り出しを各専用モデルに入力します。この構成により、速い動きへの反応、左右の意味に基づく動作整合性、手・顔の解像度問題を改善する意図が説明されています。([Google Research][8])

判断基準は次です。

| 条件           | 全画面Handで十分          | ROI化推奨                |
| -------------- | ------------------------- | ------------------------ |
| カメラ距離     | 近い                      | 遠い                     |
| 手の画面サイズ | 手外接矩形が80〜120px以上 | 80px未満が多い           |
| 動き           | ゆっくり                  | 速い手振りが多い         |
| 人数           | 1人固定                   | 複数人/背景に人          |
| 左右入れ替え   | ほぼ起きない              | 腕交差や顔前の手で起きる |
| 顔と手の重なり | 少ない                    | 多い                     |
| 品質要求       | 大まかな動きでよい        | 指・手首まで使う         |

ROI化で期待すべき主な改善は、平均誤差よりも **一時欠損率、左右取り違え、再検出時のジャンプ** の低減です。

## 16. カメラ品質スコアをUXへ反映する方法

UXでは、内部用語を出さず、ユーザーが直せる行動だけを提示します。警告は同時に1〜2個までに抑えるのがよいです。

| 検出した問題             | 表示するガイド                                                           |
| ------------------------ | ------------------------------------------------------------------------ |
| 肩が入っていない         | 「もう少し離れて、両肩が入るようにしてください」                         |
| 手が画面端               | 「手が画面の端に近いです。少し中央で動かしてください」                   |
| 手が小さい               | 「手が小さく写っています。少しカメラに近づくか、解像度を上げてください」 |
| 顔だけ大きい             | 「上半身が入るように、カメラから少し離れてください」                     |
| 露出不足                 | 「部屋を少し明るくしてください」                                         |
| 動体ぶれ                 | 「手の動きが速すぎるか、映像が暗い可能性があります」                     |
| 身体が正面を向いていない | 「正面を向くと動きが安定します」                                         |
| 信頼度低下               | 「手や肘が隠れないようにしてください」                                   |

技術的には、`requestVideoFrameCallback()` を使うと動画フレームごとのメタデータ、`presentedFrames`、`mediaTime` などが取得でき、フレーム欠落やタイムスタンプ管理に使えます。([MDNウェブドキュメント][9])

## 17. 意味に基づく動作動作層の発火条件とブレンド比率

短い上半身クリップは、常時上書きではなく **加算合成** として使います。MediaPipe Gesture Recognizerはリアルタイムジェスチャー認識の結果、手の特徴点、左右判定などを返せるため、意味に基づく動作のレイヤーの補助入力として使えます。([Google AI for Developers][4])

発火条件の基本は次です。

```text
ジェスチャー信頼度 > 0.70
かつ手信頼性 > 0.60
かつ条件継続 150〜250ms
かつ待機期間 300〜800ms
```

ブレンド比率の目安です。

| 状況                         |       追跡 | 意味に基づく動作クリップ |
| ---------------------------- | ---------: | -----------------------: |
| 通常                         | 0.85〜0.95 |               0.05〜0.15 |
| 軽い意図検出                 | 0.70〜0.85 |               0.15〜0.30 |
| 指差し / ピース安定          | 0.60〜0.75 |               0.25〜0.40 |
| 手振り動作                   | 0.40〜0.70 |               0.30〜0.60 |
| 追跡低下中のジェスチャー継続 | 0.30〜0.50 |               0.50〜0.70 |

不自然にしないためのルールは次です。

| ルール                           | 理由                                         |
| -------------------------------- | -------------------------------------------- |
| 徐々に反映 150〜250ms            | 急にクリップへ切り替わるのを防ぐ             |
| 徐々に解除 250〜500ms            | ジェスチャー終了時の戻りを自然にする         |
| 肩・上腕は追跡寄り               | クリップで肩まで大きく上書きすると不自然     |
| 手首・指はクリップ寄りでも可     | 意味に基づく動作ジェスチャーの印象が出やすい |
| ジェスチャー表示名にヒステリシス | Open/Close/Pointingのちらつきを防ぐ          |
| 手振りは周期検出を使う           | OpenPalmだけでは誤発火しやすい               |

例えば手振りは、`Open_Palm` だけでなく、手が肩〜顔の高さにあり、左右速度の符号反転が0.5〜1.2秒内に2回以上ある、という条件を加えると誤発火が減ります。

|   1 | 中立姿勢 10秒                 | 胴体・頭部・手首細かな揺れ             |

## 19. 最初に見るべき定量指標と許容ライン

最初に見るべき指標は、次の5つです。

| 優先度 | 指標                       | 許容ラインの目安                             |
| -----: | -------------------------- | -------------------------------------------- |
|      1 | 中立姿勢での細かな揺れ     | 胴体・頭部 RMS 0.5〜1.0°以下、手首 2〜3°以下 |
|      2 | 肘の反転回数               | 固定テスト中0回                              |
|      3 | 観測欠落からの復帰時の急変 | 復帰時の角度ジャンプ10〜15°以下              |
|      4 | 追加遅延                   | 手・頭は50〜100ms、胴体は150ms以内           |
|      5 | 骨の長さばらつき           | 高信頼度時の上腕/前腕推定長CV 5〜8%以内      |

追加で見るとよい指標です。

| 指標                       | 用途                             |
| -------------------------- | -------------------------------- |
| 角速度の急増件数           | ボーン回転の瞬間的な飛び検出     |
| 画面端にあるリスク継続時間 | カメラ構図問題の検出             |
| 左右の入れ替わり回数       | 左右判定補正の評価               |
| 到達距離制限の発生率       | 腕が伸び切っている時間の割合     |
| 意味分類のちらつき         | ジェスチャー状態のちらつき       |
| 回復時間                   | 手が戻ってから安定するまでの時間 |

到達距離制限の適用割合は、固定テスト中に10〜20%を超えるなら、キャリブレーション、腕長、奥行き圧縮、目標倍率のいずれかが悪い可能性が高いです。

## 20. 「よく動くが不安定」か「控えめだが破綻しない」か

キャラクター会話アプリでは、基本方針として **「控えめだが破綻しない」** を優先すべきです。

理由は次です。

| 観点       | 判断                                                 |
| ---------- | ---------------------------------------------------- |
| 会話体験   | 破綻した大きな動きは発話内容への集中を妨げる         |
| かわいさ   | 控えめで滑らかな動きの方がキャラクター性を保ちやすい |
| 信頼感     | 肘反転や手首暴れは「壊れている」印象になる           |
| 長時間利用 | 大きく不安定な動きは見疲れしやすい                   |
| 実装安全性 | 信頼度に応じて動きを減らす方が破綻しにくい           |

ただし、単に動かないキャラクターにするのではなく、次の落とし所がよいです。

```text
胴体・肩・頭:
  安定優先、低振幅、低周波

腕:
  中程度に追従。ただし到達距離制限と肘偏りの補正を強くする

手首:
  ロールを抑え、ピッチ・ヨー中心

指:
  意味に基づく動作ジェスチャー時だけ表現を強める

高信頼度時:
  少し大きく動かす

低信頼度時:
  すぐ止めず、なめらかに控えめな姿勢へ退避
```

最終的な設計原則は、**動きの大きさを信頼度に比例させる**ことです。

```text
motionAmplitude = baseAmplitude * confidenceAdjustedExpressiveness
```

これにより、高品質に検出できているときは自然に動き、検出が不安定なときは「壊れる」のではなく「控えめに落ち着く」挙動になります。キャラクター会話アプリでは、この方が利用者にとって自然です。
