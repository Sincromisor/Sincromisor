# 設計ドキュメント運用ガイド

## 1. 目的

設計文書は現在の実装を安全に変更するために構造・契約・判断理由を説明する。本書は文書の役割、更新・分割・廃止の手順と索引からの導線を定める。表記・整形・リンク・図・TODOの共通規則は[Markdown規約](../rules/coding-md.md)に従う。

## 2. 文書の置き場所

| 内容                 | 置き場所                                            | 扱い                                                    |
| -------------------- | --------------------------------------------------- | ------------------------------------------------------- |
| 全体構造             | `architecture/`                                     | コンポーネント境界と処理の流れ                          |
| 現在設計             | `frontend/`、`backend/services/`、`infrastructure/` | 実装変更時に同期する                                    |
| 通信・ファイルの契約 | `contracts/`                                        | 提供側と利用側の互換性を管理する                        |
| 採用・棄却の理由     | `decisions/`                                        | 長期的な判断をADRに残す                                 |
| 進行中の移行計画     | `initiatives/`                                      | 完了後は現在設計へ反映し、計画を縮小するか保管する      |
| 作業経過・検証結果   | リポジトリ直下の`tasks/`                            | 設計本文へ積み上げない                                  |
| 再編前の資料         | `archive/legacy-flat/`                              | [再編前の履歴](archive/legacy-flat/README.md)を参照する |

表のパスは特記したものを除き`documents/design/`を基準とする。現在仕様の詳細は担当文書にまとめ、ほかの文書からは読む理由を添えてリンクする。契約の詳細は`contracts/`に置き、各サービスの設計へ複製しない。

## 3. 文書種別とテンプレート

不要な章は削り、文書の目的に必要な内容だけを書く。

| 種別         | 記載する内容                                                                             | テンプレート                                 |
| ------------ | ---------------------------------------------------------------------------------------- | -------------------------------------------- |
| 現在設計     | 目的・範囲、責務、主要データ・状態、設定・運用・失敗時の切り分け、変更時の確認           | [現在設計](templates/current-design.md)      |
| 契約仕様     | 提供側・利用側、エンドポイント・チャネル・送受信データ、エラー、時間切れ・再試行、互換性 | [契約仕様](templates/contract-spec.md)       |
| 設計判断記録 | 背景、選択肢、決定、影響、見直し条件                                                     | [設計判断記録](templates/decision-record.md) |
| 取り組み計画 | 目標、段階、完了条件、現在設計へ反映する項目                                             | [取り組み計画](templates/initiative-plan.md) |

現在設計へ日付付きの経過や長い移行表を、契約仕様へ内部クラス設計やUI方針を混ぜない。ADRには実装チェックリストや日々のログを、取り組み計画にはコミットごとの履歴や完了後に不要な一時メモを残さない。

## 4. 新規文書作成手順

1. [設計索引](index.md)から関連文書を探し、既存文書へ追記できるか判断する。
2. 内容に合うテンプレートを選び、不要な章を削る。
3. 冒頭の「要約」に現行構造、変更時の注意、関連文書へのリンクを3〜5行で書く。「対象範囲」には対象と非対象を明記する。
4. 契約の詳細は`contracts/`へ分離し、設計からリンクする。曖昧な文章だけで済ませず、送受信形式や条件を明記する。
5. 「変更時の確認」に同時確認する実装・設定・コマンドを書く。
6. 設計索引へ文書と読む理由を追加する。

## 5. 既存文書更新手順

1. 内容を現在設計、契約、判断記録、移行計画、作業記録に分け、担当文書を更新する。
2. エンドポイント、送受信データ、DataChannel、msgpackモデル、環境変数の変更は契約仕様へ反映する。契約変更ではフロントとサーバーの両側を確認し、関連するCompose・設定クラス・実装も同期する。
3. 長期的に必要な採用・棄却理由はADRへ、作業中の検証結果はタスクへ記録する。
4. コピー、移動、改名、試作文書から正式文書への昇格では、文書全体をMarkdown規約に照らして確認する。
5. 索引から辿れることと説明が現在の内容に合うことを確認し、関連タスクに確認結果を残す。

## 6. 分割判断基準

行数の目安は[Markdown規約の文書構成](../rules/coding-md.md#3-文書構成)に従う。次の場合も分割を検討する。

- 要約が5行に収まらない。
- UI、通信契約、移行履歴、検証ログが混在している。
- 同じ見出しに現在仕様と過去の経緯が並んでいる。
- 変更のたびに文書全体を読む必要がある。

分割時は現在有効な内容を現在設計・契約へ、履歴と判断理由を完了タスク・ADRへ移す。完了した移行計画や旧実装の説明は、現在設計の通常導線から分ける。

## 7. 導線ルール

[設計索引](index.md)は変更・調査の目的別に文書と読む理由を案内する。全作業に共通の読書順序は要求せず、本書も設計文書の作成・分割・廃止などで必要な場合に案内する。

新しいカテゴリには説明を添える。廃止文書や保管資料は現在設計と区別し、再編途中の旧文書は移行中であることを示す。

旧パスへの参照は履歴として残し、現在仕様と未完了タスクでは`tasks/`の正規IDとパスを使う。

旧資料に現在設計へ未反映の重要仕様がないかは、タスク単位で確認する。
